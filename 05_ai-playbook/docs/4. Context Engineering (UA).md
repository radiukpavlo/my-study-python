# 4. Context Engineering

**Статус:** Draft
**Дата:** 21 квітня 2026

Цей розділ описує, як налаштувати AI-агента так, щоб він розумів проєкт і видавав послідовний результат — без переписування промпту щоразу, без hallucinations на кожній задачі і без копіпасту гайдлайнів у кожен chat. Це не розділ про "як добре писати промпти": разовий промпт — це tactics, а context engineering — це інфраструктура, що живе у репозиторії і працює на всю команду.

Базова теза розділу: **контекст — це окремий артефакт проєкту, який комітиться, ревʼюїться і еволюціонує разом із кодом.** Якщо `AGENTS.md`/`CLAUDE.md` оновлюється раз на пів року, якщо rules і skills ніхто не підтримує, якщо кожен інженер копіює свої prompt-и локально — у команди немає context engineering, у неї є випадковий контекст і випадкові результати.

## Що читач має винести з цього розділу

Після прочитання інженер повинен:

- розуміти різницю між entry-point файлом, rules, skills, commands і subagents;
- вміти писати `AGENTS.md`/`CLAUDE.md`, що реально читаються агентом і утримують модель у межах project conventions;
- знати, коли правило має бути rule (always-on), а коли — skill (on-demand);
- вміти винести повторювану задачу у skill або slash-command замість того, щоб пояснювати її щоразу з нуля;
- знати, коли потрібен окремий subagent і чим він відрізняється від chat-сесії;
- знати мінімальний context-setup, без якого не починається робота на новому проєкті.

## Що таке контекст для AI-агента

Контекст — це усе, що модель бачить перед тим, як згенерувати відповідь: системний prompt інструменту, entry-point файли проєкту, явно підвантажені rules і skills, файли з репозиторію, зміст поточного chat-у, відповіді MCP-серверів.

Важливо розуміти три властивості контексту:

1. **Контекст платний.** Кожен токен коштує грошей і/або обмежений лімітом вікна. 200k токенів у Claude Opus — це не "безкоштовно багато", це приблизно 70% корисного використання до того, як якість падає.
2. **Контекст нелінійний.** Модель краще тримає те, що на початку і в кінці, і гірше — те, що посередині. Завалений контекст = впущені деталі.
3. **Контекст має TTL.** Після 60–70% заповнення вікна якість відповідей деградує. У певний момент стає дешевше відкрити новий chat, ніж "лікувати" поточний.

Звідси інженерна задача: **подати мінімально достатній контекст максимально точно — і не подавати все інше.** Саме це і є context engineering.

> 💡 **Hint:** Якщо агент почав плутати файли, "забувати" обмеження або повторювати помилки — не збільшуй промпт, а скороти контекст. У 80% випадків проблема у переповненому вікні, а не у слабкій моделі.

## Ієрархія артефактів контексту

У будь-якому з primary tools (Cursor, Claude Code, Copilot, JetBrains AI) контекст збирається з однакових будівельних блоків, хоч і називаються вони по-різному:

| Артефакт              | Коли активний                                     | Типовий вміст                                              |
| --------------------- | ------------------------------------------------- | ---------------------------------------------------------- |
| Entry-point (AGENTS.md / CLAUDE.md) | Завантажується завжди на старті сесії | Стек, команди, архітектура, naming, code style, де шукати інші артефакти |
| Rules                 | Завжди активні (або прив'язані до glob-патерну)  | Короткі нормативні правила: "завжди OnPush", "no `any`"     |
| Skills                | Завантажуються за потреби (on demand, через роутинг з entry-point) | Детальні інструкції під конкретний тип задачі: "як писати тест", "як створити component" |
| Commands              | Викликаються інженером вручну (slash-команди)     | Заготовлений prompt для повторюваного workflow              |
| Subagents             | Запускаються як окрема сесія з власним контекстом | Вузька роль із власним системним prompt-ом (reviewer, bug hunter) |
| MCP-сервери           | Активні за підписки у конфізі                     | Зовнішні знання (Jira, GitHub, Figma, framework docs)       |

Ключова ідея: **не все має бути always-on.** Якщо інструкція завжди в контексті — вона з'їдає токени навіть коли не потрібна. Розподіл "що always-on, а що on demand" — центральне рішення цього розділу.

## Entry-point: AGENTS.md / CLAUDE.md

Entry-point — це корінь дерева контексту. Усе інше (rules, skills, commands) має бути або явно підвантажено з нього, або посилатися на нього. Без entry-point файлу AI працює як junior, який щойно зайшов на проєкт: пише код, але не у стилі проєкту, не з тими командами, не з тією архітектурою.

### Два формати, одна роль

- **AGENTS.md** — відкритий формат, який читають Cursor, Copilot (через `.github/copilot-instructions.md` як fallback), Codex, JetBrains AI, більшість сучасних tools.
- **CLAUDE.md** — нативний формат Claude Code.

На проєкті тримай обидва як **symlink** один на одного, або як два файли з однаковим вмістом. Це гарантує, що будь-який tool знайде свій entry-point, а зміст не розходиться.

### Ієрархія файлів (monorepo)

У монорепо з кількома стеками один кореневий entry-point незручний: він розростається до 500+ рядків і змішує Angular-правила з PHP-правилами, які тягнуться в контекст навіть коли ти працюєш зовсім з іншою частиною.

Правильний патерн — **ієрархія**:

```
<repo>/
├── AGENTS.md                     # коротко про монорепо + посилання на рівні нижче
├── apps/
│   ├── web/AGENTS.md             # Angular-specific
│   ├── api/AGENTS.md             # PHP Symfony-specific
│   └── mobile/AGENTS.md          # Flutter-specific
└── libs/
    └── shared/AGENTS.md          # cross-cutting
```

У кореневому — обов'язково лінки на вкладені, у форматі, який агент розпізнає:

```markdown
## Applications

- See @apps/web/AGENTS.md for Angular web conventions.
- See @apps/api/AGENTS.md for PHP API conventions.
- See @apps/mobile/AGENTS.md for mobile conventions.
```

Коли інженер відкриває задачу в межах `apps/web/**`, агент завантажує кореневий + `apps/web/AGENTS.md`. PHP-правила при цьому в контекст не потрапляють.

### Мінімальна структура entry-point

Нижче — секції, без яких entry-point не можна вважати завершеним. Порядок має значення: агент читає зверху вниз і зважує ранні секції сильніше.

```markdown
# <Project Name>

Один абзац: тип проєкту, стек, головне призначення. Пишеться так, щоб новий інженер зрозумів, куди потрапив.

## Quick reference

Основні команди у форматі терміналу — install, dev, build, test, lint, type-check. Без них AI не знає, як перевірити свою роботу.

## Architecture overview

1–3 абзаци: як фізично організовано проєкт (моноліт / монорепо / мікросервіси), які ключові директорії, entry point, runtime config, routing, state, data fetching.

## Project structure

Дерево директорій до 2–3 рівнів з коротким описом кожної папки. Без цього агент починає створювати файли "де попало".

## File naming conventions

Таблиця: artifact → pattern → example. Сюди йдуть усі суфікси (`.component.tsx`, `.util.ts`, `.query.ts`, `.schema.ts` тощо), case (kebab/camel/Pascal), правила префіксів (`I` для інтерфейсів, `T` для типів).

## Before implementing anything

Правила дослідження перед написанням коду: прочитати існуючий модуль, шукати reusable код, не вводити новий patterns без потреби, слідувати існуючим conventions.

## Code style rules

Явні нормативні правила: що обов'язково, що заборонено. Сюди попадає `no any`, `OnPush`, `Maybe<T>` замість `T | null`, import order, blank lines, error handling, тощо.

## Routing to skills

Для задач із детальним протоколом — посилання на skills:

- Use /write-test skill for unit testing conventions.
- Use /write-component skill for React component architecture.
- Use /write-query skill for data fetching conventions.

## Testing

Де лежать тести, яким tool-ом запускаються, coverage-target, що обов'язково має тест, які patterns використовувати.

## AI-setup notes

- Primary tool: <Cursor / Claude Code / Copilot / JetBrains AI>
- Default model: Claude Sonnet 4.6
- Sensitive directories (AI заборонено): <список>
- Approved MCP servers: <список>
```

### Routing з entry-point у skills

Це один із найпотужніших прийомів. Замість того, щоб пакувати 500 рядків конвенцій для тестів у `CLAUDE.md` і тягти їх у кожен chat, у entry-point пишеться **роутер**:

```markdown
## Testing

Use the /write-test skill for Vitest conventions, patterns, and co-location rules.

## Data fetching

Use the /write-query skill for TanStack Query hooks, adapters, and query key factories.

## State management

Use the /write-store skill for Zustand slice architecture, setter patterns, and persistence.
```

Коли інженер пише "додай unit-тест на `event.adapter.ts`" — агент бачить тригер ("unit-тест"), завантажує саме `/write-test` skill (200–500 рядків), і працює з повним детальним контекстом для тестів. Поки задача не про тести — skill не в контексті. Один і той самий обсяг інформації, але плата токенами іде тільки за те, що реально потрібно.

Entry-point при цьому короткий (150–250 рядків) і цілком тримається у вікні навіть на довгих сесіях.

### Як заповнити швидко

1. Скопіюй `package.json` / `pom.xml` / `*.csproj` у діалог з AI і попроси згенерувати першу версію `AGENTS.md` за структурою вище.
2. Перечитай рядок за рядком — AI не знає internal naming (ULID, `I`-prefix для interfaces, kebab-case для файлів, custom eslint-правила). Ручне доповнення обов'язкове.
3. Додай розділи `File naming conventions` і `Code style rules` з посиланнями на реальні приклади у коді. Правила без прикладів часто ігноруються моделлю.
4. Додай секцію `AI-setup notes` — це робить setup self-documenting для наступного інженера.
5. Закомітити у репозиторій (не у `.gitignore`).

> 💡 **Hint:** Якщо у файлі немає `Before implementing anything` і `Routing to skills` — це не entry-point, це README для людей. AI з таким файлом буде працювати, але на 30–50% гірше, ніж міг би.

## Rules: always-on конвенції

Rules — це короткі нормативні правила, що автоматично підвантажуються у кожний chat (або у chat із відповідним glob-патерном). Вони існують для того, щоб агент не забував базових правил проєкту: "завжди OnPush", "ніколи не використовуй `@Input` — тільки `input()`", "no `any`".

### Що кладемо у rules

- Короткі нормативні правила, які **часто порушуються** агентом, якщо про них не нагадати.
- Правила, які мають виконуватися **у кожній задачі** (code style, type safety, data layer conventions).
- Правила, які прив'язані до конкретного **scope** через glob: наприклад, Angular-правила для `apps/**/*.ts` — не тягнуться в контекст, коли інженер працює з PHP.

### Що НЕ кладемо у rules

- Детальні інструкції (200+ рядків) — це skill, не rule.
- Разові правила, актуальні тільки для однієї задачі — це частина promptу.
- Правила, що дублюють те, що вже є у entry-point.
- Лінгвістичні уподобання (". . . завжди відповідай українською") — AI ігноруватиме, якщо запит прийшов іншою мовою; краще не перевантажувати.

### Структура Cursor rules

```
.cursor/rules/
├── angular-rules.mdc          # glob: apps/**/*.{ts,html}
├── typescript-rules.mdc       # glob: **/*.ts
├── php-rules.mdc              # glob: apps/api/**/*.php
└── commit-message-rules.mdc   # alwaysApply: false, manual trigger
```

Приклад `.cursor/rules/angular-rules.mdc`:

```markdown
---
description: Angular coding conventions
globs: apps/**/*.{ts,html}
alwaysApply: false
---

# Angular Rules

## Component Requirements

- `ChangeDetectionStrategy.OnPush` — required on every `@Component`. No exceptions.
- `input()` / `output()` functions — never use `@Input()` / `@Output()` decorators in new code.
- `viewChild()` / `viewChildren()` signal queries — never use `@ViewChild` decorators.
- Standalone components only — no NgModules.
- `inject()` function — use instead of constructor injection.

## Type Safety

- Never use `any` — use `unknown` when type is uncertain, then narrow with type guards.
- API responses must be typed — do not cast `Observable<unknown>` results directly.
- `Record<string, any>` is not acceptable — define proper interfaces.

## Templates

- `@if` / `@for` syntax only (not `*ngIf` / `*ngFor`).
- Avoid `ngClass` / `ngStyle` — use bindings.
```

### Структура Claude Code rules

У Claude Code "завжди активні" правила — це секції у `CLAUDE.md`. Окремої `rules/` директорії немає. Підхід:

- Короткі глобальні правила — прямо у `CLAUDE.md` (секція `Code style rules`).
- Розлогі per-scope правила — окремий `CLAUDE.md` на рівні піддиректорії (Claude Code автоматично підтягує найближчий `CLAUDE.md` вгору по дереву).

### Дисципліна

- **Rule = 1 файл = 1 scope.** Не змішуй Angular і PHP в одному rule-файлі — це не налаштується через glob.
- **Довжина правила — один рядок на пункт.** Якщо правило тягне на 20 рядків — воно має бути skill, а не rule.
- **Кожне правило — з прикладом "навпаки".** Якщо написав "no `any`" — додай під ним рядок "use `unknown`, then narrow with type guards". Агент краще виконує інструкцію з альтернативою, ніж з забороною.

> 💡 **Hint:** Якщо кожного разу доводиться у промпті писати "не забудь про OnPush" — це сигнал створити rule. Якщо доводиться писати "ось повна інструкція, як писати тест" — це сигнал створити skill. Не плутай ці сценарії; rule під skill-випадок буде проігнорований, skill під rule-випадок — роздує контекст.

## Skills: on-demand інструкції

Skill — це детальна (200–700 рядків) інструкція з конкретного типу задач, яка завантажується **тільки тоді, коли задача того типу дійсно виникла**. Це головний інструмент масштабування якості AI-роботи у команді.

### Анатомія skill

Кожен skill — окрема директорія з файлом `SKILL.md`:

```
.cursor/skills/
└── write-test/
    ├── SKILL.md            # основний файл (обов'язковий)
    ├── template.md          # опціонально: шаблон для заповнення
    └── examples/            # опціонально: reference-приклади
        └── sample.test.ts

.claude/skills/
└── write-test/
    └── SKILL.md
```

Обидва інструменти автоматично сканують відповідні директорії:

| Tool        | Project scope                  | User scope               | Також сканує (legacy / cross-tool) |
| ----------- | ------------------------------ | ------------------------ | ----------------------------------- |
| Cursor 2.4+ | `.cursor/skills/<name>/`       | `~/.cursor/skills/`      | `.agents/skills/`, `.claude/skills/` |
| Claude Code  | `.claude/skills/<name>/`       | `~/.claude/skills/`      | —                                   |

> Cursor з v2.4 нативно шукає у `.claude/skills/` як fallback — тому на проєктах, де обидва інструменти, достатньо **одного** набору skills у `.cursor/skills/` із symlink з `.claude/skills/`. Ручне копіювання не потрібне.

Frontmatter — саме за ним primary tool підвантажує skill:

```markdown
---
name: write-test
description: Write unit tests following this project's Vitest conventions, patterns, and co-location rules. Use when the user asks to "write tests", "add tests", "test this", or discusses unit testing for any source file.
---

# Write Test

Write Vitest unit tests that match the conventions already established in this codebase.

Before writing any test, **read the source file under test in full** to understand its exports, types, and dependencies. Then follow the section below that matches the artifact type.

## 1. General Conventions

### File placement
- Tests are co-located with the source file: `foo.util.ts` → `foo.util.test.ts`.
- Use `.test.ts` for non-JSX tests, `.test.tsx` when test renders JSX.

### Imports
Always import vitest functions explicitly, even though `globals: true` is set:

```typescript
import { describe, expect, it, beforeEach, vi } from 'vitest';
```

...
```

Критичне місце — `description`. Саме за ним primary tool приймає рішення, чи треба підвантажити skill у поточний chat. Формулюй його як **тригер**: перелічи фрази, слова, типи задач, які мають активувати skill.

Приклад сильного description:

> Write Vitest unit tests following this project's conventions. Use when the user asks to "write tests", "add tests", "create test file", "test this", or discusses unit testing for any source file.

Приклад слабкого:

> Instructions for testing.

Другий варіант не спрацює — модель не матиме маркерів для автопідвантаження.

### Розширений frontmatter (Claude Code)

Claude Code підтримує значно ширший набір frontmatter-полів, які перетворюють skill із простої інструкції у повноцінний конфігурований workflow:

```markdown
---
name: write-test
description: Write unit tests following Vitest conventions
when_to_use: "write tests", "add tests", "test this"
paths: "src/**/*.ts,tests/**"
allowed-tools: Read Grep Bash(pnpm vitest:*)
model: claude-sonnet-4-6
effort: high
context: fork
arguments: [file]
argument-hint: [source-file-path]
---
```

| Поле                        | Призначення                                                    |
| --------------------------- |----------------------------------------------------------------|
| `description`               | Тригер для автопідвантаження (обидва інструменти)              |
| `when_to_use`               | Додатковий контекст для тригера (Claude Code)                  |
| `paths`                     | Glob-патерни — auto-trigger тільки для файлів, що матчаться    |
| `allowed-tools`             | Попередньо дозволені інструменти (без ручного approve)         |
| `model`                     | Override моделі для цього skill                                |
| `effort`                    | Рівень зусиль (low / medium / high / max)                      |
| `context: fork`             | Запуск у ізольованому subagent (замінює окремий subagent-файл) |
| `arguments` / `argument-hint` | Позиційні аргументи з підказками в autocomplete              |
| `user-invocable: false`     | Skill доступний тільки моделі, не інженеру                     |
| `disable-model-invocation`  | Skill доступний тільки інженеру, модель не може викликати сама |
| `hooks`                     | Хуки (PreToolUse / PostToolUse), скоповані під цей skill       |

> Cursor використовує мінімальний frontmatter (`name`, `description`). Решта полів ігнорується, але не ламає файл — тому один `SKILL.md` працює в обох інструментах.

### Коли створювати skill

- Коли той самий тип задачі повторено **2+ рази** з тими самими poprawками промпту.
- Коли у кодовій базі вже є **2+ reference-приклади**, на які skill може спиратися. Без прикладів skill описує ідеал, якого немає в коді, і генерує nonsense.
- Коли детальна інструкція довша за 100 рядків — у rules її класти не можна, у entry-point вона роздує базовий контекст.

### Якщо reference-прикладів ще немає: greenfield і початок проєкту

Правило "спочатку reference-код, потім skill" створює замкнене коло на новому проєкті: skills немає, бо немає прикладів; приклади не з'являються, бо немає skills. Ось як із нього вийти.

**Фаза 1 — перші 2 тижні: без skills взагалі**

Реалізуй перші 3–5 задач без skill-файлів. Використовуй AI в режимі inline-генерації або простого chat-у, де ти описуєш конвенції прямо у промпті. На цьому етапі головне — не швидкість, а формування еталонних прикладів.

Після кожної закритої задачі запитай себе: "Чи цей код показує, як ми хочемо писати подібні речі далі?" Якщо так — залиш коментар у файлі або нотатку: `# SKILL CANDIDATE: write-component`.

**Фаза 2 — коли є 2 еталони: пишеш перший skill**

Як тільки у кодовій базі є два схожі якісні артефакти одного типу (два компоненти, два endpoint-и, два тест-файли) — вони стають reference для skill. Пишеш skill, посилаючись на ці файли через `@`.

```markdown
## Reference examples

Study these files before writing:
- @src/features/auth/login.component.ts — canonical component structure
- @src/features/profile/avatar.component.ts — same pattern, different domain
```

**Фаза 3 — підтримка якості еталонів**

Skill не кращий за reference, на який спирається. Якщо еталонний файл застарів або порушує нові конвенції — skill починає генерувати застарілий код. Правило: при зміні конвенції оновлюй не тільки skill, а й самі reference-файли.

**Альтернатива для старту: `Before implementing anything` замість skill**

Якщо проєкт зовсім новий і reference-коду немає, перший і найдешевший крок — секція `Before implementing anything` у `AGENTS.md`. Вона не вимагає прикладів і вже дає AI достатньо орієнтирів:

```markdown
## Before implementing anything

1. Read the affected module in full — understand what already exists.
2. Match the file structure and naming of the nearest similar file in the codebase.
3. If no similar file exists — propose the structure before implementing, wait for approval.
4. Do not introduce new abstractions without explicit request.
```

Ця секція працює без жодного skill і покриває 80% потреби на перших тижнях проєкту.

> 💡 **Hint:** Skill, написаний до того, як у коді є хоч один еталон — це wishlist, а не інструкція. Модель прочитає його, але виконає на 30%, бо нема чого наслідувати. Краще добрий `Before implementing anything` у `AGENTS.md`, ніж поганий skill із порожніми reference.

### Що йде в skill

Структура, що окуповується (на основі реальних skill-файлів проєктів):

1. **Short introduction** — 1–2 речення, що робить skill.
2. **Architecture Overview** — куди артефакт вписується у data flow / layer model.
3. **Directory Structure & File Naming** — де створювати файл, як його називати.
4. **Props / API pattern** — канонічний приклад з коду.
5. **Rules / Конкретні обмеження** — таблиця "do / don't" з причинами.
6. **Cautionary references** — реальні commit-и, коли це правило врятувало від регресії ("commit `a8f152a` довелось переписати, бо...").
7. **Checklist** — фінальна перевірка перед тим, як закривати задачу.

### Skill vs копіпаст у промпт

Різниця не у тому, що "skill — правильно, а копіпаст — ні". Різниця у повторюваності:

- **Завдання унікальне** (1 раз за квартал) → копіпаст у промпт.
- **Завдання типове** (щотижня) → skill.
- **Завдання типове, але тільки для одного інженера** → скористайся appendix-ом до `AGENTS.md.local` або локальним текстовим файлом. Команду цим грузити не варто.

### Skill у двох інструментах одночасно

Cursor 2.4+ нативно сканує `.claude/skills/` і `.agents/skills/` як fallback. На практиці це означає:

- **Cursor + Claude Code:** тримай skills у `.cursor/skills/`, створи symlink `.claude/skills/ → .cursor/skills/`. Cursor знайде нативно, Claude Code — через symlink. Розширені frontmatter-поля Claude Code (paths, context, hooks) ігноруються Cursor-ом без помилок.
- **Cursor + Copilot:** Copilot читає `.github/copilot-instructions.md` і може підвантажувати додаткові файли за посиланням: `See .cursor/skills/write-test/SKILL.md for testing conventions`.
- **Три інструменти одночасно:** один skill у `.cursor/skills/`, symlink з `.claude/skills/`, посилання з `.github/copilot-instructions.md`.

> ⚠️ Ніколи не тримай два окремих файли (`SKILL.md` у `.cursor/` і ще один у `.claude/`). Вони завжди розходяться після третього PR.

> 💡 **Hint:** Skill — це документація на процес, яку читає модель. Той самий skill має бути зрозумілий людині, що читає його у Code Review. Якщо людина не зрозуміла — модель теж не зрозуміє, просто не скаже про це.

## Commands: шорткати для повторюваних prompt-ів

> **Стан на квітень 2026.** У Claude Code commands (`.claude/commands/`) і skills (`.claude/skills/`) **об'єднані** — обидва формати створюють slash-команду, але skills є superset із підтримкою supporting files, auto-trigger, ізольованого контексту тощо. Існуючі `.claude/commands/` продовжують працювати, але для нових workflow рекомендовано створювати skill. У Cursor 2.4+ є команда `/migrate-to-skills`, яка конвертує legacy slash-commands у skills автоматично.

Command — це **заготовлений prompt** під конкретний workflow, який інженер викликає слешем (`/plan`, `/review`, `/verify`). Command не підвантажується автоматично — його явно викликає інженер. Це головна відмінність від skill, який агент може підвантажити сам за контекстом задачі.

### Де живуть commands

| Tool        | Директорія                    |
| ----------- | ----------------------------- |
| Claude Code | `.claude/commands/`           |
| Cursor      | `.cursor/commands/` (legacy, мігрується через `/migrate-to-skills`) |

> Для нових проєктів рекомендовано оформлювати повторювані workflow як **skills з `disable-model-invocation: true`** замість окремих command-файлів. Це дає єдиний формат, єдину директорію, і можливість пізніше увімкнути auto-trigger без переписування.

### Структура (legacy-формат, сумісний з обома інструментами)

```
.claude/commands/
├── plan.md         # згенерувати план імплементації за Jira-тікетом
├── pr-prep.md      # підготувати PR: commit, push, створити PR
├── review.md       # прогнати diff через іншу модель
├── test-gen.md     # згенерувати тести на змінені файли
└── verify.md       # lint + type-check + test + аналіз результатів
```

Приклад `plan.md`:

```markdown
I'm about to start working on a task. Help me plan the implementation before writing any code.

1. If I haven't provided a ticket number, ask me for one. If I have, fetch it from Jira and read the title, description, acceptance criteria, and comments.
2. Analyse the codebase — identify which files, modules, and patterns are relevant. Check existing implementations of similar features for patterns to follow.
3. Propose an implementation plan with:
   - Files to create or modify (with specific paths)
   - Order of operations (what to build first)
   - Database changes needed (migrations, new entities)
   - API changes (new endpoints, modified responses)
   - Frontend changes (components, routes, services)
   - Test strategy
4. Flag risks — potential breaking changes, edge cases, dependencies on other teams.
5. Break into timed phases (planning, implementation, testing, review) for tracking.

Save the plan to PLAN.md so we can reference it during implementation.

Do NOT start implementing yet — wait for my approval of the plan.
```

### Базовий стартовий набір

На будь-якому проєкті окуповуються 4 команди:

| Команда      | Коли використовується                                | Що робить                                                     |
| ------------ | ---------------------------------------------------- | ------------------------------------------------------------- |
| `/plan`      | Старт будь-якої задачі з нетривіальним обсягом        | Завантажує тікет, аналізує код, пропонує план, зберігає у `PLAN.md` |
| `/review`    | Перед commit / push                                  | Ре-прогін diff через незалежну модель, пошук багів і regression |
| `/verify`    | Після будь-якої правки                               | Запускає `lint` + `type-check` + `test` і аналізує провали   |
| `/pr-prep`   | Коли код готовий до мержу                            | Формує commit message, створює PR, заповнює template          |

> 💡 **Hint:** Свій `/plan` створюй тільки тоді, коли **вбудований Plan mode** primary-tool-а тебе не влаштовує. У Cursor є окремий Plan mode (agent перемикається у read-only, будує план, запитує approve перед кодом), у Claude Code — plan mode через `Shift+Tab` / `/plan`. Для 80% задач цього вбудованого режиму достатньо. Кастомний `/plan` як slash-command має сенс, коли тобі потрібні специфічні кроки, яких стандартний режим не робить: автоматично підтягнути тікет із Jira, перевірити merged worktrees, створити гілку/worktree за naming convention проєкту, зберегти план у фіксований `PLAN.md`. Якщо твої вимоги покриваються стандартним Plan mode — не дублюй його своєю командою, інакше у команди буде два різні "план-флоу" і розбіжності у тому, що вважати планом.

### XML-формат для reusable prompt-ів

Для складних команд (особливо з умовними гілками) добре працює XML-подібна розмітка. Модель читає її стабільніше, ніж вільний текст:

```xml
<task>
  <context>
    Adding a new REST API endpoint for resource deletion.
  </context>

  <inputs>
    <resource>{{resource_name}}</resource>
    <method>DELETE</method>
  </inputs>

  <steps>
    <step>Read api-conventions.md in full.</step>
    <step>Find an existing DELETE endpoint to use as template.</step>
    <step>Generate controller, service, validation schema, unit test.</step>
    <step>Run /verify command after writing.</step>
  </steps>

  <constraints>
    <no-new-patterns>true</no-new-patterns>
    <follow-existing-style>true</follow-existing-style>
  </constraints>
</task>
```

Це не обов'язковий формат — звичайний markdown теж працює. XML виграє тоді, коли команду викликають тією самою структурою, а варіативність — тільки у параметрах.

### Command vs skill: актуальна різниця

> У Claude Code commands і skills **технічно об'єднані** — обидва створюють `/slash-command`. У Cursor 2.4+ skills є рекомендованим форматом із `/migrate-to-skills` для конвертації. Нижче — концептуальна різниця, яка зберігається незалежно від формату файлу.

| Критерій                | Command (workflow prompt)                    | Skill (on-demand інструкція)               |
| ----------------------- | -------------------------------------------- | ------------------------------------------ |
| **Хто ініціює**         | Завжди інженер (`/plan`, `/verify`)          | Агент сам або інженер — залежно від `description` |
| **Що містить**          | Повний prompt — **що саме зробити**          | Конвенції та правила — **як саме робити**   |
| **Варіативність**       | Змінна частина — параметри кожного виклику   | Стабільна частина — конвенції проєкту       |
| **Коли створювати**     | Однаковий prompt набирається 3+ рази         | Однаковий тип задачі з однаковими попраками 2+ рази |
| **Типовий розмір**      | 10–50 рядків                                 | 200–700 рядків                             |
| **Рекомендований формат** | Skill з `disable-model-invocation: true`   | Skill зі strong `description`              |

**Практичне правило:** якщо інженер щодня набирає один і той самий prompt — це command. Якщо набирає *подібний* prompt, але щоразу з відмінностями — це skill.

> 💡 **Міграційна порада:** на нових проєктах не створюй окремі `.claude/commands/` чи `.cursor/commands/` файли. Оформлюй все як skills — для "ручних" workflow додавай `disable-model-invocation: true` у frontmatter. Це дає єдину директорію, єдиний формат і можливість пізніше дозволити агенту викликати workflow автоматично.

## Subagents: окрема роль із власним контекстом

> ⚠️ **Попередження перед цим розділом.** Subagents — це **advanced-інструмент**, не базовий. Якщо ти тільки починаєш працювати з AI-агентом і ще не маєш стабільного циклу Plan → Apply → Review з rules, skills і commands — **не починай із subagent-ів**. Вони дають ілюзію контролю, але без зрілого розуміння того, що і чому робить основний агент, subagent лише помножує проблеми: важче діагностувати, чому результат поганий; дорожче за токенами; більша площа для помилок у permissions і scope.
>
> Правило великим пальцем: subagent має сенс тільки тоді, коли ти вмієш **точно пояснити**, чому поточний slash-command або skill не закриває задачу, і **точно бачиш**, у чому саме isolated context або окрема модель дадуть виграш. Якщо на це питання немає конкретної відповіді — subagent тобі ще не потрібен.
>
> На перші 1–2 місяці роботи з AI цілком достатньо **нуля subagent-ів**. Додавай їх, коли базовий цикл уже працює і ти бачиш конкретну проблему, яку без них не вирішити.

**Два способи створення subagent-а:**

1. **Окремий agent-файл** (`.claude/agents/*.md`) — класичний підхід, описаний нижче.
2. **Skill з `context: fork`** (Claude Code) — skill із frontmatter `context: fork` запускається в ізольованому subagent-контексті. Це простіший варіант, якщо subagent не потребує окремої persistent memory.

Subagent — це окрема сесія моделі з вузькоспеціалізованим системним промптом, яку запускає основний агент як tool-call. На відміну від чату, subagent:

- має **власний isolated context** — не тягне на себе історію поточного chat-у;
- має **власну модель** (часто Opus для складних, Sonnet/Haiku для рутинних);
- має **власну memory** (persistent notes, окремі від основної сесії);
- отримує результат **як резюме**, а не як пересипання сирих повідомлень.

### Коли потрібен subagent

- **Роль виходить за межі поточного mental model чату.** Наприклад, поточний chat — про імплементацію, а треба незалежний code review. У тому ж чаті модель буде підтверджувати свою ж роботу — це bias.
- **Задача потребує окремих persistent notes.** Bug-hunter тримає власний список "tip-ів", де часто ховаються помилки; reviewer тримає власний список anti-pattern-ів, помічених у проєкті.
- **Задача багаторазова і дорога за токенами.** Bug-hunting на Opus проганяється у окремій сесії з коротким fokused system-prompt — дешевше, ніж тягти ту саму логіку у головний chat.

### Структура subagent-а (Claude Code)

```
.claude/agents/
├── senior-bug-hunter.md
├── pr-reviewer.md
└── docs-explorer.md
```

Приклад `senior-bug-hunter.md` (скорочено до суті):

```markdown
---
name: senior-bug-hunter
description: "Use this agent when you want a thorough, senior-level review of recently edited files focused exclusively on bugs, logical errors, and inconsistencies. This agent does NOT review style, naming conventions, or architecture — it hunts for things that will break at runtime."
model: opus
memory: project
---

You are a senior software engineer with deep expertise in Angular (signals, RxJS), TypeScript, PHP/Symfony. You hunt exclusively for:

1. Bugs — things that will break at runtime
2. Logic errors — code that runs but produces wrong results
3. Race conditions & timing issues
4. Silent failures — errors swallowed without handling
5. State management bugs — stale closures, signal timing, subscription leaks

You do NOT comment on naming, style, architecture (unless it directly causes a bug).

## How you work

1. Use `git diff --name-only` to find changed files.
2. Read each changed file plus its closest dependencies.
3. Hunt through these lenses: Data Flow, Async/Reactive, State Consistency, API Contract, Cross-File Consistency, Template, Security, Boundary Conditions.
4. Report each bug with: Severity, File:Line, What, Why it breaks, Fix.
5. If zero bugs — say so clearly. Do not manufacture issues.

## Project knowledge

This is an Angular monorepo (Nx, Angular 20, TS 5.9) with PHP Symfony backend.
Standalone components, signals, OnPush, @if/@for control flow, CSS variables for theming, OAuth 2.0 device flow.
```

### Типовий набір subagent-ів на проєкті

- **Code reviewer** — незалежна перевірка diff перед PR. Модель Opus, промпт про bugs + security + project conventions.
- **Bug hunter** — пошук логічних помилок у змінених файлах. Запускається перед commit, не після PR.
- **Architect / planner** — аналіз великих задач, що торкаються кількох модулів, з окремою persistent memory про архітектурні рішення.
- **Docs explorer** — окрема сесія на глибоке читання зовнішньої документації (Angular, React, MUI release notes), не засмічуючи головний chat.

### Subagent ≠ multi-agent orchestration

На рівні 1 цього плейбука **не** вводиться практика повноцінних multi-agent систем (агент A робить планування, передає агенту B, той агенту C з автоматичним зв'язком). Це L2-сценарій, окупний тільки на стабільних повторюваних pipeline-ах (типу auto-QA). Для щоденного циклу "plan → apply → review" одного subagent-reviewer-а достатньо.

### Permissions для subagent-ів

Кожен subagent успадковує permissions від основного процесу Claude Code, але має власний allow-list. Мінімум — whitelist команд, які reviewer-агент може запускати без ручного approve:

```json
{
  "permissions": {
    "allow": [
      "Bash(git diff:*)",
      "Bash(git log:*)",
      "Bash(pnpm run lint:*)",
      "Bash(pnpm run type-check:*)"
    ]
  }
}
```

> 💡 **Hint:** Subagent — це персоналізація моделі, а не ще один чат. Якщо subagent приємно виконує роботу, яка могла б бути зроблена slash-командою — це signal, що subagent зайвий. Субагент виправдовується тільки коли виграш у якості (через isolated context або persistent memory) помітний на око.

## Як обрати: rule, skill, command, subagent, prompt?

Частіша плутанина на старті — "а що саме треба створити в цій ситуації?" Коротка decision matrix:

| Умова                                                                    | Відповідь      | Рекомендований формат файлу |
| ------------------------------------------------------------------------ | -------------- | --------------------------- |
| Правило коротке (1–3 рядки), має діяти у кожній задачі цього стеку        | **Rule**       | `.cursor/rules/*.mdc` / секція у `CLAUDE.md` |
| Правило детальне (100+ рядків), специфічне для типу задачі                | **Skill**      | `.cursor/skills/<name>/SKILL.md` |
| Готовий prompt, який я раз за разом набираю руками                       | **Command**    | Skill з `disable-model-invocation: true` |
| Окрема роль, яку запускаю на готовий код (review, bug-hunt)               | **Subagent**   | Skill з `context: fork` (Claude Code) / `.claude/agents/*.md` |
| Разова потреба, унікальна для поточної задачі                            | **Inline prompt** | — |

Критерії перевірки:

- Якщо інструкція **> 200 рядків** — це точно не rule.
- Якщо інструкція **ніколи не потрібна без явного виклику** — це command (skill з `disable-model-invocation`), не rule і не auto-trigger skill.
- Якщо інструкція **запускається на результат іншої інструкції** — це subagent (skill з `context: fork` або окремий agent-файл), не частина головного флоу.

## Практичні тактики

Нижче — короткий набір прийомів, які дають відчутний виграш у якості контексту.

### Прямі посилання на файли через `@`

Замість того, щоб описувати "у модулі auth є такий-то код" — посилайся на файл напряму:

> Додай метод `refreshToken` у @libs/auth/src/services/auth.service.ts, за аналогією з методом `login`.

Модель бачить точний файл, не розшукує його семантичним пошуком, і не hallucinate-ить інтерфейс. Економія токенів — 30–50% на типовій задачі, якість результату — помітно вища.

### "Before implementing anything"

Стандартна секція в entry-point, що змушує агента спочатку прочитати модуль, а потім писати. Без цієї секції модель одразу починає генерувати і часто дублює те, що вже є поруч:

```markdown
## Before implementing anything

Always explore before writing code. Before implementing any feature, fix, or addition:

1. Read the affected module in full — understand what already exists.
2. Search for reusable code — grep for similar names and patterns across the codebase. Reuse what exists; extend only when necessary.
3. Identify duplication — if the requested change would duplicate logic that already exists elsewhere, stop and flag it.
4. Follow the module's existing conventions — match file structure, naming, data-flow patterns, and abstraction level.
5. Propose before implementing non-trivial changes — if the implementation requires touching more than one module, outline your approach first.

The goal is a codebase that stays coherent. When in doubt: read more, write less.
```

Це не стилістична рекомендація — це ключовий prompt-engineering trick, що змінює поведінку моделі з "generate-first" на "read-first".

### Terminology lock

Термінологія у проєкті легко розпливається: "hotkey" vs "keyboard shortcut", "drawer" vs "panel", "event" vs "earthquake". Модель схильна вводити новий термін, якщо її не зупинити, і через 3–4 задачі у коді з'являється 2–3 назви для того самого.

Явне правило у entry-point:

```markdown
## Feature terminology

- Before introducing a new domain term, grep the codebase for existing usage and match it.
- If the term is genuinely new, propose the choice before scattering it across files, state properties, and UI text.
- Terminology must match across every layer: state property names, component names, file names, function names, interface names, test descriptions, UI strings.
- A partial rename is worse than the original inconsistency.
```

### Clear context часто

Агент у довгій сесії починає плутати файли і втрачати точність після 60–70% заповнення вікна. Практика, що окуповується:

- Декомпозуй задачу на підзадачі (крок у `PLAN.md`).
- Після кожної великої підзадачі — `clear`/новий chat.
- У новий chat завантажуй тільки resume попереднього (1–2 абзаци) і релевантні файли через `@`.

Це коштує зайвих 30 секунд на старті нового chat-у і заощаджує години налагодження того, що агент "раптом забув" про обмеження, прийняте годину тому.

### Fix the file, not the prompt

Якщо агент систематично порушує правило, що прописане у entry-point — проблема переважно не в моделі, а у формулюванні. Патерн виправлення:

1. Візьми конкретний випадок порушення.
2. Переформулюй правило з прикладом "правильно / неправильно":

```markdown
## Nullable types

❌ Don't:
const user: User | null = getUser();

✅ Do:
const user: Maybe<User> = getUser();

Always use `Maybe<T>` for nullable values (declared in `src/global.d.ts`).
```

3. Додай короткий `## Rules (Things to Avoid)` розділ у відповідний skill — модель стабільніше виконує explicit-negative правила.

### Skill — тільки з reference code

Писати skill "з нуля" — марна робота: агент виконує інструкцію на словах, але скочується до generic-паттерну, бо **в коді проєкту такого ще немає**. Послідовність:

1. Руками зроби 2–3 приклади того, що має бути (компонент, тест, endpoint).
2. Переконайся, що ці приклади — **еталон** (code review, якість вища за середню по кодовій базі).
3. Тоді пиши skill, посилаючись на ці приклади і використовуючи їх як еталон.

Зворотна послідовність генерує skill, який модель не може виконати, і код, який не відповідає жодному реальному прикладу.

> 💡 **Hint:** Якщо скіл описує ідеал, якого немає у кодовій базі — це не skill, це wishlist. Модель його проігнорує або виконає на 30%. Приведи reference-код у потрібний стан **перед** тим, як писати skill.

## Антипатерни

Типові помилки, що зустрічаються у командах, які тільки починають:

- **500+ рядків у `AGENTS.md`.** Entry-point, який не влазить у контекст навіть на Sonnet, — це корупційна яма токенів і недисципліноване зведення всього в одне місце. Виноси у rules / skills / per-app файли.
- **"Правила" на одне використання.** Задача прийшла разова, інженер додав абзац у `AGENTS.md`, задача закрилася. Абзац залишився у контексті назавжди. Правило: все, що разове — inline у prompt, не в entry-point.
- **Skill без frontmatter.** Файл `.cursor/skills/write-test/SKILL.md` без `name` і `description` просто не підвантажується автоматично. Перевірка: після створення skill — відкрити новий chat, сказати "write test for foo.util.ts" і переконатися, що skill активувався.
- **Дублювання між rules і skill.** Те саме правило дубльоване у `.cursor/rules/angular-rules.mdc` і у `.cursor/skills/write-component/SKILL.md`. При оновленні одного — забувають оновити інше. Правило повинне жити в одному місці, інше — посилається.
- **Skill описує ідеал, якого немає в коді.** Skill каже "використовуй pattern X", у коді нема жодного прикладу X, агент робить щось середнє. Відбувається, коли інженер пише skill "авансом". Лікування — спочатку reference-код, потім skill.
- **Subagent замість slash-команди.** Окремий subagent створюється для речі, яка могла б бути `/command`. Витрати токенів вищі, контроль гірший. Subagent виправданий тільки коли isolated context реально дає виграш у якості.
- **Застарілий `AGENTS.md`.** Стек оновився, з'явилися нові правила, файл не оновили. Модель продовжує працювати за старими конвенціями і конфліктує з новим кодом. Лікування — `AGENTS.md` у PR-checklist: якщо міняєш стек / conventions, онови entry-point.
- **Кілька конфліктуючих entry-point-ів.** `AGENTS.md`, `CLAUDE.md`, `.cursor/rules/general.mdc`, і `.github/copilot-instructions.md` — у всіх чотирьох написано про OnPush, але в різних формулюваннях. Модель отримує суперечливий сигнал. Лікування — один source of truth (AGENTS.md), решта — через symlink або через `See @AGENTS.md`.

## Чек-лист готовності до розділу 5 (Core Workflow)

Перед тим, як переходити до ядра робочого циклу (plan → apply → review), у інженера має бути:

- Entry-point файл (`AGENTS.md`/`CLAUDE.md`) з повним набором секцій і розміром до 300 рядків.
- Ієрархія entry-point для монорепо — якщо проєкт монорепо.
- Хоча б один **rules** файл з always-on правилами стеку, прив'язаний до scope через glob.
- Хоча б два **skills** для повторюваних типів задач (типово: `write-test` + `write-<artifact>`).
- Базовий набір **workflow skills** (з `disable-model-invocation: true`): `/verify`, `/review`. Кастомний `/plan` — тільки якщо вбудований Plan mode primary-tool-а не закриває потреби; інакше користуємось стандартним режимом.

- `Before implementing anything` секція у entry-point, наповнена реальними прикладами.
- Команда знає відмінності між rule / skill / command / subagent і вміє обрати відповідний тип артефакту під нову потребу.

Якщо хоча б один пункт не закритий — повернися до відповідного підрозділу. Робочий цикл з розділу 5 припускає, що контекст уже інженерно поставлений, і без цієї бази буде постійно спотикатися на "чому AI не знає про X" і "чому AI вигадав файл Y".
