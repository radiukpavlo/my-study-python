# A. Словник термінів

**Статус:** Draft
**Дата:** 21 квітня 2026

Цей довідник фіксує єдине значення термінів, що вживаються у плейбуку. Мета — усунути плутанину у командній комунікації, PR-обговореннях і документації: щоб "skill", "rule", "subagent", "plan mode" означали одне й те саме для кожного інженера, а не розходилися на синоніми і доморощені інтерпретації.

Словник **не** є вступом до AI-розробки. Він розрахований на читача, який уже проходить плейбук і повертається за точним значенням у процесі роботи. Для вивчення концепцій з нуля читай відповідні розділи — після кожного терміна стоїть посилання на розділ, де практика описана детально.

## Як користуватися словником

- Терміни згруповано тематично, не за алфавітом — щоб суміжні поняття були поруч і видно було відмінності (rule vs skill vs command, Plan → Apply → Review, reasoning vs balanced vs execution models).
- Англомовні назви (Cursor, Claude Code, CLAUDE.md, `AGENTS.md`, MCP) не перекладаються — вони — нативні ідентифікатори інструментів і файлів, переклад створює невідповідність із документацією.
- Якщо термін вживається у кількох значеннях залежно від контексту — це фіксується явно у полі "Контекст".
- Якщо термін — жаргонізм спільноти (vibe coding, slopsquatting, YOLO-mode), це позначено як "сленг"; у офіційній документації використовуй нейтральні відповідники.

> 💡 **Hint:** Якщо у PR-ревью стикаєшся з терміном, якого тут немає, — це кандидат на додавання. Відкривай PR до цього файлу з короткою карткою "Термін → Означення → Де використовується". Локально пояснити колезі "що я мав на увазі" — розумно один раз; другий раз — вже втрата часу команди.

## Основні принципи та ролі

**AI-augmented engineering.** Модель розробки, у якій AI виконує частину інженерних задач (генерація коду, тестів, документації, планів), а людина відповідає за архітектуру, ревʼю і фінальні рішення. Не "AI пише код за мене" і не "я пишу код із підказками" — окрема дисципліна з власним циклом і набором артефактів. Основа всього плейбука; детально — розділ 1.

**Human-in-the-loop.** Принцип, за яким за кожен рядок коду відповідає людина, а не AI. AI — виконавець; інженер — архітектор і reviewer. Практичні наслідки: не merge-имо код, який інженер не прочитав; AI не комітить і не push-ить самостійно; якщо інженер не може пояснити AI-код на ревʼю, код не готовий. Див. розділ 1.

**Plan-first.** Принцип "код пишеться після плану, ніколи до". Для нетривіальних задач перший промпт — запит на план, не на код. План ревʼюється людиною до того, як AI торкнеться коду. Поганий план, помножений на швидкість AI, = поганий код у великому обсязі. Див. розділ 1, розділ 5.

**Trust but verify.** Принцип, за яким AI-вивід завжди перевіряється — ревʼю, лінт, тести, cross-model verification. Довіра без перевірки — найдорожча помилка в AI-розробці. Оформляється як фаза Review у циклі Plan → Apply → Review.

**Context over prompt.** Принцип, за яким якість AI-виводу на 80% визначається контекстом (entry-point, skills, rules, reference-код), а не формулюванням окремого промпту. Наслідок: коли AI вперто робить "не так", правильна реакція — оновити skill/rule, а не переписувати prompt увосьме.

**Small scope, clean context.** Принцип "один агент = одна задача = один контекст". Довгі сесії деградують після 60–70% заповнення вікна; велику задачу ріжуть на підзадачі і прогоняють кожну окремо у власному chat-і.

**Lazy prompt.** Стиль взаємодії, за якого інженер пише мінімальний запит ("додай refresh token за аналогією з login"), а решту потрібного контексту модель бере з entry-point, rules і skills. Ознака зрілого context engineering: один рядок-запит → повноцінна точна реалізація. Протилежність — перепакування всього контексту у кожен промпт.

**Engineer-as-architect.** Операційне правило з розділу 1: інженер відповідає за постановку задачі, план, контекст, ревʼю кожного diff, фінальну якість і рішення "AI тут не підходить — пишу руками". Не "набирає код посимвольно" і не merge-ить без ревʼю.

**Freedom of choice (policy).** Політика: компанія не нав'язує конкретний toolset. Інженер вільний обирати інструменти за умови дотримання principles з розділу 1 і project-specific constraints. Не означає "роби що хочеш" — принципи і client constraints — обов'язкові.

## Рівні зрілості (maturity model)

**Level 1 — Assisted coding.** Цикл Plan → Apply → Review на кожну задачу; AI працює як "швидкий junior під ревʼю". Baseline для всіх інженерів. Повне покриття у цьому плейбуці.

**Level 2 — Spec-driven development.** Spec (ADR, guideline, blueprint) генерується і ревʼюється **до** коду; код — деривація від spec. Передбачає стабільний Level 1 і проєкт зі spec-процесом. У плейбуці згадується оглядово.

**Level 3 — AI-first SDLC.** Агентські системи (orchestrator + subagents + hooks) автоматизують SDLC; людина — оператор. Експериментальний режим; у v1 плейбука не покривається.

## Інструменти, середовище, моделі

### Клас інструменту

**Primary tool.** Основний AI-інструмент, через який інженер виконує 80%+ роботи: code generation, chat, agent mode, context management. Обирається один per проєкт на інженера. Примітки: Cursor, Claude Code, GitHub Copilot, JetBrains AI Assistant — усі вважаються primary-класу. Див. розділ 2.

**Helper tool / auxiliary tool.** Допоміжний інструмент, що закриває окрему нішу поверх primary: ChatGPT/Gemini як друга думка, Codex як незалежний reviewer, Ollama для sensitive коду, Spokenly для голосового вводу. Не primary-замінник, а окрема роль. Див. розділ 2.

**IDE-centric tool.** AI-інструмент, вбудований в IDE (Cursor, GitHub Copilot у VS Code/JetBrains, JetBrains AI). Сильний на задачах 1–5 файлів із видимим inline-ревʼю. Див. розділ 2.

**Terminal-centric tool / CLI-agent.** AI-агент, що живе у терміналі (Claude Code CLI). IDE-agnostic, сильний на autonomous multi-file задачах, long refactor, mass-edit, agentic research. Див. розділ 2, розділ 7 (§7.3.3).

**MCP (Model Context Protocol).** Відкритий протокол, за яким AI-інструмент отримує зовнішні дані і виконує зовнішні дії (Jira, Figma, GitHub CLI, документація фреймворків). **MCP-сервер** — конкретна реалізація протоколу для однієї інтеграції. Підключається у конфігу tool-а; активний за підписки у конфізі. Див. розділ 3, розділ 4.

**VDI (virtual desktop infrastructure).** Ізольоване віддалене робоче середовище клієнта, куди не завжди можна встановити додаткові AI-інструменти. Project-level constraint: "працюй у тому, що доступно у VDI; інші tools — для offline research". Див. розділ 2.

### Клас моделі

**Reasoning model / smart model.** Клас моделей, оптимізованих під глибокий reasoning, multi-step задачі, архітектурні рішення (Claude Opus). Повільніші і дорожчі; рекомендований діапазон використання — 10–20% часу інженера (plan, architecture, complex debug).

**Balanced model.** Клас із оптимальним балансом якості та швидкості для 90% повсякденного коду (Claude Sonnet, GPT-4o / GPT-5.x). Default-вибір для feature implementation, тестів, документації. 50–60% часу інженера.

**Execution model / fast model.** Клас швидких моделей для boilerplate, automation, рутинних операцій (GPT Codex, Gemini Flash). Сильні, коли швидкість важливіша за reasoning.

**Large-context model.** Модель із розширеним context window (Gemini Pro — до 1M токенів). Рекомендується як **допоміжний reader** для аналізу великих codebases (> 100k токенів) — не як primary.

**Local model / private model.** Модель, що працює на машині інженера без передачі даних назовні (Ollama з Qwen Coder, DeepSeek; LM Studio). Використовується для sensitive-зон, NDA-коду, air-gapped environments. Нижча якість, повний контроль над даними.

**Model routing.** Свідомий вибір моделі per task: Opus — для плану і складного, Sonnet — для виконання, Codex/GPT — для verification і автоматизації, Local — для sensitive. Default правило: Sonnet. Opus — лише коли задача явно перевищує Sonnet. Див. розділ 2.

**Multi-model verification / cross-model verification.** Практика: генеруєш рішення однією моделлю, перевіряєш іншою. Різні моделі навчені на різних корпусах і мають різні blind spots — збіг відповідей підвищує впевненість, розбіжність — сигнал до human review. Для critical decisions, не для рутини.

**Dual-model verification.** Формалізована версія multi-model verification: одна модель на план, інша на bug-hunt у diff-і. Окупається на задачах із високою ціною помилки; на рутині — overhead.

**Hallucination.** Вивід моделі, що виглядає достовірним, але не відповідає реальності: неіснуючий API, вигаданий файл, видуманий метод, signatures, які не існують. Типовий наслідок недостатнього контексту або занадто загального промпту. Лікування — точні посилання на файли через `@`, reference-код, явна заборона "робити за аналогією" без прикладу.

### Обсяг і вартість

**Context window.** Ліміт токенів, що модель бачить в одному запиті (200k у Claude Opus, 1M у Gemini Pro). Перевищити не можна; наближення до ліміту деградує якість. Див. розділ 4.

**Context TTL.** Практичний ліміт якісного використання вікна — зазвичай 60–70% від максимуму. Після цього модель починає плутати файли, "забувати" обмеження, повторювати помилки. Після TTL дешевше відкрити новий chat, ніж "лікувати" поточний.

**Token budget.** Місячний або добовий ліміт токенів у рамках підписки (Claude Max, Cursor Pro+, Ultra). Інженер свідомо розподіляє його між reasoning-моделлю (дорого) і balanced/execution (дешевше). Див. розділ 2.

**Token overage.** Ситуація, коли інженер перевищує ліміт tier і робота паузиться або стає дорожчою за per-token ціною. Типова причина — Opus на задачах, де достатньо Sonnet, або subagent-orchestration без depth limit. Див. розділ 7.

**Context bloat.** Стан, у якому вікно заповнене нерелевантним контекстом (rules, що не стосуються задачі; skills, які не потрібні; історія старих спроб). Наслідок — модель витрачає увагу на непотрібне і ігнорує ключове. Лікування — `/clear` і новий chat із мінімально необхідним контекстом.

## Артефакти контексту

**Context engineering.** Інженерна дисципліна налаштування контексту AI-агента: ієрархія файлів, rules, skills, commands, MCP-серверів; рішення про те, що always-on, а що on-demand; дисципліна підтримки у репозиторії. Окремий артефакт проєкту, що комітиться, ревʼюїться і еволюціонує разом із кодом. Центральний об'єкт розділу 4.

**Entry-point.** Корінь дерева контексту — файл, що завантажується завжди на старті сесії (`AGENTS.md` або `CLAUDE.md`). Містить стек, команди, архітектуру, naming, code style, роутинг у skills. Без entry-point AI працює як junior, що щойно зайшов на проєкт. Див. розділ 4.

**AGENTS.md.** Відкритий формат entry-point, який читають Cursor, Codex, JetBrains AI, більшість сучасних tools. Стандарт де-факто у спільноті. На проєкті зазвичай тримається як symlink або дублікат `CLAUDE.md`, щоб обидва tool-класи знайшли свій файл. Обов'язковий файл у day-1 checklist (розділ 4).

**CLAUDE.md.** Нативний формат entry-point для Claude Code. Ієрархічний: Claude Code автоматично підтягує найближчий `CLAUDE.md` уверх по дереву, що зручно для монорепо з per-app конфігурацією. Функціонально збігається з `AGENTS.md`; тримається синхронно через symlink.

**Copilot instructions file (`.github/copilot-instructions.md`).** Єдиний project-level файл для GitHub Copilot. Фактично той самий entry-point, тільки у спеціальному шляху. Для підтримки синхронізованості — або symlink на `AGENTS.md`, або посилання `See @AGENTS.md` у тілі.

**Rule (Cursor rule, `.mdc`).** Коротке нормативне правило, що автоматично підвантажується у кожний chat (або у chat із glob-scope). Приклад: "завжди OnPush", "no `any`", "use `Maybe<T>`". Обсяг — 1 рядок на пункт; повний файл — 10–30 рядків. Лежить у `.cursor/rules/<scope>-rules.mdc`. Не містить детальних інструкцій і не дублює skill. Див. розділ 4.

**Skill.** Детальна (200–700 рядків) інструкція під конкретний тип задачі, що завантажується **on-demand** за тригером у `description`. Лежить у `.cursor/skills/<name>/SKILL.md` (Cursor) або `.claude/skills/<name>/SKILL.md` (Claude Code). Приклади: `/write-test`, `/write-component`, `/write-query`. Створюється після 2+ повторень патерну і наявності 2+ reference-прикладів у коді. Див. розділ 4.

**Command (slash-command).** Заготовлений prompt під повторюваний workflow, що викликається інженером вручну (`/plan`, `/verify`, `/review`, `/pr-prep`). Лежить у `.claude/commands/<name>.md` або `.cursor/commands/<name>.md`. Відмінність від skill: command **викликається явно**, skill — автоматично за тригером. Див. розділ 4, розділ 6.

**Subagent.** Окрема сесія моделі з вузькоспеціалізованим системним промптом, запускається основним агентом як tool-call. Має isolated context, власну модель, власну memory. Типові ролі: code reviewer, bug hunter, architect, docs explorer. Advanced-інструмент — вводиться після стабілізації базового циклу, не раніше. Див. розділ 4.

**Hook.** Автоматичний trigger у Claude Code (PreToolUse, PostToolUse, SessionStart), що запускає зовнішній скрипт на певній події життя сесії. Типові use case: автоматичний `lint` + `type-check` після кожного AI-редагування, заборона модифікацій у sensitive директоріях. Див. розділ 3.

**Glob / scope.** Шаблон, що обмежує область дії rule або skill конкретними файлами (`apps/**/*.ts`, `libs/**/*.php`). Rule із glob-ом не тягнеться у контекст, коли інженер працює поза scope — це економія токенів. Див. розділ 4.

**Frontmatter.** YAML-блок на початку `SKILL.md` або subagent-файлу з полями `name`, `description` (обов'язкові), опційно `model`, `memory`, `allowed-tools`. За `description` primary tool приймає рішення, чи підвантажувати skill. Skill без frontmatter не активується автоматично. Див. розділ 4.

**Symlink (у контексті контекстних файлів).** Прийом синхронізації `AGENTS.md` і `CLAUDE.md` (або skill-файлів між `.cursor/skills/` і `.claude/skills/`): один файл — єдине джерело правди, другий — посилання. Ручне копіювання завжди розходиться, symlink — ні.

**Routing to skills.** Секція у entry-point, що перелічує доступні skills і тригери їх активації: "Use `/write-test` skill for unit testing conventions". Ключовий прийом, що дозволяє тримати entry-point коротким (150–250 рядків), підвантажуючи детальні skill-и тільки під конкретний тип задачі. Див. розділ 4.

**Before implementing anything.** Стандартна секція у entry-point, що змушує агента спочатку прочитати модуль, потім писати. Змінює поведінку моделі з "generate-first" на "read-first" і зменшує дублювання. Обов'язкова у day-1 setup-і (розділ 4).

**Terminology lock.** Правило у entry-point, що забороняє моделі вводити новий domain-термін без перевірки існуючого вживання у коді. Захист від розповзання синонімів ("hotkey" vs "shortcut", "drawer" vs "panel"). Див. розділ 4.

**Entry-point hierarchy.** Патерн організації entry-point-ів у монорепо: кореневий `AGENTS.md` містить опис монорепо і посилання на per-app `AGENTS.md`. Коли інженер відкриває задачу у scope одного app-а, агент завантажує кореневий + app-level; інші не потрапляють у контекст. Див. розділ 4.

## Робочий цикл

**Plan → Apply → Review.** Базовий робочий цикл L1, за яким інженер переводить задачу з беклогу у змерджений PR. Фази — `Intake (без AI) → Plan (AI + you) → Apply (AI + you) → Review (AI + you) → Commit (you)`. Gate-based: без затвердженого плану не починається Apply; без зеленого `/verify` не починається Review; без clean review не комітимо. Див. розділ 5.

**Task intake.** Перша фаза циклу, виконується **без AI**. Прочитати тікет, acceptance criteria, пов'язані PR-и; орієнтовно оцінити affected modules; перевірити залежності. Мета — переконатися, що задача зрозуміла достатньо, щоб її можна було передати AI. Див. розділ 5.

**Plan mode (built-in).** Вбудований режим primary-tool-а, у якому агент переходить у read-only, будує план імплементації і запитує approve перед тим, як торкнутися коду. У Cursor — окремий режим, у Claude Code — через `Shift+Tab` або `/plan`. Для 80% задач достатньо вбудованого режиму без кастомізації. Див. розділ 4, розділ 5.

**PLAN.md.** Файл у корені проєкту (або worktree), у якому зберігається затверджений план імплементації. Використовується як письмовий контракт між інженером і AI, на який посилаються через `@PLAN.md` у кожному Apply-промпті. Не комітиться у репозиторій — aux-файл циклу. Див. розділ 5.

**Gate / gate-based.** Контрольна точка між фазами циклу, що не дозволяє перейти далі без explicit approve або зеленого автоматичного перевіряльника. Приклади gate-ів: затверджений `PLAN.md` перед Apply; зелений `/verify` перед Review; чистий review перед commit. Див. розділ 5.

**Apply micro-cycle.** Внутрішній мікро-цикл фази Apply: `prompt → generate → review → correct`. Один крок плану — один промпт — один checkpoint, не batch. На кроці з 4+ ітераціями без сходження — вийти з Apply і повернутися у Plan. Див. розділ 5.

**Checkpoint.** Точка перевірки всередині Apply: після згенерованого diff інженер читає код рядок-за-рядком, запускає targeted `lint`/`type-check`/`test` і тільки потім переходить до наступного кроку. Без checkpoint-ів AI генерує в обсязі, який людина фізично не може ревʼювити.

**Self-verification.** Перший прогін ревʼю, що робить сам агент після Apply: re-read diff, перевірка cross-file consistency, запуск linter/type-check/tests. Ловить 40–60% помилок за умови явного формулювання "assume you've made mistakes". Без цього формулювання повертає "LGTM" — нікчемний результат. Див. розділ 5.

**Independent reviewer.** Другий прогін ревʼю іншою моделлю або subagent-ом із role "pessimistic senior engineer". Ловить те, що self-verification структурно не бачить: cross-file inconsistency, race conditions, silent failures, API contract mismatch з backend-ом. Див. розділ 5.

**Bug hunter.** Типова роль subagent-а або команди: переглядає змінені файли виключно на предмет bug-ів, logic errors, race conditions, silent failures; **не** коментує naming, style, архітектуру. Зазвичай на Opus, з короткою persistent memory про типові баги проєкту. Див. розділ 4.

**Clear context (практика).** Прийом роботи у довгих сесіях: після завершення 2–3 логічних кроків — `/clear` або новий chat; у новий завантажити через `@` тільки `PLAN.md` і релевантні файли. Коштує 30 секунд на старті — заощаджує години debug-у "чому AI раптом забув про правило X". Див. розділ 4, розділ 5.

**Worktree.** Git-фіча (`git worktree add`), що створює окрему директорію з окремою гілкою. Використовується у AI-workflow, щоб паралельно тримати кілька робочих гілок без `stash`/`checkout` і щоб agent-сесії не заважали одна одній. Інтегрується з `/plan`, що автоматично створює worktree за naming convention проєкту.

**Verify (`/verify`).** Стандартна slash-команда, що запускає `lint` + `type-check` + `test` і аналізує результат. Запускається перед кожним gate-переходом. Входить у базовий стартовий набір commands на будь-якому проєкті. Див. розділ 4, розділ 6.

**Review (`/review`).** Стандартна slash-команда, що прогоняє `git diff` через незалежну модель або subagent із role "critical reviewer". Запускається перед commit. Базовий набір commands. Див. розділ 4, розділ 6.

**Plan (`/plan`).** Кастомна slash-команда, що автоматизує планування з project-specific кроками: підтягнути тікет із Jira, створити worktree за naming convention, зберегти план у фіксований `PLAN.md`. Створюється **тільки** якщо вбудованого Plan mode не достатньо.

**PR-prep (`/pr-prep`).** Стандартна slash-команда, що формує commit message, створює PR, заповнює PR template на основі diff-у і тікета. Важлива деталь: AI тільки **готує** і показує результат; stage/commit/push робить людина. Див. розділ 6.

**Definition of done.** Набір критеріїв, за якими задача вважається виконаною: закриті acceptance criteria, зелений `/verify`, чистий review (0 Critical), оновлена документація (якщо проєкт цього вимагає), коректне commit/PR-оформлення. AI робить частину — human відповідає за gate.

**Pre-commit gate.** Набір перевірок перед першим `git add`: зелений `/verify`, чистий `/review`, `git status` не містить aux-файлів (`PLAN.md`, scratch), `.env*` у ignore-листі. Див. розділ 5.

## Промпти, команди, бібліотека

**Prompt library.** Сукупність заготовлених промптів, що зберігаються у проєктному репозиторії у вигляді commands, subagent-файлів і особистого `prompts.md`. Живе як інженерний артефакт: ревʼюїться у PR, еволюціонує разом із проєктом. Не каталог "крутих промптів з Twitter". Див. розділ 6.

**Inline prompt.** Разовий запит у поточний chat під унікальну задачу, що не повторюється. Не оформлюється у command/skill. Критерій: один раз за квартал → inline; щотижня → command; з деталями, що змінюються щоразу → skill.

**Prompt anatomy.** Структура стабільного промпту: `Intent → Inputs → Steps → Constraints → Output format → Fallback`. Відсутність будь-якої зі складових — типова причина nondeterministic-результату. Див. розділ 6.

**Intent (у промпті).** Перший рядок промпту, що фіксує, **що саме робить цей промпт і від чиєго імені**. Перемикає модель у потрібну mental model для всього виклику. Приклад сильного intent: "Stop and critically verify the work you've just completed. Assume you've made mistakes". Приклад слабкого: "Review the code".

**Constraints (у промпті).** Блок, що фіксує, **чого робити не можна**. Критично важливий — зупиняє модель від "допоміжних" дій: reformat unrelated imports, refactor "заодно", auto-commit без approve. Без constraints-блоку модель часто розширює scope за власною ініціативою.

**Parameterized prompt.** Промпт, у якому стабільна частина фіксована, а змінна — передається як параметр при виклику (`$ARGUMENTS`, `{{resource_name}}`, `$TICKET`). Дозволяє переиспользовати один і той самий command під різні інстанси задачі.

**XML-style prompt.** Формат промпту з XML-подібною розміткою (`<task>`, `<context>`, `<steps>`, `<constraints>`). Модель читає структуру стабільніше, ніж вільний текст. Виграє, коли команду викликають тією самою структурою, а варіативність — тільки у параметрах. Див. розділ 4.

**Fix the file, not the prompt.** Патерн роботи з систематичним порушенням правила: замість того, щоб переписувати промпт увосьме, — оновлюється skill/rule/entry-point із формулюванням "правильно / неправильно" і прикладом. Модель стабільніше виконує explicit-negative правила з альтернативою, ніж просту заборону. Див. розділ 4.

## Якість, безпека, відповідність

**Privacy mode / no-train settings.** Налаштування у cloud AI-tools, що вимикає використання коду для тренування моделей (Cursor Privacy Mode, ChatGPT data controls, Anthropic Workspace settings). Обов'язкове для роботи на клієнтському коді. Вимикається **разово** під час setup-у; інакше — порушення NDA. Див. розділ 2, розділ 3.

**No-train setting.** Синонім попереднього терміна у технічній документації провайдерів.

**Allow-list (permissions).** Явний список команд, які агент може виконувати без ручного approve (`Bash(pnpm run lint:*)`, `Bash(git diff:*)`). Правило: мінімально достатній. `git commit`/`git push`/`gh` — **ніколи** у whitelist без explicit flow. Див. розділ 7 (§7.3.2).

**Deny-list (permissions).** Явний список заборонених команд (`rm -rf`, `drop`, `truncate`, `force push`, `npm publish`). Завжди активний незалежно від allow-list-у. Лінія захисту від випадкового виконання деструктивних дій.

**Auto-accept / YOLO mode.** Режим, у якому агент сам редагує файли і виконує команди без підтвердження (Cursor `auto-accept`, Claude Code `--dangerously-skip-permissions`). Дозволений **тільки** на read-only операції і tightly-scoped експерименти у worktree. Для будь-якої роботи, що потрапляє у PR, — manual approve. Див. розділ 7 (§7.3.1). **Сленг.**

**Credentials isolation.** Правило: AI agent не має доступу до production credentials, API keys, secrets. Реалізація: `.env*` у ignore-листі tool-а, `.gitignore`, secret manager, окремі змінні середовища. Див. розділ 2.

**Sensitive zone / sensitive data zone.** Директорія або тип коду, де AI заборонено або дозволено лише local-моделям: credentials, client PII, код під жорстким NDA, business-critical бізнес-логіка. Документується у `AGENTS.md` і у `.cursorignore`/`.aiignore`. Див. розділ 2, розділ 3.

**Data residency.** Вимога, щоб дані (включно з кодом) не залишали певну географічну або інфраструктурну зону. Типовий наслідок: заборона на cloud AI із серверами за межами зони; робота через local-моделі.

**Audit trail.** Збережена історія AI-сесій (логи, transcripts) для post-review у разі incident. Обов'язкова на compliance-проєктах (HIPAA, SOC 2, ISO 27001), опційна на інших.

**Approved tool list.** Список AI-інструментів, які клієнт дозволяє використовувати на своєму коді. Пріоритет над особистими вподобаннями інженера — "approved list закриває дискусію". Інші tools — для offline research поза робочим часом. Див. розділ 2.

**Package verification.** Обов'язкова перевірка кожної AI-recommended dependency перед додаванням: реальна сторінка npm/PyPI, зірки/downloads, дата останнього релізу, CVE-перевірка. Захист від slopsquatting і typosquatting.

**Slopsquatting.** Публікація шкідливих пакетів із назвами, які LLM-моделі часто **hallucinate-ють** (наприклад, пакет з правдоподібним іменем, якого ніколи не існувало). AI рекомендує → інженер встановлює → виконується зловмисний код. Захист — package verification перед будь-яким `install`.

**Typosquatting.** Класична атака: публікація пакета з ім'ям, схожим на популярний (`react-redex` замість `react-redux`). AI іноді підхоплює неправильне ім'я з tutorial-у. Захист — той самий: package verification.

## Антипатерни і ризикові практики

**Vibe coding.** Apply без Plan: інженер одразу пише промпт "реалізуй feature X"; AI генерує; після третьої ітерації вже неможливо згадати original intent. Категорично не L1-практика. Фікс — жодного Apply без затвердженого `PLAN.md`. Див. розділ 7. **Сленг.**

**LGTM review (anti-pattern).** Ревʼю як формальність: diff довгий, час обмежений, тест зелений → accept без reference на checklist. AI-згенерований код небезпечний тим, що **виглядає правильно**; саме на ньому LGTM-ревʼю дає тихий борг у прод. Фікс — timeboxed ревʼю (15–30 хв) з фіксованим checklist-ом. Див. розділ 7.

**Mega-PR.** Один PR на цілу епіку, згенерований AI за годину. Ревʼювабельний тільки формально — інженер фізично не може прочитати 2000 рядків diff уважно. Фікс: один Plan → один PR → один scope. Епіка = послідовність PR-ів, кожен окремо прохідний.

**Happy-path-heavy tests.** Тести, написані AI за замовчуванням, що покривають тільки успішні сценарії; null, empty, unauthorized, network failure, race condition пропущені. Фікс — після генерації explicit-промпт "now add negative tests: ...", і переглянути, що тести реально щось падають на зміні source-коду.

**Scope creep (в Apply).** Безконтрольне розширення scope усередині фази Apply: "заодно я полагодив імпорти у 20 сусідніх файлах". Diff стає нерев'юабельним. Фікс: scope зафіксовано у плані; усе "заодно" — окремий PR після merge основного.

**Одна модель на всі задачі.** Opus для README, Haiku для архітектури у модулі з 50 файлами. Наслідок — або token overage, або погана якість на critical-path. Фікс — model routing із розділу 2. Див. розділ 7 (§7.3.4).

**Один інструмент на всі задачі.** IDE-agent на long refactor 2000 рядків (який природньо живе у CLI); CLI-agent на швидкий CSS-твік. Інерція "усе в IDE — зручно" призводить до годин боротьби з інструментом. Фікс — decision tree з розділу 2. Див. розділ 7 (§7.3.3).

## Типи помилок у коді (review lenses)

Терміни, що зустрічаються у фіксованому checklist-і ревʼю (розділ 5).

**Off-by-one error.** Класична помилка: цикл починається з 1 замість 0, `<=` замість `<`, індекс масиву виходить за межі. AI стабільно робить на нетривіальних boundary-умовах; лінза ревʼю.

**Silent failure.** Помилка проковтується без логування або alert-у: `catch` без handle, swallowed promise rejection, `try/except: pass`. У runtime поведінка неправильна, логів немає, bug дебажиться годинами. Лінза ревʼю.

**Race condition.** Помилка паралельного виконання: subscription leak, stale closure, перегони за shared-state. AI не бачить runtime-timing; лінза ревʼю. Типові маркери: відсутній `takeUntilDestroyed`, `AbortController`, `useEffect` cleanup.

**Stale closure.** React/signal-specific різновид race condition: функція захоплює старе значення state, потім викликається з уже неактуальним контекстом. Типова AI-помилка при роботі із signals і hooks.

**Cross-file inconsistency.** Зміна у одному файлі (interface, enum, API endpoint) без оновлення consumers. Найчастіший AI-bug на multi-file задачах — модель "забуває" про віддалених consumers. Окрема лінза ревʼю і окремий step у `/verify`-промпті.

**API contract mismatch.** Frontend-сервіс очікує одну форму response, backend повертає іншу. Після AI-рефакторингу одного боку — частий випадок. Перевіряється у cross-file consistency lens.

## Метрики і вимірювання

**Plan-to-merge time.** Час від затвердження плану до merged PR. Healthy-діапазон для типової фічі середнього розміру — < 1 день. Індикатор того, наскільки цикл Plan → Apply → Review збалансований. Див. розділ 5.

**Apply iterations per step.** Скільки промптів потрібно, щоб пройти один крок плану. Healthy — 1–3 ітерації; 4+ — крок був нерозмірно великий або план хибний, треба різати дрібніше.

**Critical issues per PR.** Кількість Critical-знаходжень на фазі Review після AI-генерації на один PR. Healthy — 0–2; 3+ — сигнал про слабкий Plan або недостатній контекст.

**Failing CI rate.** Частка PR-ів, де CI знайшов помилку, яку мав відловити локальний `/verify`. Healthy — < 10%; більше — hooks не покривають того, що робить CI.

**Rework rate.** Частка merged PR-ів, у яких після merge знайшли bug, що вимагав hotfix. Healthy — < 5%; більше — ревʼю поверхневий або self-verification не запускається.

**AI-generated share.** Частка рядків AI-генерованого коду у merged PR. Baseline з інтервʼю: 80–90% у зрілих інженерів (10–20% — ручні правки). Міра зрілості L1.

**Speed gain (×-коефіцієнт).** Виграш швидкості від AI: мінімальний ×1.5–×2 на enterprise-legacy, до ×10 на документації, до ×100 на незнайомому стеку, де інженер знає концепти, але не синтаксис. Міряється особисто, порівнюючи схожі задачі до/після адаптації. Див. розділ 1.

**AI-euphoria warning signs.** Сигнали, що команда переоцінює ефект: перенесення метрик із MVP/personal-проєкту на enterprise; оцінка короткотермінового спринту без long-term; "я не розумію, як це працює, але воно працює". Див. розділ 1.

## Загальні технічні скорочення

**SDLC (Software Development Life Cycle).** Цикл розробки: planning → design → implementation → testing → deployment → maintenance. У контексті Level 3 — "AI-first SDLC" означає автоматизацію частин циклу агентськими системами.

**ADR (Architecture Decision Record).** Документ, що фіксує архітектурне рішення і його обґрунтування. У Level 2 (spec-driven) ADR генерується AI і ревʼюється до коду.

**AC (Acceptance Criteria).** Критерії приймання задачі — конкретний список умов, за якими задача вважається закритою. Частина тікета, вихідний матеріал для Plan-фази.

**CI/CD (Continuous Integration / Continuous Delivery).** Автоматизований pipeline збірки, тестування, деплою. У AI-workflow має повторювати ті самі перевірки, що локальний `/verify`, — інакше локальний "зелений" розходиться з CI.

**PR (pull request) / MR (merge request).** Запит на злиття гілки з основною гілкою репозиторію. На L1 — обов'язковий artifact delivery-фази; AI-згенерований PR ревʼюється людиною незалежно від кількості моделей, що над ним працювали.

**LTS (Long-Term Support).** Версія runtime або library з довгим циклом підтримки. Node.js LTS (≥ 20.x) — вимога для Claude Code CLI та більшості MCP-серверів.

**VDI (Virtual Desktop Infrastructure).** Див. розділ "Інструменти, середовище, моделі".

**NDA (Non-Disclosure Agreement).** Юридичне зобов'язання не передавати код/дані клієнта третім особам. Часто перетинається з AI-політикою: без dedicated no-train settings або local-моделі робота на NDA-коді у cloud AI — порушення.
