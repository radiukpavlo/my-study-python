# 7. Anti-pattern Catalog

**Статус:** Draft
**Дата:** 21 квітня 2026

Цей розділ — довідковий каталог того, **що не працює** у AI-augmented розробці, і що робити замість цього. На відміну від попередніх розділів, тут не викладається позитивна методологія — тут перелічуються конкретні паттерни, які інженери і ширша спільнота вже спостерігали у проді, і які коштували grey hair, rollback-ів або клієнтського тріалу.

Базова теза розділу: **більшість провалів із AI — це не "AI зламався", а "людина використала його неправильно".** Ті самі інструменти, що одним інженерам дають 2–3x прискорення, іншим дають 3x кількості bug-ів у продакшні. Різниця — не у tool-і і не у моделі; різниця у процесі, промпті і рівні довіри до output-у.

Каталог не вимагає послідовного читання. Його можна відкривати у момент, коли робота зламалася: "нічого не працює вже годину → подивись в Workflow anti-patterns"; "згенероване виглядає дивно → подивись в Prompt anti-patterns". Кожен запис має **сигнали** — спостережувані симптоми, за якими інженер упізнає антипаттерн у себе, — і **фікс** — мінімальну дію, щоб вийти з нього.

## 7.1. Що читач має винести з цього розділу

Після прочитання інженер повинен:

- упізнавати типові антипаттерни у себе за спостережуваними сигналами, а не за інтуїтивним "щось не так";
- знати, чому антипаттерн виникає — часто це не лінь, а закономірний результат попередньої фази циклу;
- мати готовий фікс для кожного випадку і розуміти, у якому розділі плейбуку покрита "здорова" альтернатива;
- відрізняти антипаттерн від тактичної помилки — тактичну виправляємо один раз, антипаттерн треба виривати з кореня (промпт/skill/процес);
- розуміти, які антипаттерни коштують годин, а які — репутації або клієнтського контракту; пріоритизувати виправлення за вартістю провалу.

## 7.2. Як читати каталог

Структура кожного запису:

- **Назва** — коротка, впізнавана.
- **Опис** — 1–2 речення: у чому саме паттерн.
- **Чому виникає** — типова причина, не "тому що інженер поганий".
- **Сигнали** — спостережувані ознаки у коді / чаті / PR / CI.
- **Наслідки** — що ламається і коли це проявляється.
- **Фікс** — мінімальна дія для виходу; посилання на розділ, де описана здорова альтернатива.

Каталог згруповано за чотирма напрямами:

1. **Tool misuse** (§7.3) — неправильний вибір чи конфігурація AI-інструменту.
2. **Prompt anti-patterns** (§7.4) — формулювання, що дають нестабільні або хибні результати.
3. **Workflow anti-patterns** (§7.5) — поломки на рівні циклу Plan → Apply → Review і його оточення.
4. **Architecture & security risks** (§7.6) — паттерни, що створюють архітектурний або безпековий борг.

Всередині кожної групи порядок — від найчастіших/найдешевших до виправлення, до рідкісних/найдорожчих.

> 💡 **Hint:** Якщо ти натрапив на антипаттерн, якого немає у каталозі, — це кандидат на додавання. Формулюй за тим самим шаблоном (назва → сигнали → фікс) і додавай через PR. Локальне відкриття "ой, у мене теж так було" без фіксації у каталозі означає, що наступний інженер витратить ті самі години на ту саму помилку.

## 7.3. Tool misuse

Антипаттерни цієї групи виникають, коли інструмент обрано неправильно або сконфігуровано надто агресивно. Здебільшого — наслідок того, що інженер застосовує tool-set "як у відео/статті", без перевірки, чи відповідає він задачі і політиці проєкту.

### 7.3.1. Auto-accept / YOLO-mode за замовчуванням

Інженер вмикає режим, у якому агент сам редагує файли і виконує команди без підтвердження (Cursor `auto-accept`, Claude Code `--dangerously-skip-permissions`, Copilot Agent auto-apply). Мотивація — "швидше".

**Чому виникає:** ручний approve кожного tool-call здається "гальмом"; модель робить правильні дії у 90% випадків, тож інженер припиняє дивитися на diff.

**Сигнали:**

- У git-log-у зʼявляються файли, яких інженер не планував чіпати.
- Після сесії не можеш відповісти "що саме зроблено" без `git diff`.
- Тести проходять, але поведінка у runtime не та, що очікувалася.

**Наслідки:** невидимі зміни у файлах, до яких не дійшло review; тихий scope creep; у найгіршому випадку — виконані деструктивні команди (`rm`, `git reset --hard`, `drop database`).

**Фікс:** auto-accept дозволений **тільки** на read-only операції і на tightly-scoped edits у дійсно експериментальних worktrees. Для будь-якої роботи, що потрапляє у PR, — manual approve на кожному edit / bash. Дивись розділ 3 (Tool Setup) — блок про дозволи і hooks.

### 7.3.2. Надто широкі permissions / allow-list

У конфізі агента `bash` з full shell access, `git commit`, `git push`, `rm -rf`, `npm publish` у whitelist-і. Агент використовує ці інструменти "за потреби".

**Чому виникає:** при першому setup-і інженер додає все, що може знадобитися, щоб "не переривати flow". Потім забуває вузити список.

**Сигнали:**

- Агент сам робить commit без явного запиту.
- У chat-історії зʼявляються `git push` / `gh pr create`, яких ти не просив.
- Локально виникли зміни у файлах, які агент мав тільки читати.

**Наслідки:** агент комітить PLAN.md-шки, scratch-файли, `.env.local`. Безповоротний `git reset --hard` у не-тій гілці. Виконаний `npm publish` із версією, яка не мала публікуватися.

**Фікс:** allow-list — мінімально достатній. `git commit`/`git push`/`gh` — **ніколи** у whitelist без explicit flow (типу `/commit-msg` із `WAIT for approval`). Деструктивні команди (`rm -rf`, `drop`, `truncate`, `force push`) завжди у deny-list. Перегляд permissions — раз на місяць і щоразу при зміні tool-а.

### 7.3.3. Один інструмент для всього

Інженер обрав primary tool (наприклад, Cursor) і намагається робити у ньому 100% задач: long refactor на 2000 рядків, який природньо живе у CLI-агенті; quick edit на 3 рядки, який швидше зробити вручну; agentic research, який краще виконує subagent з ізольованим контекстом.

**Чому виникає:** інерція ("усе в IDE — зручно"); небажання тримати у голові дві ментальні моделі (IDE + CLI + web-chat).

**Сигнали:**

- На refactor-і у 20 файлах IDE висне або upload-ить увесь проєкт у контекст.
- Код на 5 рядків зайняв 15 хвилин через "а давай агент".
- На research-задачах ("знайти, де використовується цей API у монорепо") IDE дає неповний результат.

**Наслідки:** години, витрачені на боротьбу з інструментом; context bloat; постійні token-overage.

**Фікс:** decision tree з розділу 2 (Tool Selection). IDE-agent для задач у scope 1–5 файлів із видимим review. CLI-agent для long refactor-ів, mass-edit-ів, agentic research. Ручна редакція для трьохрядкового фіксу. Web-chat для brainstorm / planning без коду.

### 7.3.4. Вибір моделі "за замовчуванням"

Один і той самий model-slug (Sonnet 4 / Opus 4 / GPT-5) на всі задачі, незалежно від складності. Opus для того, щоб згенерувати `README.md`; Haiku для архітектурного рішення у модулі з 50 файлами.

**Чому виникає:** інженер один раз налаштував default-модель і забув; вибір моделі сприймається як "конфіг", а не як параметр задачі.

**Сигнали:**

- Token-bill у кінці місяця непропорційний кількості задач.
- На "простих" задачах результат занадто довгий і overengineered.
- На складних задачах модель здається на другій ітерації і починає hallucinate.

**Наслідки:** 3–5x overspend на простих задачах; недотягування якості на складних (де треба було reasoning-heavy модель).

**Фікс:** розділ 2 — таблиця відповідності задача → модель. Reasoning-heavy / Opus-tier → architecture, complex refactor, план під епіку, security review. Balanced / Sonnet-tier → щоденний Plan → Apply → Review. Fast / Haiku-tier → lint-fix, typo, typing, документація short-form.

### 7.3.5. Переповнений entry-point

`AGENTS.md` / `CLAUDE.md` на 500–800 рядків, у якому змішано весь ридмі-матеріал: історія проєкту, ADR-и, coding conventions, links на Confluence, examples для 10 фреймворків.

**Чому виникає:** інженер "на всяк випадок" тягне у entry-point усе, що колись знадобилося; ніхто не чистить.

**Сигнали:**

- Контекст заповнений на 30% ще до початку задачі.
- Модель ігнорує частину правил (типово — ті, що посередині файлу).
- Якість відповідей на задачах у одному модулі гірша, ніж на задачах у іншому, хоча складність співставна.

**Наслідки:** контекст-платіж на кожному turn-і; інструкції-середини файлу не виконуються; модель плутає Angular-правила з React-правилами у монорепо.

**Фікс:** розділ 4 (Context Engineering) — ієрархія `AGENTS.md`, skills on-demand, rules тільки always-needed. Корневий entry-point ≤ 150 рядків. Все інше — у skills або у nested `AGENTS.md`.

### 7.3.6. Cargo-culting CLI-патернів у IDE (і навпаки)

Інженер прочитав у чиємусь thread про Ralph Loop (bash-цикл, що переукладає prompt у свіжу CLI-сесію) і намагається відтворити його у Cursor; або намагається робити interactive plan-mode у headless CLI, де він не призначений.

**Чому виникає:** практика описана без контексту tool-а; інженер копіює технічний паттерн без перевірки підтримки.

**Сигнали:**

- Декілька днів налаштування нестандартного workflow, який "у них працює, а у мене ні".
- Пошук у GitHub Issues: `"feature X" does not work in <tool>`.
- Самописні bash-wrapper-и навколо tool-а, що дублюють його вбудовану функціональність з помилками.

**Наслідки:** витрачені години на воркераунди; нестабільний workflow, який не переноситься між машинами; помилки у репрезентативних кейсах (свій Ralph Loop пропускає session-boundary і контекст не чиститься).

**Фікс:** перевіряти підтримку через офіційні доки і release-notes tool-а на момент читання статті. Статті старші 6 місяців — readonly reference; поведінка tool-ів змінюється швидко. Ralph Loop / nested subagents — CLI-оріентовані практики; у IDE використовуй рівноцінні нативні механізми (`/clear`, session reset, plan-mode). Розділ 2 і 3 — узгодження tool → workflow.

### 7.3.7. Bot-reviewer як ground truth

Cursor Bug Bot, Copilot Review, GitHub Code Scanning повідомляє про проблему — інженер (або автор PR) автоматично виправляє без перевірки, чи коментар правдивий.

**Чому виникає:** bot-повідомлення форматоване як авторитетне; блокує merge; виправити "швидше", ніж сперечатися.

**Сигнали:**

- PR-и ростуть на коміти типу `fix: address bot comment` без зрозумілого опису.
- Після виправлення bot-зауваги виникає нова regression (бо "виправлення" зламало робочий код).
- Ти не можеш пояснити, чому зміна потрібна — крім "бот сказав".

**Наслідки:** regression від фіксу "проблеми", якої не було. PR ростуть і стають нерев'юабельними. Довіра до bot-review падає, і справжні проблеми ігноруються разом з false-positives.

**Фікс:** у розділі 5 (Review) описано assessment-крок "is this comment actually correct?" до будь-якого фіксу від bot-а. False-positive rate AI-review-bot-ів — 20–40% (див. chapter 5, типові метрики). Категоризуй коментарі (Valid / Partial / Invalid), accept-уй тільки Valid / Partial. Для Invalid — reply з обґрунтуванням.

### 7.3.8. Multi-agent "virtual team" без governance

Інженер налаштовує 5–7 subagent-ів (BA, Architect, Backend, Frontend, QA, DevOps, Reviewer), оркестратор їх викликає паралельно, результати зливаються. Ідея виглядає "масштабовано".

**Чому виникає:** ідея привʼязана до гучних demo і блогпостів; outshine-ефект ("моя AI-команда"); невірне переконання, що multi-agent = краща якість.

**Сигнали:**

- Token-spend росте у 5–10 разів, якість не змінюється (або падає).
- Subagent-и дають суперечливі відповіді; оркестратор не знає, який обрати.
- Час від промпту до результату виріс у 3–5 разів.
- Нікому не зрозуміло, чиє рішення опинилося у коді.

**Наслідки:** token-cost без eqv-приросту якості; неможливо трасувати, чому згенеровано саме цей код; розмита відповідальність.

**Фікс:** на L1 і L2 (див. розділ 1, рівні зрілості) достатньо 1 primary agent + 1 independent reviewer (інша модель або subagent). Multi-agent team — advanced-tier, потребує process governance, який у плейбуку ще не описаний. Не починай з 7 ролей — починай з одного агента і одного reviewer-а. Розділ 4 — коли subagent виправдано.

### 7.3.9. Figma MCP / design-to-code як чорна коробка

Інженер підключив Figma MCP і очікує, що "з дизайну автоматично згенеровано pixel-perfect UI". Перші 2–3 прогони дають прийнятний результат, потім — щоразу потрібно правити кольори, spacing, component structure.

**Чому виникає:** маркетингове обіцяння "design to code"; інженер пропускає етап створення design-system skill-а.

**Сигнали:**

- Кожен PR з UI-змінами містить ручні правки tailwind/css, що повторюються.
- Згенеровані компоненти не вписуються у проєктну component library.
- Колір-палітра у PR дрейфує від design-token-ів.

**Наслідки:** UI-drift, зайвий рефакторинг на етапі Review, втрата довіри до MCP-інструменту.

**Фікс:** Figma MCP — джерело даних, а не автоматизація. Після витягання дизайну запускається skill `write-component`, у якому описані конвенції компонентної бібліотеки, мапа design token-ів, правила наслідування variant-ів. Візуальне QA — завжди людське. MCP не замінює design-system skill.

### 7.3.10. Running local LLMs там, де це не потрібно

Інженер піднімає LM Studio / Ollama з 70B-моделлю на робочому ноуті "для швидкості і приватності".

**Чому виникає:** мотивація безпеки ("даних не віддаємо у cloud"); хайп навколо open-source моделей.

**Сигнали:**

- IDE тормозить під час AI-запитів.
- Batterylife падає з 6 годин до 1.5.
- Якість відповіді помітно нижча за cloud-модель на тому ж промпті.

**Наслідки:** повільний iteration-цикл; якість відповідей нижча; ресурси машини йдуть на LLM, а не на білд і тести.

**Фікс:** local LLM — тільки там, де є реальна вимога (сенситивні дані, клієнтська політика, air-gapped-оточення). Для щоденної роботи — cloud-моделі через enterprise-endpoint (див. розділ 2 і 3). Якщо приватність — вимога, обговори з клієнтом approved-tooling, не воркераундь у одиночку.

## 7.4. Prompt anti-patterns

Антипаттерни цієї групи виникають на рівні формулювання промпту. Вони коштують дешево (одна іtерація), але повторюються щодня і формують sloppy-muscle-memory. Виправити окремий промпт — питання 5 хвилин; виправити звичку — тижнів.

### 7.4.1. Vague intent ("зроби красиво" / "покращ")

Промпт не має конкретної цілі: `Review the code`, `Refactor this`, `Make it better`, `Зроби мені красиво`. Модель сама вирішує, що "краще".

**Чому виникає:** інженер очікує, що модель "розбереться за контекстом"; лінь формулювати.

**Сигнали:**

- Кожен прогін дає інший результат навіть на незмінному коді.
- Відповідь містить advice замість конкретних змін ("ось 10 речей, які ви могли б покращити").
- Ти вже тричі переформулюєш "ні, я мав на увазі інше".

**Наслідки:** модель обирає довільну інтерпретацію; велика частина "fixes" не потрібна або шкідлива; іtерації марні.

**Фікс:** кожен промпт починається з **Intent** — одне речення: "що саме зробити і з якої позиції" (див. розділ 6, анатомія промпту). `Review` → `Stop and critically verify the work you've just completed. Assume you've made mistakes — your job is to find them.` `Refactor` → `Extract duplicated validation logic from X and Y into shared module, preserving exact behavior.`

### 7.4.2. Відсутність output format

Промпт описує, **що** зробити, але не описує, **у якому вигляді повернути**.

**Чому виникає:** автор пише промпт "для себе" — він знає очікуваний формат, припускає, що і модель знає.

**Сигнали:**

- Кожен запуск видає різну форму (markdown-table / bullet-list / prose).
- Команда не може автоматизувати парсинг виводу.
- На одному запиті — довгий essay, на наступному — три bullet-а.

**Наслідки:** неможливо використати промпт у скриптах або як частину pipeline-у; ручна обробка виводу після кожного запуску.

**Фікс:** блок **Output format** обовʼязковий у кожному repeatable-промпті (див. розділ 6). Форма — або markdown-table з фіксованими колонками, або JSON/XML, або "ready-to-paste reply". Приклад формату — у тілі промпту, не "format as needed".

### 7.4.3. Відсутність constraints / Do NOT

Промпт каже, що зробити, не каже, чого **не** робити. `Refactor service X` без `do not change the public API`.

**Чому виникає:** інженер очікує, що модель "здогадається" про обмеження; constraints здаються formальністю.

**Сигнали:**

- Diff торкається файлів поза scope-ом (reformat неспоріднених imports, перейменовування змінних у сусідніх модулях).
- Public API змінено, сіпавши callers.
- "Заодно" модель виправила багів, які ти не просив, і половина з них зламала інший функціонал.

**Наслідки:** scope growth у рамках одного PR; зламані callers; незворотні "optimization"-рефактори.

**Фікс:** блок **Constraints** у кожному implementation-промпті — мінімум один `Do NOT`. Типові: `Do NOT touch files outside the scope listed above`, `Do NOT start implementing — wait for plan approval`, `Do NOT change the public API of X`, `Do NOT reformat unrelated imports`. Приклади у розділі 6.

### 7.4.4. Mega-prompt на все

Один промпт на 300–500 рядків, у якому перемішано: plan, spec, implementation, test, review, commit-message, PR-description.

**Чому виникає:** інженер шукає "universal command" — one shot, one answer. Натхнення зі статей "AI agent robot that does everything".

**Сигнали:**

- Промпт не вміщується на екран; важко згадати, що в ньому.
- Модель виконує перші 2 кроки, пропускає наступні 5.
- Результат — змішаний: щось зроблено, щось тільки описано у прозі.

**Наслідки:** контекст забивається інструкціями, на код лишається мало токенів; модель втрачає scope у першому ж довгому turn-і; unpredictable partial-completion.

**Фікс:** один промпт — одна фаза циклу. `/plan` не робить apply; `/apply` не робить review; `/review` не комітить. Розділ 6 — starter-set з чотирьох фокусних команд замість одного mega-prompt-у.

### 7.4.5. Один chat на цілий день

Інженер починає ранок з `claude` / нової сесії і не закриває її до вечора. За день — десятки різнорідних задач у тому самому chat-і.

**Чому виникає:** `/clear` здається "втратою прогресу"; інерція.

**Сигнали:**

- На задачі C модель ще памʼятає обмеження із задачі A (часом корисно, частіше — ні).
- Відповіді все довші й менш релевантні; модель "ходить кругами".
- На третій годині сесії вона плутає файли або поведінку.

**Наслідки:** context rot (див. розділ 4); token-overspend; modely "забувають" щойно озвучене правило, бо воно загубилося на 10 turn-ів нижче.

**Фікс:** новий chat на кожну нетривіальну задачу; явний `/clear` між фазами (Plan → Apply → Review — різні сесії або clear-и). Стан зберігай у файлах (`PLAN.md`, `CHANGELOG.md`), не у chat-історії. Розділ 4 — TTL контексту.

### 7.4.6. Копія промпту з Twitter / блога без адаптації

Інженер копіює "найкращий промпт для code review" з зовнішньої статті, запускає на своєму проєкті, отримує нерелевантний результат.

**Чому виникає:** віра у generalized best-prompt; незнання, що промпт — artifact, привʼязаний до стеку.

**Сигнали:**

- Промпт посилається на фреймворки, яких у вас немає.
- Приклади у промпті — на іншій мові (JS у промпті для Python-проєкту).
- Рекомендації на кшталт "run `jest`" на проєкті, де `vitest`.

**Наслідки:** модель або генерує нерелевантний результат, або hallucinate missing files / tools.

**Фікс:** промпт-з-інтернету — стартова точка, не робоча версія. Адаптуй: стек, naming, build-команди, project conventions, приклади з вашого коду. Версіонуй у `.claude/commands/` свого репозиторію. Розділ 6 — еволюція бібліотеки.

### 7.4.7. "You are a senior X…" persona spam

Перший рядок кожного промпту: `You are a senior principal engineer with 15 years of experience in <stack>, acting as a code reviewer for a fintech startup in Europe.`

**Чому виникає:** ранні (2023–2024) матеріали з prompt engineering радили persona-prompting; моделі того часу реально виграли від ролі. Модерні (2026) — значно слабше.

**Сигнали:**

- Persona — довша за саму задачу.
- Відповіді стилістично претензійні ("як senior я би порадив…"), але по суті такі ж, як без persona.
- На специфічних задачах persona не впливає на результат ні в який бік.

**Наслідки:** токени вперше 50 рядків промпту йдуть на стилізацію, а не на задачу; стиль відповіді не відповідає команді (модель пише "як тренер", коли треба pragmatic-reply).

**Фікс:** persona — тільки там, де вона змінює mental model (critical reviewer, adversarial bug-hunter). Для більшості задач — одне речення intent з дієсловом. Розділ 6 — анатомія промпту.

### 7.4.8. Відсутність "admit uncertainty" правила

У глобальних rules або у промпті немає інструкції "якщо не впевнений — скажи так". Модель каже `Fixed!`, `This should work now`, `Issue resolved`, навіть коли не виправила нічого.

**Чому виникає:** модель за замовчуванням confident; правило "admit uncertainty" пропущене при setup-і entry-point.

**Сигнали:**

- Тричі поспіль `Fixed!` без реальних змін або зі змінами, що нічого не ламають і нічого не чинять.
- Тести проходять, поведінка не змінюється.
- Запит "show me the diff" видає diff з пробілів або no-op.

**Наслідки:** години на "imaginary fixes"; інженер вірить, що задача закрита, баг повертається через тиждень.

**Фікс:** global rule у `AGENTS.md` / `CLAUDE.md`: `If you are not certain a change is correct, say so. Do not claim a fix without showing evidence (diff, test output, or explicit verification step).` У верифікаційних промптах — вимагати evidence (diff, test output). Розділ 4 — rules always-on.

### 7.4.9. Нема дати / версії залежностей

Промпт ставить питання про API / бібліотеку, не вказуючи версію. Модель відповідає за тим API, яке памʼятає з training data.

**Чому виникає:** інженер припускає, що модель використає "найновішу версію"; або припускає, що проєктна версія і є "найновіша".

**Сигнали:**

- Модель посилається на методи, яких немає у твоєму `package.json` / `pom.xml`.
- Приклади у відповіді використовують застарілі імпорти ("deprecated in v5").
- CI падає на import-і, який модель припустила доступним.

**Наслідки:** години на виправлення API-хибності, яка була зʼїла за замовчуванням.

**Фікс:** у промптах на бібліотеку — явна версія і дата: `Using <lib> v3.2 (as of Jan 2026). Check the current API on the official docs if uncertain.` У entry-point-і — коротка таблиця "ключові бібліотеки і їхні версії". Web-search / docs-skill для актуальної інформації.

### 7.4.10. ASCII-art замість компактного діаграм-формату

Промпт просить модель намалювати ASCII-схему архітектури: `┌──────┐ ┌──────┐`. На 20 компонентів виходить артефакт на 80 рядків, який модель важко parse-ить.

**Чому виникає:** звичка з до-AI часів; ASCII-art виглядає "кодерно".

**Сигнали:**

- Частина box-ів малюється криво, лінії розʼїдаються.
- При доопрацюванні схеми модель "ламає" вже намальовані box-и.
- Контекст забивається ASCII-символами, що не несуть семантики.

**Наслідки:** багато токенів на візуальну форму, мало — на зміст; подальші turn-и плутаються у структурі схеми.

**Фікс:** Mermaid / PlantUML — компактні структуровані формати, які моделі читають і генерують стабільніше. `graph TD; A[User] --> B[API]; B --> C[DB]` замість 20 рядків ASCII. Розділ 6 — output format.

## 7.5. Workflow anti-patterns

Антипаттерни цієї групи виникають на рівні циклу Plan → Apply → Review (див. розділ 5) і його оточення. Часто це не провал однієї фази, а пропуск гейту між фазами — і наступна фаза компенсує проблему додатковою роботою замість того, щоб повернутися у попередню.

### 7.5.1. Vibe coding (Apply без Plan)

Інженер одразу пише у промпт "реалізуй feature X", отримує код, дивиться, коригує, повторює.

**Чому виникає:** задача здається "простою", plan здається "overhead"; спокусливо економити 15 хвилин.

**Сигнали:**

- Після третього promp-ту ти вже не памʼятаєш original intent.
- У diff зʼявляються файли, про які не йшлося.
- Архітектурне рішення (напр. "нова таблиця чи колонка у існуючій") приймається моделлю тихо.

**Наслідки:** нерев'юабельний PR; tech-debt на архітектурному рівні; 2x часу на те саме, бо повертаєшся до Plan після години apply.

**Фікс:** жодного Apply без затвердженого `PLAN.md`. Plan дешевий (хвилини), код — дорогий (години). Розділ 5 — фаза 2 (Planning). Мінімальний план — 5 рядків у `PLAN.md`: файли, порядок, тести, ризики.

### 7.5.2. Review як формальність

Diff довгий, часу немає, тести зелені → `Approve`. Часто — AI-згенерований PR, прочитаний "по діагоналі".

**Чому виникає:** бажання не блокувати колегу; "тести зелені" сприймається як достатній сигнал; AI-код виглядає правильно (це його найкориснішa і одночасно найнебезпечніша риса).

**Сигнали:**

- Review-коментарі тільки стилістичні, жодного архітектурного.
- LGTM без пояснення.
- Час на review — менше 5 хвилин на 300-рядковий PR.

**Наслідки:** regression у проді через тиждень; silent tech-debt; AI-код закладає помилки, які виявляються, коли автор уже переключився на іншу задачу.

**Фікс:** review timeboxed (15–30 хв на PR) із фіксованим checklist-ом. Жодного `LGTM` без reference на checklist. `/verify` + independent-reviewer (інша модель) до людського review. Розділ 5 — фаза 4. AI-згенерований код — особливий ризик: **виглядає правильно, але може не бути**. Не довіряй на око.

### 7.5.3. Тестування в одному turn-і з реалізацією

Модель у одному промпті генерує і implementation, і test. Тест "перевіряє" саме те, що код випадково робить (включно з bugs).

**Чому виникає:** економія turn-ів; інтуїтивне "код і тести поруч".

**Сигнали:**

- Тести зелені з першого разу на нетривіальній фічі.
- Assertion-и перевіряють `toHaveBeenCalled` замість поведінки.
- При зміні source-файлу — тест падає, хоча семантика не змінилася.

**Наслідки:** false safety; тести не виявляють регресії; при першій зміні коду — тести доводиться переписувати.

**Фікс:** роздільні turn-и — спочатку код, потім тест. Або ще краще — тести пише інша сесія / модель, яка бачить тільки спеку, не реалізацію. Промпт для тесту — "test behavior, not call sequences" (розділ 6, `/test-unit`).

### 7.5.4. Контекст не очищається між фазами

Plan закінчився, Apply починається у тому самому chat-і без `/clear`; Review — знову там же.

**Чому виникає:** `/clear` сприймається як втрата прогресу; `PLAN.md` і `CHANGELOG.md` не ведуться, тому "історія у chat-і — єдина памʼять".

**Сигнали:**

- Модель на етапі Review пропонує "swap approach X to Y" — те, що вже обговорили і відкинули у Plan.
- Відповіді все довші; частина з них повторюється.
- Контекст на 70%+, ще до важливого turn-у.

**Наслідки:** context rot; суперечливі рекомендації між фазами; регресія вже обговорених рішень.

**Фікс:** `/clear` між Plan і Apply; між Apply і Review. Стан — у файлах (`PLAN.md`, `CHANGELOG.md`), не у chat-історії. Розділ 4 — TTL контексту. Розділ 5 — гейти між фазами.

### 7.5.5. Scope growth усередині Apply

Модель (або інженер за нею) "заодно" виправляє імпорти у 20 сусідніх файлах, робить minor style cleanup, оновлює залежність.

**Чому виникає:** оптимістичне "поки ми тут, давайте заодно…"; відсутність явного `Do NOT` у промпті.

**Сигнали:**

- Diff — 30+ файлів, з яких 25 не стосуються задачі.
- Комміт-історія складна; автор не може пояснити, які файли належать до фічі, а які — ні.
- Code-reviewer не може відрізнити change-of-interest від noise.

**Наслідки:** нерев'юабельний diff; merge-ризик; regression у "заодно" зміненому коді, який ніхто уважно не подивився.

**Фікс:** scope зафіксований у `PLAN.md` → promtpt посилається на нього (`@PLAN.md`). Constraints `Do NOT touch files outside the scope listed above`. Все "заодно" — окремий PR після merge основного. Розділ 5, розділ 6.

### 7.5.6. Нескінченний fix-loop

Модель на п'ятій ітерації все ще не виправляє баг; інженер все ще її "мотає".

**Чому виникає:** sunk-cost ("уже стільки часу інвестував"); надія, що "ще один промпт" спрацює.

**Сигнали:**

- Та сама помилка на третій ітерації поспіль.
- Модель каже `Fixed!`, але тест валиться там же.
- Ти вже не памʼятаєш, що пробував, а що ні.

**Наслідки:** години на те, що рішалося за 10 хвилин руками; token-overspend; відчуття провалу.

**Фікс:** правило "3 strikes" — якщо тест / діагностика валиться три рази поспіль одним і тим самим способом, зупинися. Варіанти дії: новий chat із мінімальним контекстом; руки у код (debug через `console.log` / breakpoint); ескалація до колеги / іншої моделі. Не "ще один промпт".

### 7.5.7. Manual edits без re-sync з агентом

Інженер править щось руками у IDE, потім просить агента продовжити. Агент не бачить ручних правок, повертає файли до попереднього стану "по пам'яті".

**Чому виникає:** агент не перечитує файл перед редагуванням у тому ж turn-і (економія токенів); інженер не повідомляє про ручний edit.

**Сигнали:**

- Тільки що вручну виправлений рядок раптом повернувся до попередньої форми.
- У diff зʼявляються зміни, які ти вже закоментував або видалив руками.
- Агент "дивується" існуючому коду: "I'll add function X" — коли function X уже є.

**Наслідки:** повторні фікси того самого місця; втрачені ручні правки; fights з агентом за одні й ті самі рядки.

**Фікс:** після ручного edit-у — або новий chat (simpler), або explicit instruction: `I have manually edited <file>. Re-read it before making further changes.` Краще довший-term фікс — ground-truth у `CHANGELOG.md`, куди агент сам пише зміни, і inженер коментує свої ручні.

### 7.5.8. Немає persistent change-log у довгих сесіях

На 10-й іterації Apply інженер просить `відкати останню зміну` — агент не знає, що це означає, або відкочує не те.

**Чому виникає:** відсутня дисципліна писати кожну зміну у файл.

**Сигнали:**

- `undo`/`revert` запити агенту дають непередбачуваний результат.
- Після 7–8 ітерацій git-log виглядає як "wip, wip, wip, fix, fix, fix — все мертве".
- Неможливо сказати, на якій іterації все ще працювало.

**Наслідки:** втрачена робота; болючий `git reflog`-археологічний копіж; неможливо зробити clean rollback до відомо-робочого стану.

**Фікс:** правило у entry-point: `After each significant change, append to CHANGELOG.md: timestamp, file, one-line description.` Commit на stable boundaries — не у кінці дня, а коли тест зелений + diff compact. `git stash` / worktree для експериментів, які можуть не спрацювати.

### 7.5.9. Commit без ручного stage

Агент сам робить `git add .` + `git commit`. У PR летять `PLAN.md`, scratch-файли, `.env.local.override`, переміщені `node_modules`.

**Чому виникає:** `git commit` у allow-list; `/pr-prep` команда без approve-гейту.

**Сигнали:**

- У PR-diff раптом `package-lock.json` на 10k рядків змін (reset-ився lock-file).
- У commit-і `dist/` або `.next/` build-артефакти.
- Автор PR не може пояснити, чому саме ці файли пішли.

**Наслідки:** зламаний history; іноді — leak (секрети у випадково закомічений файл); повторний `git revert` + rewrite-і гілки.

**Фікс:** `git commit` ніколи не у whitelist без explicit flow; stage — завжди manual approve. Розділ 5 — фаза 5 (Commit & Deliver). Команда `/commit-msg` генерує повідомлення, але не робить commit. `.gitignore` акуратний; pre-commit hook, що блокує commit `.env*`.

### 7.5.10. `--no-verify` як звичка

Pre-commit / pre-push hooks сповільнюють — інженер почав регулярно використовувати `git commit --no-verify`.

**Чому виникає:** hook повільний; нема терпіння; fix-loop пришвидшили "швидким commit-ом".

**Сигнали:**

- У `git log` видно `--no-verify` у повідомленнях.
- CI ловить те, що мав відловити pre-commit.
- Колеги скаржаться, що у main приходить broken main з lint-помилками.

**Наслідки:** quality-control вимкнений; CI стає повільним pre-commit-ом; регресії у main.

**Фікс:** якщо hook повільний — зменш його scope (lint тільки на staged файлах, тести тільки на affected), а не відключай. `--no-verify` — аварійний засіб для одного commit, не звичка. Розділ 3 — налаштування hooks. Якщо hook регулярно bypass-иться командою — це сигнал редизайну hook-а, а не exceptional.

### 7.5.11. Один mega-PR на цілу епіку

AI за півдня згенерував 2000-line PR. Reviewer-и дивляться на нього, не знають, звідки підійти, ставлять `Approve` по знайомству або `Request changes` без конкретики.

**Чому виникає:** AI швидкий → інженер нарощує scope; немає психологічного бар'єра "більше — важче зробити".

**Сигнали:**

- PR на 500+ рядків змінених у 10+ файлах.
- Назва PR — `feat: implement X` (загалом про все).
- Review триває 2+ дні, коментарі поверхневі.

**Наслідки:** тому merge затягується; якість review низька; конфлікти з іншими PR; при bug-hunt неможливо звузити source change.

**Фікс:** один Plan → один PR → один scope. Епіка = послідовність PR-ів, кожен < 400 рядків. Рекомендація з розділу 5 — `/plan-split` для великих задач.

### 7.5.12. AI для задач, швидших руками

Інженер витрачає 5 хвилин на промпт і виправлення згенерованого, щоб зробити зміну, яка руками зайняла б 30 секунд: rename variable у 2 файлах; одна строчка JSX; corrected typo в docs.

**Чому виникає:** звичка "все через AI"; tool-ова еуфорія після перших успіхів.

**Сигнали:**

- Короткі diff-и мають довгу chat-історію.
- На простих змінах ти ітеруєш 2–3 рази, що довше, ніж просто зробити.
- Token-spend непропорційний обсягу зміненого коду.

**Наслідки:** net slowdown; token-overspend; деградація власних навичок написання коду.

**Фікс:** AI — для leverage. Rule-of-thumb: якщо руками менше ніж за хвилину, — роби руками. AI — для refactor-ів, генерації тестів, multi-file changes, задач з неявним scope-ом. Розділ 2 — decision tree.

### 7.5.13. Клієнт / PM вставляє AI-спеку у тікет

Тікет приходить із готовими API-сигнатурами, таблицями БД, class-diagram-ами, які PM/клієнт згенерував ChatGPT-ом. Інженер починає реалізовувати.

**Чому виникає:** AI-tooling доступний усім; PM-у здається, що він допомагає; немає process-а, де тікет = business scenario, не technical design.

**Сигнали:**

- Тікет містить code snippets, часто — у неконсистентному стилі.
- Запропонована схема БД суперечить проєктним конвенціям.
- API-сигнатури ламають backwards-compatibility без обговорення.

**Наслідки:** інженер "заклинюється" на запропонованому дизайні; власна технічна дискусія пропускається; пізніше виявляється, що підхід не інтегрується з системою.

**Фікс:** дисципліна про розподіл відповідальності: тікет = business scenario (що і для кого), technical design = engineering (як). AI-згенерований технічний матеріал у тікеті — reference only, не contract. `/feature-analyse` (розділ 6) відокремлює бізнес-вимоги від implementation reference.

### 7.5.14. Людське review як bottleneck

AI згенерувало 10 PR-ів за день. Reviewer-и не встигають читати якісно, accept-лять половину formально.

**Чому виникає:** приріст AI-velocity не збалансований приростом review-capacity; команда досі рев'ює "як раніше".

**Сигнали:**

- Queue непрочитаних PR-ів росте.
- Час від open-PR до merge — 2–3 дні, з них review — години.
- Постmerge regression rate росте.

**Наслідки:** merge-bottleneck; quality drop; demotivation у reviewer-ів (їх стає "AI-дампом").

**Фікс:** шарове review — linter → AI pre-review (`/review` з розділу 6) → human на critical paths; PR-и малі (< 400 рядків); author доповнює PR own-`/verify` звіт перед запитом людського review. Розділ 5 — responding to PR comments.

## 7.6. Architecture & security risks

Антипаттерни цієї групи — найдорожчі. Їхня ціна не години, а клієнтські санкції, compromise-и production-а, IP-втрата, репутаційні ризики. Усі вони залежать від того, що інженер розуміє **до** того, як включити AI, а не після.

### 7.6.1. Секрети / credentials у chat-контексті

Інженер копіпастить `.env` файл або connection string у chat-запит, щоб "модель розібралася з конфігом".

**Чому виникає:** зручність; брак усвідомлення, що chat-запити зберігаються на стороні провайдера.

**Сигнали:**

- У chat-історії видно `DATABASE_URL=postgres://user:password@host...`.
- Скріншот IDE з видимим sidebar, де відкритий `.env`.
- Промпт містить API-ключ Stripe / AWS / OpenAI.

**Наслідки:** leak у logs провайдера; потенційна compliance-violation (GDPR, SOC2); клієнт дізнається — тріал або санкція.

**Фікс:** секрети **ніколи** не в контексті. Placeholders (`<DATABASE_URL>`) + локальне виконання для перевірки. У entry-point rule: `Never include secrets, credentials, or production data in any prompt.` Enterprise-endpoint з no-retention policy для клієнтських проєктів. Розділ 3 — настройка privacy-mode.

### 7.6.2. Mock-data з реальним PII у репозиторії

Frontend / QA-fixtures містять "приклади" з реальними імʼями, email-адресами, номерами телефонів, взятими з продакшну "щоб виглядало реалістично". AI згенерував їх за реальним зразком.

**Чому виникає:** запит до AI: "згенеруй test users"; модель іноді вставляє справжньо виглядаючі дані.

**Сигнали:**

- У `fixtures/` / `mocks/` — імена, які схожі на справжні акаунти.
- Emails у `john.smith@example.com` стилі, але з реально існуючих доменів клієнта.
- GDPR-audit знаходить "користувача у репозиторії".

**Наслідки:** privacy-incident; потенційний лист від регулятора; публічний репозиторій із реальним PII → шлях для social engineering.

**Фікс:** вимагати у промптах на test data — `Faker / mock library` патерни (`user_<uuid>@example.test`, `555-0100` для phone). Правило у entry-point: `All mock data must be clearly fictitious — use reserved-domain emails (.test, .example), synthetic names, and safe-range test numbers.` Lint на PII у fixtures.

### 7.6.3. AI може торкатися production-systems

Агент має в allow-list-і `kubectl`, `psql` з production-URL, `aws` CLI з production-credentials; або MCP-сервер, підключений до production-бази "для читання".

**Чому виникає:** зручно debug-ити "з контексту"; single machine для dev+staging+prod.

**Сигнали:**

- У chat-історії видно реальні `kubectl get pods -n production`.
- Агент виконав `DROP TABLE` у dev, а DB-URL вказував на staging-dump з копією prod-а.
- AWS-credential-и мають прод-права.

**Наслідки:** можливий виконаний прод-query через галюцинацію; data exfiltration; compliance-incident; у найгіршому — production incident.

**Фікс:** агент **ніколи** не має прод-credential-ів. Розділення: dev-machine = dev/staging credentials; production — окремий обмежений доступ через bastion / break-glass, без агентів. Read-only access до production — якщо справді потрібно, через окремий proxy з audit log. Розділ 3 — rail-guards на tool permissions.

### 7.6.4. Unvetted packages / supply chain

AI порадив встановити `npm install <cool-lib>`, інженер встановив без перевірки.

**Чому виникає:** довіра до pattern-а "AI так порадило"; brak звички перевіряти package reputation.

**Сигнали:**

- У `package.json` зʼявляються пакети, яких немає у проєктному `ADR`-і / approved-list.
- Пакет малопопулярний (< 1000 weekly downloads), не має release-history.
- Назва схожа на популярний пакет (typosquatting: `lodash-utils`, `reakt`, `axois`).

**Наслідки:** supply-chain compromise; install-time script виконує щось зловмисне; уразливість через 2–3 місяці після мимовільного update-у.

**Фікс:** правило у entry-point: `Before adding any new dependency, verify: weekly downloads > 10k, last release within 12 months, maintainer is known.` Approved-list у великих проєктах. `npm audit` / Snyk / Dependabot. Розділ 4 — skill для vetting packages.

### 7.6.5. Over-engineered архітектура "за замовчуванням"

AI згенерував abstract factory + strategy + visitor для trivial data-transform-у. Або — microservice з gRPC-контрактами для функції на 20 рядків.

**Чому виникає:** моделі навчалися на enterprise-коді; за замовчуванням їхня "best practice" — abstract-over-abstract.

**Сигнали:**

- На просту фічу — 5+ нових класів / інтерфейсів.
- `patterns.md`-стилістика у PR з patterns, яких не вимагала задача.
- Нова фіча додає 3+ рівнів абстракції між entry-point-ом і business-logic.

**Наслідки:** maintainability collapse; onboarding нового інженера виростає; rewriting через рік на "trivial first version".

**Фікс:** Constraint у промптах на implementation: `Prefer the simplest solution. Do NOT add abstraction layers unless explicitly asked. If you feel an abstraction is needed, ask me first.` YAGNI — expliцитно у skill. Architecture review — людська, навіть якщо AI "виглядає переконливо".

### 7.6.6. Duplication замість reuse

AI не "побачив" існуючого utility-модуля, згенерував ще один з таким самим функціоналом.

**Чому виникає:** контекст не включає utility-шар; entry-point не мапить існуючі хелпери.

**Сигнали:**

- У diff — новий `utils.ts` з функціями, які вже є у `lib/` / `shared/`.
- `grep` знаходить 3 реалізації однієї функції.
- Tests новонаписані дублюють існуючі.

**Наслідки:** code duplication; невідповідна поведінка між дубликатами; bug-фікс у одному, інший залишається broken.

**Фікс:** у entry-point — секція "where to find common utilities" з path-ми до `lib/`, `shared/`, `utils/`. У `/plan` — крок "identify existing modules that can be reused". Constraint у implementation-промптах: `Before creating new utilities, grep the codebase for existing ones.` Розділ 4, розділ 5.

### 7.6.7. Stale docs як ground truth

Confluence / wiki / README вже не відображає реальність. AI читає їх і впевнено генерує код, який узгоджений з docs, але не з actual behavior.

**Чому виникає:** docs не оновлюються після refactor-ів; AI довіряє тексту, бо текст "виглядає як specification".

**Сигнали:**

- AI згенерував виклик API, який у коді вже deprecated.
- Модель описує flow, якого вже немає у codebase.
- PR-и містять код, узгоджений з документацією і НЕ узгоджений із поточним кодом.

**Наслідки:** поведінка runtime не відповідає ні docs ні тим, що AI написав; невидимі bugs.

**Фікс:** code > docs. AI має читати код першим, docs — як supplementary context. Для long-term — spec-driven підхід (розділ 1, L2) де docs регенеруються з коду. Періодична аудит-прогонка: `/doc-from-code` — згенерувати docs з коду, порівняти з існуючим wiki, оновити wiki.

### 7.6.8. IP / client data у public моделях без privacy mode

Інженер використовує free-tier ChatGPT / Claude web з training-opt-in за замовчуванням на клієнтському коді.

**Чому виникає:** звичка з "своїх проєктів"; brak знання настройки privacy-mode на tool-і.

**Сигнали:**

- Privacy-mode вимкнено у налаштуваннях клієнта.
- У terms tool-а явно зазначено, що free-tier може використовувати дані для training.
- Клієнтський tech-contract забороняє "передачу даних третім сторонам", а policy tool-а її дозволяє.

**Наслідки:** IP-leak; клієнт узнає → контрактна відповідальність; код клієнта потенційно використовується для training моделі.

**Фікс:** для клієнтських проєктів — **тільки** enterprise-endpoint-и з no-retention / no-training (Claude Enterprise, ChatGPT Business/Enterprise, Azure OpenAI). Privacy-mode увімкнено **до** першого запиту. Розділ 3 — setup. Перевір умови tool-а і клієнтський NDA **до** старту проєкту.

### 7.6.9. AI генерує insecure code

Тривіальні classical vulnerabilities у AI-output-і: SQL injection (конкатенація), XSS (innerHTML з user-input), CSRF-uncovered endpoints, hardcoded secrets у examples.

**Чому виникає:** training data містить багато "tutorial-стилю" коду, де безпека пропущена заради стислості.

**Сигнали:**

- `query = "SELECT * FROM users WHERE id=" + userId`
- `div.innerHTML = userInput`
- `@app.route("/admin/delete", methods=["POST"])` без auth-check.

**Наслідки:** security-incident у проді; OWASP Top 10 regression; клієнт-audit знаходить vulnerabilities у AI-частині коду.

**Фікс:** security-skill у проєкті, що розписує: parameterized queries, output-encoding, auth-middleware, secret-management. Security review — обовʼязковий turn у `/review` (або `/bug-hunt` на security focus) перед merge-ем для будь-якого код, що торкається auth / input / DB. SAST у CI. Розділ 6 — subagent `/security-review`.

### 7.6.10. Architectural drift

Модель на кожній фічі обирає "найпростіший спосіб сьогодні", не звіряючись з existing architectural patterns. За 3 місяці — 5 різних способів робити HTTP-запити, 3 способи state-management-у, 2 DI-підходи.

**Чому виникає:** entry-point / rules не фіксують архітектурні рішення явно; кожен інженер генерує "як правильно сьогодні".

**Сигнали:**

- Новий код не наслідує паттерни з 80% codebase.
- ADR-и ніхто не підтримує; або їх нема взагалі.
- Code review-и все більше про "у нас не так робиться".

**Наслідки:** maintainability crash через 6 місяців; onboarding новачка — місяць замість тижня; bug-фіксинг розтягується.

**Фікс:** ADR-и в проекті + entry-point посилається на них. Skill-и під кожен cross-cutting concern (HTTP client, state, errors, logging). Constraint: `Follow conventions in @ADR-003 (HTTP client). Do NOT introduce new HTTP libraries.` Розділ 4 — rules і skills для architectural consistency.

### 7.6.11. Pixel-perfect loop без design-system

Інженер відкрив Figma → screenshot → "implement this pixel-perfect" → AI генерує close-but-wrong → tweak loop на години.

**Чому виникає:** пропущений етап skill-а під design-system; візуальні порівняння не автоматизовані.

**Сигнали:**

- 20+ ітерацій на один компонент.
- Кожна правка — на 2–3 px / shade-color.
- Результат виглядає не так, як сусідні компоненти у застосунку.

**Наслідки:** UI-drift; години на компонент; final result все одно потребує manual polish.

**Фікс:** design-system skill (tokens, spacing, typography, component library links). Figma MCP — для структури і text-контенту, не для візуального кодування. Візуальне QA — людське око + Percy / Chromatic snapshot tests. Розділ 4 — skills під UI.

### 7.6.12. Юніори на повній автономії

Junior підключає Cursor Agent auto-mode, фічі генеруються автоматично; inженер-автор робить formal-review без розуміння generated code.

**Чому виникає:** скорочення onboarding-time-у; надія, що "AI вчитиме junior-а".

**Сигнали:**

- Junior не може пояснити, чому generated код працює.
- PR-коментарі revealing fundamental gaps ("що таке transactional scope?").
- `/bug-hunt` знаходить баги, які junior впевнено accept-нув.

**Наслідки:** deep tech-debt від code-у, власник якого його не розуміє; стагнація професійного росту; неможливо ескалювати проблему, бо author "знає тільки prompts".

**Фікс:** L1-standard для junior-ів — manual implementation з AI як helper, не як generator. Mandatory explanation step: `Explain in your own words what this code does and why.` AI-assisted ≠ AI-autonomous. Розділ 1 — maturity levels. Junior повинен пройти L1 перед будь-яким agentic-режимом.

### 7.6.13. Erosion of engineering judgment

Досвідчений інженер поступово перестає читати generated код уважно; довіра стає blanket; mental model самого codebase тоншає.

**Чому виникає:** AI дає confident вивід; довіра накопичується; "перечитувати код" сприймається як вираз недовіри до інструменту.

**Сигнали:**

- На debug-сесіях інженер не знає, як структурований код, який сам "написав" з AI.
- При зміні AI-tool-а продуктивність падає різко (не було навичок — був інструмент).
- Conversation з AI заміняє conversation з кодом.

**Наслідки:** при incident-і в проді автор не може debug-нути; знання системи belongs to tool, а не до інженера; професійна вразливість.

**Фікс:** правило — code ownership не делегується. Review AI-output-у — читати, не diagonal-skim. Періодичні "AI-free" задачі — debug з `console.log`, читання unknown коду без chat-помічника. Розділ 5 — review як obligation, не формальність.

## 7.8. Як використовувати каталог у команді

### 7.8.1. На персональному рівні

- Раз на 2 тижні переглядати останні 5–10 своїх PR проти каталогу — які антипаттерни у себе спостерігаєш найчастіше.
- Кожний знайдений у себе антипаттерн → відповідна дія: оновити промпт (розділ 6), або rule (розділ 4), або workflow-звичку (розділ 5).
- Не "намагатися уникати всіх одночасно" — вибирай top-3 на квартал.

### 7.8.2. На рівні команди

- Постреєж-retro кожного спринту — один пункт "на які антипаттерни ми натрапили на цьому спринті".
- Повторюваний антипаттерн у > 1 інженера → це сигнал, що процес або context-setup на проєкті має прогалину, а не що інженери "роблять неправильно".
- Фікс — через зміну shared-артефактів (`AGENTS.md`, rules, skills, commands), не через memo "пам'ятайте, що...".

### 7.8.3. На рівні проєкту

- Новий проєкт: каталог — частина onboarding-чекліста. Проходиш по §4 (Security & Architecture) до того, як дати AI першу задачу.
- Client-facing проєкти: блок §4 читається разом з клієнтським NDA / security-policy. Будь-який конфлікт → зупинка до узгодження.
- Audit раз на квартал: пройтись по §4 проти реального setup-у — де реальність розходиться з рекомендаціями.

> 💡 **Hint:** Не роби з каталогу чек-лист з 50 пунктами, який треба проходити на кожному PR. Це катаlog — довідник, у який заглядаєш, коли помічаєш проблему. Автоматизація частини перевірок (lint, SAST, pre-commit hooks, privacy-mode у tool-і) окуповується значно краще, ніж ручний review проти каталогу.

## 7.9. Чек-лист "у мене все під контролем"

Мінімальний набір критеріїв, що показує: основних антипаттернів у вашому setup-і вже немає. Якщо на 8+ пунктів відповідь "так" — ти у здоровому діапазоні; на < 6 — повертайся у відповідні розділи.

- Auto-accept вимкнено на будь-яких write-операціях; `git commit` / `git push` / `rm` ніколи не у whitelist без explicit-flow.
- `AGENTS.md` / `CLAUDE.md` ≤ 150 рядків; детальні інструкції — у skills on-demand.
- Вибір моделі — свідомий для нетривіальних задач; не default на все.
- Кожен repeatable-промпт має **Intent, Inputs, Steps, Constraints, Output format, Verification hook** (анатомія з розділу 6).
- Жодного Apply без затвердженого `PLAN.md`; жодного commit-у без ручного stage; жодного merge без людського review.
- `/clear` між фазами Plan → Apply → Review; стан у файлах, не у chat-історії.
- Секрети, production credentials, клієнтські персональні дані — ніколи у chat-контексті; privacy-mode увімкнено для tool-ів, що працюють з клієнтським кодом.
- Pre-commit hooks швидкі і не bypass-яться через `--no-verify`; CI дублює їх для safety.
- Bot-review коментарі проходять assessment-крок ("is this comment actually correct?") до фіксу.
- Новий PR містить < 400 рядків змін і scope, зафіксований у `PLAN.md`.
- Security-огляд для коду, що торкається auth / input validation / DB — окремий turn, не частина generic `/review`.
- Junior-и на проєкті проходять L1 з AI як helper, не як autonomous generator; explanation-step обов'язковий у їхніх PR.

Каталог антипаттернів — останній розділ L1 плейбука. Якщо усі попередні розділи (Philosophy → Prompt Library) засвоєні, а поточний використовується як довідник при поломках, — переходь до L2 (Spec-Driven Development): окремий, ще не опублікований том, що припускає стабільний L1 на щоденних задачах.
