# 6. Prompt Library

**Статус:** Draft
**Дата:** 21 квітня 2026

Цей розділ описує, як побудувати і підтримувати **власну бібліотеку промптів** — набір заготовлених інструкцій під повторювані задачі, який живе у репозиторії поруч із кодом, ревʼюїться у PR і еволюціонує разом із проєктом. Це не каталог "крутих промптів", зібраних з Twitter, а інженерний артефакт із власним lifecycle-ом.

Базова теза розділу: **якщо інженер пише один і той самий prompt третій раз — це не prompt, це команда, яку ще не оформили.** Бібліотека промптів — це оптимізація муcle-memory: переводить рутинні інструкції з голови у `.claude/commands/`, `.cursor/commands/`, `.claude/agents/` чи локальний `prompts.md` так, щоб наступний запуск коштував один слеш, а не десять хвилин згадування формулювань.

Передумова розділу: у інженера вже пройдено розділи 3–5. Контекст налаштовано (entry-point, rules, skills), цикл Plan → Apply → Review працює на реальних задачах. Без цього prompt library нічого не оптимізує — додавання `/plan` над відсутнім workflow просто дає швидший шлях до поганого коду.

## Що читач має винести з цього розділу

Після прочитання інженер повинен:

- знати, коли промпт треба оформити у command/skill/agent, а коли лишити inline;
- володіти анатомією промпту — бачити у формулюванні, що саме змусить модель виконати крок, а що — проігнорувати;
- мати стартовий набір промптів під п'ять типів задач: planning, spec generation, implementation, testing, review & commit;
- вміти адаптувати промпт під свій стек: які шматки стабільні, які параметризуються, які винести у skill;
- розуміти, як бібліотека еволюціонує — коли промпт додається, коли оновлюється, коли видаляється;
- знати типові антипатерни "роздутих" бібліотек і як не прийти до 80 промптів, з яких команда використовує 6.

## Що таке prompt library

Prompt library — це **сукупність заготовлених промптів**, що зберігаються у проєктному репозиторії, організовані за типом задачі і викликаються як slash-команди (`/plan`, `/verify`, `/review`), передаються у subagent-и або копіпастяться у поточний chat для разових-але-типових сценаріїв.

Три критерії, за якими текст належить до бібліотеки:

1. **Повторюваність.** Той самий тип задачі 3+ разів на місяць у тебе особисто або у команди.
2. **Стабільна частина.** Є формулювання, які **не змінюються** між запусками — вони і складають prompt. Змінна частина (параметри) передається у момент виклику.
3. **Документуюча сила.** Промпт, прочитаний людиною, зрозумілий — бо описує протокол роботи над задачею, а не магічне закляття.

Коли текст не проходить хоча б один критерій — це не кандидат у бібліотеку, а inline-запит у поточний chat.

### Prompt library vs skill vs rule vs subagent

Частіша плутанина на старті — "куди саме це покласти". Нижче — коротке розмежування в одному місці (повний опис — у розділі 4):

| Артефакт     | Викликається         | Містить                                       | Типовий розмір     |
| ------------ | -------------------- | --------------------------------------------- | ------------------ |
| **Rule**     | Автоматично (always) | Коротке нормативне правило (1–3 рядки)         | 10–30 рядків       |
| **Skill**    | Автоматично (on demand) | Детальну інструкцію "як робити X"              | 200–700 рядків     |
| **Command**  | Вручну (`/verify`)   | Готовий prompt "зробити Y прямо зараз"         | 20–100 рядків      |
| **Subagent** | Як tool-call         | Роль + методологію "ось як думай"              | 100–300 рядків     |
| **Inline**   | Як частина chat-у    | Разовий запит під унікальну задачу              | 1–10 рядків        |

**Prompt library = сукупність commands і subagent-промптів** (плюс опційно колекція inline-заготовок у особистому `prompts.md`). Rules і skills — окремі артефакти контексту, не частина бібліотеки.

> 💡 **Hint:** Якщо новий prompt складно розмістити — це сигнал, що у ньому змішані дві різні речі. Типовий приклад: промпт на 300 рядків, у якому перша половина — конвенції тестування (це skill), друга — "згенеруй і запусти тести на змінених файлах" (це command). Розділи на два артефакти — обидва працюватимуть краще.

## Анатомія працюючого промпту

Різниця між промптом, що дає стабільний результат, і таким, що "іноді працює", — у структурі, не у довжині. Нижче — шість складових, які мають бути у кожному промпті бібліотеки. Відсутність будь-якої з них — типова причина nondeterministic-результату.

### 1. Intent

Одне речення у першому рядку: що саме робить цей промпт і від чиєго імені. Модель читає перший рядок як найважливіший — це позиція, з якої вона обирає mental model для всього виклику.

Приклад сильного intent: `Stop and critically verify the work you've just completed. Assume you've made mistakes — your job is to find them.`

Приклад слабкого: `Review the code.`

Перший явно перемикає модель у critical-reviewer-mode; другий залишає інтерпретацію на модель — вона сама вирішить, чи "шукати баги", чи "похвалити гарний стиль".

### 2. Inputs

Які артефакти приходять ззовні. Явно перелічи: PR номер, ticket ID, шлях до файлу, git range, `$ARGUMENTS`. Якщо частина вхідних даних опційна — вкажи fallback: "If I haven't provided a ticket, ask for one."

Без цього блоку модель або hallucinate-ить відсутні дані, або зупиняється з питанням посередині виконання.

### 3. Steps

Послідовність кроків — **пронумерована, з дієсловом на початку**. Модель значно стабільніше виконує нумеровані списки, ніж "do A, B, C in one paragraph". Кожен крок — одна дія.

Якщо крок має умовну гілку ("if A then X, else Y") — винеси її у явне `if`/`else`, не ховай у пропозиції.

### 4. Constraints

Що робити **не можна**. Це не формальність — це ключовий блок, який зупиняє модель від "допоміжних" дій: reformat unrelated imports, refactor "заодно", auto-commit без approve.

Приклади обмежень, що реально окуповуються:

- `Do NOT start implementing yet — wait for my approval of the plan.`
- `Do NOT stage files without my explicit approval.`
- `Do NOT touch files outside the scope listed above.`
- `Do NOT delegate this to another agent — execute step by step yourself.`

### 5. Output format

Чим точніше описано формат виводу, тим менше часу на його розбір руками. Варіанти:

- **Структурований список** з фіксованими лейблами (`🔴 Critical / 🟡 Warning / 🟢 Suggestion / ✅ Good`).
- **Markdown-таблиця** з колонками `File / Issue / Severity / Fix`.
- **JSON / XML** — для випадків, коли вихід парситься іншим tool-ом.
- **Ready-to-paste reply** — коли результат лягає у GitHub/Linear як коментар.

Без output-specification модель сама вирішує форму — і форма змінюється від запуску до запуску.

### 6. Verification hook

Як перевірити, що промпт відпрацював. Часто це посилання на `/verify` або конкретну команду (`pnpm test -- <file>`). Verification-крок робить промпт замкнутим: він не просто щось згенерував, а довів, що результат проходить гейт.

Компактний приклад промпту з усіма шістьма блоками:

```markdown
<!-- Intent -->
Write unit tests for the source file I pass via $ARGUMENTS.

<!-- Inputs -->
Arguments: path to a source file under `src/`.
Read the project testing conventions from `.claude/skills/write-test/SKILL.md`.

<!-- Steps -->
1. Read the source file in full — identify exports, types, dependencies.
2. Identify the artifact type (util, hook, component, slice, route).
3. Check if a co-located `.test.ts` / `.test.tsx` already exists.
   - If yes: extend it, do not overwrite.
   - If no: create a new co-located test file.
4. Cover: happy path, null/empty/zero, error paths, boundary conditions.
5. Run `pnpm test -- <test-file>` and report the result.

<!-- Constraints -->
- Do NOT modify the source file being tested.
- Do NOT add tests to unrelated files.
- Do NOT skip failing cases with `it.skip`.

<!-- Output format -->
After the run, report:
- Files created / modified
- Test scenarios covered (list)
- Test run result (pass / fail with exact error)

<!-- Verification hook -->
If any test fails, do NOT "fix" the test to make it pass. Report the failure
and wait for my decision.
```

> 💡 **Hint:** Якщо промпт у тебе на 5 рядків і "чомусь не стабільно працює" — перевір, чи є у ньому **всі шість** блоків. Відсутній Constraint блок — типова причина "AI зробив, але заодно поламав X". Відсутній Output format — причина того, що кожен запуск виглядає по-різному і результат важко парсити.

## Planning prompts

Планування — це фаза, де промпт окуповується найсильніше: кожен неточний plan на порядок дорожче виправити на етапі Apply. Тут достатньо двох-трьох прицільних промптів у бібліотеці.

### `/plan` — план імплементації за тікетом

Ядро `/plan` — перевести тікет у структурований, ревʼюабельний план, збережений у `PLAN.md`.

```markdown
I'm about to start working on a task. Help me plan the implementation before
writing any code.

1. If I haven't provided a ticket number, ask me for one. If I have — fetch it
   (Jira/Linear/GitHub) and read title, description, acceptance criteria,
   comments.
2. Analyze the codebase — identify which files, modules, and patterns are
   relevant. Check existing implementations of similar features for patterns
   to follow.
3. Propose an implementation plan with:
   - Files to create or modify (specific paths).
   - Order of operations (what to build first — usually data layer before UI).
   - Database changes (migrations, new entities).
   - API changes (new endpoints, modified responses).
   - Frontend changes (components, routes, services).
   - Test strategy (what to test, which patterns to use).
4. Flag risks — potential breaking changes, edge cases, dependencies on other
   teams, areas needing extra QA.
5. Save the plan to PLAN.md in the current directory so we can reference it
   during implementation.

Do NOT start implementing yet — wait for my approval of the plan.
```

Розширення, що окуповуються на конкретних стеках:

- **Worktree setup** — якщо проєкт працює з git worktrees, додай у кінці кроки "clean up merged worktrees, create new worktree per naming convention". Це виключає ручний setup на старті кожної задачі.
- **Branch naming** — якщо на проєкті є convention `feat/<ticket>-<slug>` — винеси у крок генерації гілки.
- **Affected tests scan** — додай крок "list existing tests that will need updates". Це попереджає ситуацію "план готовий, а тести ніхто не згадав".

### `/plan-spike` — розвідувальний план під невідомий модуль

Коли scope незрозумілий і треба спочатку дослідити код, не починаючи імплементації. Окремий промпт, бо повний `/plan` тут хибно попросить "план імплементації" там, де треба "план дослідження".

```markdown
I need to investigate a module before planning an implementation. Do NOT
propose code changes yet — your output is an investigation report.

Target: @<module-or-file-path>

1. Read the target file(s) and their immediate dependencies.
2. Map the data flow — entry points, state, side effects, outputs.
3. Identify risk zones — complex logic, hidden coupling, implicit contracts,
   areas with TODO/FIXME/HACK comments.
4. List test coverage — which scenarios have tests, which do not.
5. Produce INVESTIGATION.md with:
   - Architecture summary (3–5 bullets)
   - Data flow diagram (ASCII or mermaid, short)
   - Risk zones (with file:line references)
   - Coverage gaps
   - Open questions (what you could not determine from reading alone)

Do NOT write code. Do NOT propose changes. This is research only.
```

Вихід цього промпту — вхід для наступного запуску `/plan`.

### `/plan-split` — розбиття великої задачі на підзадачі

Коли тікет очевидно великий (фіча на кілька модулів, міграція, епіка). Не генерує імплементаційний план — генерує список під-тікетів.

```markdown
This task is too large for a single Plan → Apply → Review cycle. Split it
into sub-tasks.

1. Read the ticket / feature brief I provide.
2. Analyze the codebase to understand existing structure.
3. Break the work into sub-tasks of 1–3 days each. For each sub-task:
   - Title (action-oriented)
   - Scope (files / modules touched)
   - Dependencies (which sub-tasks must be done first)
   - Risk level (low / medium / high)
   - Test strategy (one sentence)
4. Group sub-tasks into logical phases:
   - Phase 1: Foundation (schema, entities, core services)
   - Phase 2: API
   - Phase 3: Frontend
   - Phase 4: Integration & polish
5. Output as TICKETS.md ready to paste into Jira/Linear.

Do NOT propose implementation details inside each sub-task — that happens in
per-sub-task /plan runs. Keep each sub-task small enough to fit a single PR.
```

> 💡 **Hint:** Не тримай у бібліотеці десять варіантів `/plan`. На старті достатньо цих трьох: базовий `/plan`, розвідувальний `/plan-spike`, розбивка `/plan-split`. Кожен додатковий варіант має відповідати на питання "який сценарій не покривається існуючими трьома?" — якщо відповідь розмита, його час ще не настав.

## Spec generation prompts

Spec-prompts потрібні, коли на вхід приходить **сировина від продукту** — Notion-сторінка зі змішаними вимогами і фантазіями, Google Doc із pasted AI-виводом, голосова замітка. Задача — перевести сировину у структурований артефакт, що можна ревʼюнути до того, як хтось почав кодити.

### `/feature-analyse` — декомпозиція feature-специфікації

Окупається, коли приходить документ на 3–10 сторінок з мікс-контентом.

```markdown
You are a senior technical analyst. I will provide a feature spec document
that mixes business requirements, technical explanations, and AI-generated
code examples. Your job is to untangle it.

Produce four separate files in the current directory:

1. BUSINESS_REQUIREMENTS.md — pure business logic, no code
   - Problem being solved, for whom
   - User stories (As a [role], I want [action], so that [benefit])
   - Acceptance criteria per requirement
   - Business rules and constraints
   - Edge cases from the business perspective

2. IMPLEMENTATION_REFERENCE.md — technical details and code examples
   - Any code from the document (MARK AS REFERENCE ONLY, not to be copied)
   - Suggested technical approach
   - API contracts / data models mentioned
   - Integration points
   - Flag anything that contradicts our existing patterns (check CLAUDE.md /
     AGENTS.md for conventions).

3. GAP_ANALYSIS.md — what we have vs what we need
   - Existing modules/services/components we can reuse
   - Patterns already used for similar features
   - Database changes required
   - API endpoints needed (new vs modifications)
   - Frontend changes needed (new vs modifications)

4. FEASIBILITY_REPORT.md — critical evaluation
   - 🔴 Blocker — cannot implement as described; must be resolved first
   - 🟡 Concern — possible but risky; propose alternative
   - 💬 Clarification needed — ambiguous, needs product input

If any 🔴 Blocker found: STOP. Do not proceed to ticket breakdown.
State clearly which blockers must be resolved before work can start.

Do NOT copy code from the spec into the codebase. Code examples are reference
material only — our actual conventions win.
```

### `/ac-generate` — генерація acceptance criteria

Коли тікет має вільний опис, але немає явних AC.

```markdown
Generate acceptance criteria for the feature described below.

Input: <ticket link OR pasted description>

Output format — Gherkin-style, grouped:

**Happy path**
- Given <precondition>, when <action>, then <expected result>

**Negative path**
- Given <invalid input>, when <action>, then <expected error>

**Edge cases**
- Empty / null / zero
- Maximum values / overflow
- Concurrent actions
- Unauthenticated / unauthorized user
- Network failure mid-action

Each criterion must be:
- Testable (can be verified by a test or manual step)
- Specific (no "works correctly" — state WHAT "correctly" means)
- Independent (not coupled to another criterion)

Output as AC.md with three sections above. Nothing else.
```

Подальший крок — передати `AC.md` у `/test-cases-generate` (див. нижче).

### `/user-stories-structure` — сирі вимоги → структуровані user stories

Коли приходить розмова з клієнтом, голосова розшифровка, or stream-of-consciousness wishlist.

```markdown
I'll provide raw requirements (notes, transcript, chat log). Structure them
into user stories with acceptance criteria.

Your output — STORIES.md with sections:

## Overview
Short summary (3–5 bullets) of what the feature is and who it is for.

## User Stories
For each story:
- **Story**: As a [role], I want [action], so that [benefit]
- **Acceptance Criteria**: Given/When/Then format (happy + negative + edge)
- **Out of scope**: what we are explicitly NOT building in this story

## Open Questions
Ambiguous points that need product input before we proceed. Number them so
product can reply inline.

## Dependencies
Other features / systems / teams this depends on.

Do NOT invent requirements that are not in the input. If something is unclear,
put it in Open Questions instead of guessing. If the input is contradictory,
flag the contradiction in Open Questions — do not pick a side silently.
```

## Implementation prompts

У фазі Apply промпти короткі і прицільні. Жодних "реалізуй пункти 1–5 плану". Нижче — шаблони, що закривають 80% implementation-кроків.

### `/step` — один крок плану

Базовий шаблон для мікро-циклу Apply. Не оформляється як slash-command у чистому вигляді — використовується як заготовка, куди підставляються конкретні файли і поведінка.

```markdown
Implement ONE step from PLAN.md — the step titled "<step title>".

Scope:
- Files to modify: @<file-1>, @<file-2>
- Behavior: <one-sentence description of what the code must do>
- Pattern to follow: @<reference-file> (match its style and structure)

Constraints:
- Do NOT touch files outside the scope above.
- Do NOT refactor imports in files you are not editing.
- Do NOT introduce new patterns — match the reference file.
- If you find a real bug in code you are not supposed to edit, stop and
  report it; do not silently fix it.

Output:
- Unified diff of all changes.
- One-line summary of what changed in each file.

After you output the diff, WAIT for my confirmation before applying it.
```

### `/extend-pattern` — розширити існуючий патерн

Коли у коді вже є 2+ приклади патерну і треба додати ще один під той самий конвеншн (новий endpoint, нова query-hook, нова slice).

```markdown
Add a new <artifact type> following the existing pattern in this codebase.

New artifact:
- Name: <name>
- Purpose: <one-sentence description>
- Inputs / outputs: <contract>

Existing references (READ these in full before starting):
- @<reference-1>
- @<reference-2>

Rules:
1. File location, naming, exports — exactly match the references.
2. If the references disagree on something, use the newer one (check git log).
3. Co-locate tests following the same pattern as the references.
4. Do NOT invent a new abstraction. If you cannot match the pattern exactly,
   STOP and tell me why — do not ship a "similar but different" variant.

Verify:
- Run lint, type-check, tests on the new file.
- Report any failures.

Do NOT commit.
```

### `/debug` — діагностика конкретного симптому

Коли є відтворювана помилка і треба знайти причину. Окремий промпт, бо модель за замовчуванням перемикається у "fix mode" і пропонує зміни до того, як встановлено cause.

```markdown
I have a reproducible bug. Do NOT propose a fix yet — your job is root-cause
analysis.

Symptom:
<describe the observed behavior>

Expected:
<describe what should happen>

Steps to reproduce:
<list>

Relevant code (start here, expand as needed):
- @<file-or-module>

Your process:
1. Read the relevant code and trace the data flow from input to the observed
   output.
2. List all possible causes in order of likelihood. For each, state:
   - What the cause would be
   - Evidence that supports or contradicts it (file:line references)
   - How to confirm it (additional code to read, log to add, experiment to run)
3. Identify the MOST likely cause and the ONE experiment that would confirm
   or eliminate it.
4. Only after I confirm the cause — propose a fix in a separate response.

Do NOT make changes to code. Do NOT say "I fixed it" before the cause is
confirmed.
```

### `/refactor-contained` — локальний рефакторинг без зміни поведінки

Рефакторинг — небезпечна зона для AI. Без явних обмежень модель "заодно переписує" контракти і ламає callers. Окремий промпт із жорсткими guard-rails.

```markdown
Refactor the code inside @<file-or-symbol> WITHOUT changing external behavior.

Goal of the refactor:
<one sentence — e.g., "extract the validation logic into a separate helper">

Hard constraints:
1. Public API (exports, signatures, return types) MUST NOT change.
2. Callers MUST NOT need updates. If any caller would need an update — STOP
   and report it; this means the API did change and we need a different plan.
3. Tests MUST continue to pass without modification.
4. No unrelated "improvements" (renaming variables for taste, reordering
   imports, formatting) — only the refactor we agreed on.

Process:
1. Run tests BEFORE any change — confirm they pass. Save the result.
2. Apply the refactor.
3. Run tests AFTER — confirm same results. If any test behaves differently,
   the refactor changed behavior; revert and stop.
4. Run lint and type-check. Report diff.

Do NOT commit.
```

### `/extract-context` — зібрати релевантний контекст під задачу

Допоміжний промпт для ситуацій, коли треба завантажити у новий chat мінімум файлів, не перебираючи їх руками.

```markdown
I'm about to open a new chat for a task. List the minimum set of files I
should load via @-references.

Task description:
<paste task / ticket summary>

Your process:
1. Grep the codebase for symbols, strings, file names, module names mentioned
   in the task.
2. Identify the 5–10 files MOST relevant to the task.
3. For each file, explain in ONE line why it is relevant.
4. Identify 2–3 reference files that show the existing pattern for this kind
   of change.
5. Output a ready-to-paste list: `@path/to/file.ts — reason`.

Do NOT include:
- Generated files
- Files that are only superficially related (e.g., share a string but are in
  a different domain)
- More than 10 files total (context budget)
```

## Testing prompts

AI добре пише тести на **код, який написав не він, і який уже ревʼюнутий людиною**. Нижче — три промпти, що відповідають рівням тестової піраміди.

### `/test-unit` — unit-тести на змінений файл

```markdown
Write unit tests for the file I pass via $ARGUMENTS (or for the files in the
current git diff if no argument given).

Follow conventions in @.claude/skills/write-test/SKILL.md (or equivalent).

Process:
1. Read the source file(s) in full — identify exports, types, dependencies.
2. Identify artifact type (util / hook / component / slice / route) to pick
   the correct test pattern.
3. Check if a co-located test file already exists.
   - If yes: extend it, do not overwrite.
   - If no: create a new co-located file with the correct suffix
     (`.test.ts` / `.test.tsx`).
4. Cover, in this order:
   - Happy path (one test per exported function/behavior)
   - Negative path (invalid inputs, thrown errors)
   - Edge cases (null, empty, zero, boundary, max)
   - Concurrency (only if the code is async / reactive)
5. For each test: arrange / act / assert, one behavioral assertion per `it`.
6. Run `<test-runner>` on the new/changed test files. Report exact failures
   if any.

Constraints:
- Do NOT modify the source file being tested.
- Do NOT mock deeply inside domain logic — mocks at IO boundaries only
  (HTTP, DB, storage).
- Do NOT use `it.skip` / `describe.skip`.
- Do NOT introduce hardcoded `new Date()` in time-sensitive tests — use a
  fixed date or the project's clock helper.

Output:
- Files created / modified
- Scenarios covered (bulleted list)
- Test run result
```

### `/test-integration` — скелет + happy path

Integration-тести AI робить добре на скелеті, але гірше — на edge-кейсах.

```markdown
Write an integration test for the endpoint / flow: <name>.

Test pattern reference: @<existing-integration-test-file>

Scope:
- Entry point: <HTTP method + path, OR flow entry>
- Expected behavior: <what the system should do end-to-end>

Write:
1. Setup (module, test DB / fixtures, auth if needed)
2. Happy path: one scenario that exercises the full flow.
3. ONE negative scenario: the most likely failure mode (invalid input OR
   auth failure OR downstream failure).

Do NOT write edge-case variations yet. I will add them in a follow-up prompt
where we list scenarios explicitly. Integration tests that are overly broad
on first pass become a maintenance burden.

Verify the tests pass. Report the run output.
```

### `/test-cases-generate` — QA test cases з AC

Level-1 застосування AI до manual QA: генерація test cases з acceptance criteria, без автоматизації.

```markdown
Generate QA test cases from the acceptance criteria below.

Input:
- @AC.md OR pasted acceptance criteria.

Output — CASES.md with this structure:

## Happy Path
For each happy-path AC: one test case.

## Negative Path
For each negative AC: one test case per error scenario.

## Edge Cases
Add cases not explicitly in AC but likely to matter:
- Empty / null / zero inputs
- Max / min / overflow
- Concurrent actions (double-click, two tabs)
- Unauthenticated / unauthorized
- Network failure mid-action
- Large datasets (if relevant)

Each case in this format:
- **ID**: TC-<feature>-<nnn>
- **Title**: short, action-oriented
- **Pre-conditions**: bulleted
- **Steps**: numbered, one action per step
- **Expected result**: specific and observable
- **Priority**: P0 / P1 / P2

Constraints:
- Do NOT invent acceptance criteria that are not in the input.
- Mark cases you are not confident about with `⚠️ needs review`.
- Keep each case independent (self-contained setup).

The output will be reviewed manually before being uploaded to the test
management tool.
```

> 💡 **Hint:** Результат `/test-cases-generate` має review-rate false-positive-ів близько 20–40%. Без ручного прочитання результат використовувати не можна. Якщо ти викладаєш його одразу у Zephyr/TestRail без review — ти економиш 10 хвилин, витрачаючи 2 години тестерів на роботу з невалідними кейсами.

## Review and commit prompts

Це найщільніший блок бібліотеки. Кожен наступний прошов через review знаходить проблеми, яких не побачив попередній — додавання ще одного типу review-prompt дає помітний приріст у якості, тому тут виправдано мати 4–5 промптів, а не два.

### `/verify` — self-verification AI після Apply

Перший прогін. Модель критично перевіряє свою ж роботу.

```markdown
Stop and critically verify the work you've just completed. Assume you've
made mistakes — your job is to find them.

Step 1: Re-read the original task
- What was asked? (Re-read PLAN.md, the ticket, or the original request.)
- Did you deliver what was requested, or solve a different problem?
- Are ALL acceptance criteria addressed?

Step 2: Verify every changed file
- Run `git diff` and for each file:
  - Read the full diff line by line.
  - Did you modify code you were not supposed to touch?
  - Any TODO / FIXME / placeholder / hardcoded test values left behind?
  - Imports all correct and used?
  - Typos in strings, variable names, API paths, URLs?

Step 3: Cross-file consistency
- Interface/type changed → ALL consumers match?
- API endpoint changed → frontend service matches new contract?
- New enum value → handled in every switch/if?
- DB column changed → migration + entity + serializer + API response all in
  sync?

Step 4: Run lint, type-check, tests on changed files
- Report exact error messages. Do NOT paraphrase failures.

Step 5: Edge cases you probably missed
- What happens with null / empty / zero input?
- Unauthorized user?
- Network failure?
- Empty result set?
- Concurrent invocation?

Step 6: Honest confidence rating
- ✅ High — correct, tested, follows conventions
- ⚠️ Medium — likely correct but could not fully verify [explain what]
- ❌ Low — found issues [list them and fix immediately]

Be ruthless. Better to catch mistakes now than have them found in review.
```

### `/review` — structured diff review

Другий прогін. Окрема модель або окрема сесія проходить diff за чек-лістом.

```markdown
Review the current git diff (staged + unstaged) for this repository.

Analyze the changes through these lenses:

1. Bugs & Logic Errors — wrong conditions, off-by-one, null/undefined
   handling, missing edge cases, inverted boolean checks.
2. Security — SQL injection, XSS, exposed secrets, missing auth checks,
   unsafe user input.
3. Performance — N+1 queries, unbounded lists, unnecessary re-renders,
   missing indexes, oversized payloads.
4. Project Conventions — check against CLAUDE.md / AGENTS.md. Match the
   existing patterns (no ad-hoc abstractions).
5. Test Coverage — are new code paths tested? Are tests behavioral (not
   just "called this mock")?
6. Documentation — public methods/interfaces documented if project requires
   it? API changes reflected in README / OpenAPI?

Format findings as:
- 🔴 Critical — must fix before merge
- 🟡 Warning — should fix, potential issue
- 🟢 Suggestion — nice-to-have
- ✅ Good — call out things done well

Each finding: `path/to/file.ts:LINE — <description>`.

If the diff is clean — say so explicitly. Do NOT manufacture issues to
appear thorough.
```

### `/bug-hunt` — subagent-роль "senior bug hunter"

Запускається як окрема сесія (subagent або новий chat). Фокус — виключно на bugs, не на style/architecture.

```markdown
You are a senior software engineer with 20+ years of experience. You have
an obsessive eye for bugs, race conditions, logic errors, and behavioral
inconsistencies. You are NOT a linter — you do NOT comment on style, naming,
architecture, or documentation.

You hunt exclusively for:
1. Bugs — things that will break at runtime.
2. Logic errors — code that runs but produces wrong results.
3. Inconsistencies between files — mismatched types, divergent assumptions.
4. Race conditions & timing issues.
5. Silent failures — errors swallowed without handling.
6. State management bugs — stale closures, signal timing, subscription leaks,
   effect loops.

Process:
1. Use git to find changed files: `git diff --name-only HEAD` or
   `git diff --name-only --cached`.
2. For each changed file:
   - Read the full file.
   - Read the nearest dependencies (imports, parent components, called services).
3. Hunt through eight lenses:
   - Lens 1: Data flow — trace every variable source-to-sink; can it be
     null/undefined at any point?
   - Lens 2: Async / reactive — subscriptions cleaned up? Can signals emit
     before ready? Circular effects? Lost or duplicated emissions in
     switchMap/mergeMap?
   - Lens 3: State consistency — can multiple state updates get out of sync?
     Is state valid after error paths?
   - Lens 4: API contracts — HTTP payloads match backend? Response types
     correctly mapped? Error responses handled?
   - Lens 5: Cross-file consistency — interfaces, enums, service method
     signatures all aligned across callers?
   - Lens 6: Template bugs — UI expressions safe against undefined? Event
     handlers bound correctly? trackBy provided where needed?
   - Lens 7: Security — user input sanitized? Auth tokens in logs or URLs?
   - Lens 8: Boundary conditions — empty arrays, null objects, first/last
     item, single-item list, 1000+ items, double-clicks, destroyed-during-
     inflight-request?

Report each bug as:
🐛 [Critical/High/Medium/Low] — Brief title
📍 path/to/file.ts:LINE
What: exact bug
Why it breaks: specific scenario that fails
Fix: minimal code suggestion

Critical rule: NEVER flag something as a bug unless you can articulate the
SPECIFIC scenario in which it fails. "This could be a problem" is not good
enough — describe input, state, sequence of events. Be precise or be silent.

If zero bugs — say so clearly: "No bugs or inconsistencies found in the
changed files." Do NOT manufacture issues.

End with: summary of issues by severity and the single most dangerous issue
(if any).
```

### `/pr-review` — ревʼю чужого PR

Окремий промпт, бо контекст чужого коду відрізняється: ти не писав його, не знаєш намір автора, не бачив план.

```markdown
Review a pull request from another developer.

1. If I provided a PR number or URL, fetch the diff and description:
   - `gh pr view <number>` — description and linked ticket
   - `gh pr diff <number>` — full diff
2. If the PR references a ticket, fetch it to understand requirements.
3. Analyze through these lenses:
   - Correctness — does the code do what the PR description / ticket says?
     Logic errors, off-by-one, missing edge cases, error paths.
   - Bugs — null/undefined risks, race conditions, subscription leaks,
     state inconsistencies.
   - Security — SQL injection, XSS, exposed secrets, auth checks.
   - Project conventions — check CLAUDE.md / AGENTS.md.
   - Tests — are new code paths tested? Are tests behavioral and not just
     "called mock X"?
   - Missing pieces — acceptance criteria not covered? Missing migration?
     README update needed?
4. Format findings:
   - 🔴 Must fix — blocks approval
   - 🟡 Should fix — approve with changes
   - 💬 Question — need clarification from the author
   - 🟢 Suggestion — optional improvement
   - ✅ Good — things done well (always mention at least one)
5. Verdict:
   - ✅ Approve — no blocking issues
   - 🔄 Approve with comments — minor issues, can merge after addressing
   - ❌ Request changes — blocking issues found
6. Generate review comments ready to paste into GitHub / Linear. Each:
   - File: path/to/file.ts (line X-Y)
   - Comment: <text>

Do NOT post the review automatically. Output only.
```

### `/pr-fix` — обробка коментарів ревʼюера

Критичний нюанс: автоматичні bot-reviewer-и (Cursor Bug Bot, Copilot review) мають false-positive rate 20–40%. Промпт явно пришиває assessment-крок перед будь-яким фіксом.

```markdown
A reviewer (human or bot) left comments on my PR. Process them carefully.

**DO NOT START FIXING UNTIL I APPROVE THE ASSESSMENT.**

1. If I provided a PR number or URL, fetch:
   - `gh pr view <number> --comments` — all review comments
   - `gh pr diff <number>` — full diff
   - `gh pr view <number>` — PR description and linked ticket

2. For each comment, assess BEFORE fixing:
   - Does the comment identify a real bug or a false positive?
   - Does the suggested fix actually solve the problem (if one is given)?
   - Is the comment relevant to our project conventions (CLAUDE.md)?
   - For automated bots: be extra skeptical. Verify every claim against the
     actual code and project context.

3. Categorize each comment:
   - ✅ Valid — will fix: comment is correct; implement fix
   - ⚠️ Partially valid: concern is real but suggested fix is wrong; propose
     a better fix
   - ❌ Invalid — no change: comment is incorrect; draft a reply explaining
     why current code is right

4. Output the assessment table:
   | Comment by | File:line | Assessment | Action |
   |------------|-----------|------------|--------|

5. WAIT for my approval before implementing any fixes.

6. After approval — implement fixes for ✅ and ⚠️ only. For each:
   - Make the minimal change needed.
   - If the fix pattern exists elsewhere, check whether those places need the
     same fix.

7. Run `/verify` on the changes you just made.

8. Output the final report:
   - Comments total: X
   - Fixed: Y
   - Rejected with reply: Z
   - All checks passing: yes/no

Do NOT commit. Wait for my explicit approval.
```

```markdown
Rules:
- Subject: `<type>: <short description>` (<=72 chars, imperative mood).
  Types: feat, fix, refactor, docs, test, chore, perf, style, ci, build.
- Body (only if diff is non-trivial): WHY (motivation) and WHAT changed at
  a high level. Do NOT duplicate the diff line by line.
- Reference the ticket: `<PROJECT>-<NUMBER>` in the subject or footer per
  project convention.
- If there is a breaking change — add `BREAKING CHANGE: <description>` in
  footer.

Output format:

<subject>

<body if needed>

<footer if needed>

Show me the message. DO NOT commit.
```

## Як побудувати власну бібліотеку

Не починай з 20 промптів. Починай з 4 і дорощуй за сигналами.

### Starter set (Day 1)

Чотири команди, без яких подальші розділи плейбука розкачуються погано:

| Команда      | Коли використовується                              | Джерело в бібліотеці              |
| ------------ | -------------------------------------------------- | --------------------------------- |
| `/plan`      | Старт нетривіальної задачі                          | Planning section вище             |
| `/verify`    | Після будь-якої правки                              | Review section вище               |
| `/review`    | Перед commit / push                                 | Review section вище               |
| `/commit-msg`| Перед `git commit`                                  | Commit section вище               |

Цих чотирьох достатньо на перші 2–4 тижні. Додаткові промпти з'являються тоді, коли інженер фіксує у себе **повторюваний ручний prompt, який він уже набрав 3+ рази**.

### Path to growth (Week 2–Month 2)

Розширення в такому порядку окуповується найшвидше:

1. `/test-unit` — щойно з'являються перші unit-тести у проєкті.
2. `/pr-description` — щойно наростає кількість AI-згенерованих PR-ів і їх ручний опис стає bottleneck-ом.
3. `/bug-hunt` як subagent — коли команда відчула false-positive review-рівень від основної моделі (modely-compliant-трап).
4. `/pr-fix` — коли на проєкті зʼявився bot-reviewer (Cursor Bug Bot, Copilot), і false-positive-рівень з нього став проблемою.
5. `/feature-analyse` — коли зʼявляється роль BA і на вхід надходять великі feature-brief-и.

Кожен новий промпт додається з двома перевірками: `чи справді я робив це 3+ рази вручну?` і `чи є у мене еталонний запуск, з якого копіюю формулювання?`. Якщо "ні" на одне з питань — зарано.

### Версіонування і ревʼю

Бібліотека живе у репозиторії (`.claude/commands/`, `.cursor/commands/`, або відповідній директорії primary tool) і підлягає тим самим правилам, що і код:

- Будь-яка зміна команди — через PR із reviewer-ом.
- У PR-description — мотивація: "чому було недостатньо поточної версії", "що саме змінилося", "як перевірено".
- Тест: автор PR на цю команду перезапускає її на останній 1–2 реальних задачах і вставляє вихід як comment до PR.
- Breaking changes (вихід іншого формату, інші умови зупинки) — з префіксом `BREAKING:` у commit message, щоб команда побачила.

### Коли видаляти

Промпт видаляється з бібліотеки, якщо:

- Його не викликав ніхто протягом 4+ тижнів (у team-chat або через git-log `.claude/commands/`).
- Primary tool почав покривати його "нативно" — наприклад, Cursor Plan mode зняв потребу в кастомному `/plan`.
- Формулювання застаріло (стек змінився, команди білду інші, project conventions оновилися), а власник команди не підтримує.

Видаляти краще, ніж підтримувати застарілий промпт у бібліотеці. Застарілий промпт — це прихована regression-пастка: хтось новий у команді викликає `/plan`, отримує план за старими правилами, і фіча несумісна з поточною архітектурою.

> 💡 **Hint:** Бібліотека з 30 промптів, з яких реально використовуються 5, — гірша за бібліотеку з 5 промптів. Зайві команди засмічують autocomplete, змішуються у голові ("це який з трьох `/review`-ів?") і створюють ілюзію зрілості без її наявності. Раз на квартал проходь бібліотеку і безжально видаляй unused.

## Metaprompting: промпт, що пише промпт

Після 5–10 ручних промптів виникає паттерн, який окуповується: **мета-промпт, що генерує заготовку для нового промпту у бібліотеку**.

```markdown
I want to add a new prompt to our library. Help me write it.

Inputs I will give you:
- Name: `/<slug>`
- Goal (1 sentence): <what the prompt must achieve>
- Trigger examples (3 real examples of how the user would ask for it
  manually today)
- Existing prompt in the library that it is closest to: `/<slug>`

Your output:
A draft of the new prompt, following the six-block anatomy (Intent, Inputs,
Steps, Constraints, Output format, Verification hook).

Constraints on your output:
1. Steps must be numbered, each starting with an imperative verb.
2. Constraints block must include at least one "Do NOT ..." rule.
3. Output format must be specific — no "format as needed".
4. Must fit in <80 lines. If the logic does not fit — propose splitting into
   two prompts and stop.
5. If any input is missing, STOP and ask me for it. Do not guess.

After you produce the draft, I will test it on one real task. Then we refine.
Do not add the command file — I will do that after one successful test run.
```

Цей промпт скорочує цикл "idea → draft → test → refine" разів у три. Варто мати у бібліотеці одразу після того, як з'являються перші дві-три кастомні команди.

## Антипатерни

Типові помилки у організації prompt library, що зустрічаються у команд на першому-другому місяці роботи:

- **"Prompt dump" замість бібліотеки.** Файл `prompts.md` з 40 копі-пейстами з Twitter/Reddit без жодної структури. Ніхто з команди цим не користується, автор — теж, бо не може знайти потрібне. Фікс: у бібліотеці — тільки команди, що пройшли 3+ повторення у реальних задачах, з frontmatter/описом; без цього — не додавати.
- **Один mega-prompt замість кількох фокусних.** `/do-everything` — "спланує, зімплементить, напише тести, зревʼює, зробить commit". Працює у demo, провалюється у проді: модель втрачає scope у першому ж довгому turn-і. Фікс: кожен промпт — одна фаза циклу; `/plan` не робить apply, `/apply` не робить review.
- **Promptи без constraints.** "Refactor the service" без "do not change the public API" закінчується зламаними callers. Без явного `Do NOT ...` модель сама вирішує, що входить у задачу. Фікс: у кожному промпті — блок constraints із хоча б одним `Do NOT`.
- **Копіювання прикладів із статей 1:1.** Команда копіює "найкращий промпт з підбірки" з зовнішньої статті і дивується, чому він не працює на їх проєкті. Фікс: промпт адаптується під project conventions (стек, naming, команди білду); приклади з статей — стартова точка, не робоча версія.
- **Повна відсутність output format.** Промпт описує що зробити, не описує у якому вигляді повернути. Кожен запуск дає різну форму виводу — ніхто з цим не працює системно. Фікс: блок output format обов'язковий.
- **Prompt-дубль, що розходиться зі skill-ом.** У `/write-test` промпті — одні правила; у `.claude/skills/write-test/SKILL.md` — інші, бо skill оновили, а команду — ні. Модель отримує суперечливі інструкції. Фікс: у промпті — посилання на skill (`Follow conventions in @.claude/skills/write-test/SKILL.md`), а не дублювання вмісту.
- **Command без trigger-прикладів у description.** У slash-command-і description = "does stuff with diff". Автокомпліт у tool-і не допомагає, онбординг нового інженера — завжди питання "а що цей `/<команда>` робить?". Фікс: description = 1–2 речення з прикладами, коли команда викликається.
- **Prompt, що комітить без approve.** У бібліотеці живе команда `/auto-merge` або `/pr-prep`, що робить `git commit` і `git push` без людського gate-у. Фікс: у будь-якому implementation-промпті `Do NOT commit` — обовʼязковий рядок; stage і commit — завжди ручне.
- **Language drift.** Половина промптів англійською, половина — українською, деякі змішані. Модель продовжує відповідати мовою промпту — команда отримує mixed-language output у PR-описах і reviews. Фікс: усі промпти бібліотеки — однією мовою (рекомендовано English, оскільки technical terms і tool-output і так англійською).
- **Subagent для речі, що була б командою.** Створюється окремий subagent для `/commit-msg` або `/pr-description`, хоча isolated context там не дає нічого. Вище token-cost, складніший control. Фікс: subagent — лише там, де isolated context або persistent memory реально потрібні (independent reviewer, bug-hunter); для решти — slash-command.

## Метрики якості бібліотеки

Персональний мінімум, що варто переглядати раз на 2–4 тижні:

| Метрика                                      | Що вимірюється                                        | Healthy діапазон                              |
| -------------------------------------------- | ----------------------------------------------------- | --------------------------------------------- |
| **% промптів, використаних за 30 днів**      | Скільки команд з бібліотеки реально викликалися        | >70%; менше — чисти unused                   |
| **Частка команд із "WAIT for approval"**     | % implementation-промптів із явним human gate-ом       | 100% для Apply-промптів                       |
| **Час на виклик основних 4 команд**          | Від думки "треба план/review" до запуску              | <10 сек; довше — скіл memory не сформувався  |
| **False-positive rate у `/review` / `/bug-hunt`** | % коментарів, що виявилися помилковими                | <20%; більше — промпт недостатньо критичний   |
| **Drift** (prompt vs project state)          | Скільки команд посилаються на конвенції, яких у коді вже немає | 0; будь-який drift — видалити або оновити   |

Не варто автоматизувати усі ці цифри. Раз на квартал пройтися вручну по `.claude/commands/` і відповісти на п'ять питань — достатньо.

## Чек-лист готовності до розділу 7 (Anti-pattern Catalog)

Перед переходом до каталогу антипатернів у інженера має бути:

- Стартовий набір команд (`/plan`, `/verify`, `/review`, `/commit-msg`) закомічений у проєктному репозиторії.
- Хоча б одна кастомна команда, народжена із реальної повторюваної задачі, — не копія з цього розділу, а власна адаптація.
- Зрозуміло, коли інструкція йде у skill (контекст), а коли — у command (готовий prompt).
- Принаймні один subagent-промпт (`/bug-hunt` або еквівалент), що запускається як окрема сесія з іншою моделлю або role-ю для independent review.
- У бібліотеці немає промптів, що комітять без approve; у кожному implementation-промпті явний `Do NOT commit` / `WAIT for approval`.
- Проведено один цикл "промпт не спрацював → переглянули формулювання → зафіксували у PR із reviewer-ом" — тобто бібліотека версіонується і ревʼюїться, а не росте у `main` без контролю.
- У прочитаному вигляді, без запуску, кожен промпт зрозумілий новому інженеру. Якщо якийсь потребує "а, це треба знати контекст" — переформулюй або винеси контекст у skill.

Якщо хоча б один пункт не закритий — поверніся до відповідного розділу. Anti-pattern Catalog (розділ 7) припускає, що у інженера вже є достатньо повторюваних промптів, щоб побачити на них системні проблеми і назвати їх своїми іменами.
