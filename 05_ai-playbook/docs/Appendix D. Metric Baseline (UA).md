# D. Metric Baseline

**Статус:** Draft
**Дата:** 22 квітня 2026

Цей appendix задає числовий baseline для очікувань від AI-augmented розробки. Розділ використовується як референс у трьох сценаріях: (1) інженер оцінює, чи його особистий прогрес "нормальний"; (2) tech lead / PM планує AI-adoption і закладає реалістичні терміни; (3) ретроспектива — команда перевіряє, чи практика дала виміряний ефект, а не тільки "стало зручніше".

Базова теза розділу: **без вимірювань не можна відрізнити реальний прогрес від AI-euphoria.** Почуття "все літає" — нормальний побічний ефект перших тижнів; через місяць воно проходить, а метрики залишаються. Якщо метрики не рухаються — проблема в process-і, не в AI.

## D.1. Що читач має винести з цього розділу

Після прочитання інженер повинен:

- знати типовий діапазон прискорення по типах задач і не розраховувати на x10 там, де реалістично x2;
- розуміти, які метрики міряти особисто в перший місяць, і вміти швидко зібрати baseline без складного tooling;
- мати шаблон self-baseline-звіту, який можна заповнювати 5 хвилин на тиждень;
- розпізнавати сигнали регресії (ріст багів, ріст витрат на токени, стагнація циклу) — і знати, у який розділ playbook повертатися за фіксом;
- розуміти обмеження цих даних: self-reported, senior-skewed, не для performance review.

## D.2. Як читати цифри в цьому розділі

**Джерело даних.** Серія 1:1 інтервʼю з 14 інженерами (Phase 2, квітень 2026) + крос-перевірка з публічними звітами (GitHub Copilot Productivity Study 2024, Stack Overflow Dev Survey 2025, METR 2025 RCT).

**Природа даних.** Self-reported, ретроспективна самооцінка. Це **орієнтир, не KPI**. Інженер, що отримує ×1.8 замість очікуваного ×2, не "відстає" — він у діапазоні.

**Що таке "до" і "після".**

- **До AI** — ручне кодування в IDE без агентного режиму. Допускається snippet-generation (ChatGPT-копіпаст, старий Copilot-autocomplete) — це pre-2025 baseline більшості інженерів.
- **Після AI** — стабільна практика Plan → Apply → Review (Level 1 зрілості, розділ 1) з налаштованим CLAUDE.md/AGENTS.md і хоча б одним кастомним skill.

**Від чого залежить позиція в діапазоні.**

- Тип проєкту: greenfield ≫ brownfield ≫ legacy без документації.
- Якість context engineering: розгорнутий CLAUDE.md + skills підсилюють ефект у рази.
- Familiarity зі стеком: знайомий стек дає менший приріст; незнайомий стек + AI — найбільший leverage.
- Тип задачі: бізнес-логіка / CRUD / boilerplate — top диапазону; UI / accessibility / legacy refactor — нижній.

> 💡 **Hint:** Не порівнюй свої цифри з цифрами іншого інженера без поправки на стек і тип проєкту. x10 на greenfield TypeScript-стартапі і x1.5 на 10-річному Java-monolith — це обидва "у нормі". Неправильно — ставити собі мету "як у Х", правильно — ставити мету відносно **свого** baseline-у минулого місяця.

## D.3. Зведений baseline (сумарний профіль)

Цифри нижче — медіана по 14 senior-інженерах, що активно використовують AI у денній роботі.

| Показник | Типове значення | Діапазон |
|---|---|---|
| Частка AI-generated коду (merged PR) | 80–90% | 30% (legacy, свідомо обмежено) — 100% (mature Go service) |
| Мінімальний виграш швидкості на середніх задачах | ×2 (≈50%+) | ×1.3 (legacy refactor) — ×10+ (greenfield, незнайомий стек) |
| Виграш на бізнес-логіці / CRUD / API | 50–70% faster | 30% — 80% |
| Виграш на документації / spec / translations | ×10 | ×5 — ×20 |
| Виграш на unit-тестах за шаблоном | 70–90% faster | 50% — 95% |
| Виграш на UI-верстці (без Figma MCP) | ~20% | 0% — 40% |
| Виграш на greenfield з хорошим context eng. | 80/20 AI/manual | 70/30 — 90/10 |
| Витрати на інструменти ($/міс на інженера) | $70–120 | $20 (basic subscription) — $500+ (multi-agent experiments) |
| Середня кількість активних custom skills | 3–5 | 0 (agents-only підхід) — 15+ (feature-scoped skills) |

**Як інтерпретувати.** "Типове значення" — що бачить інженер через 1–2 місяці стабільної практики. "Діапазон" — де зараз реальні люди; вихід за діапазон в обидва боки — сигнал розібратися, чому (див. §D.7).

> 💡 **Hint:** Якщо через 2 тижні стабільної практики ти не бачиш хоча б ×1.5 ускорення на середніх бізнес-задачах — проблема не в AI. Повертайся до розділу 1 ("Де AI працює добре") і розділу 4 (Context Engineering). Типова причина — відсутній або мінімальний CLAUDE.md.

## D.4. Прискорення за типом задачі

Діапазон ефекту різко залежить від типу задачі. Таблиця нижче допомагає швидко оцінити реалістичну цільку ще до початку роботи.

| Тип задачі | Прискорення | Частка AI-generated | Коментар |
|---|---|---|---|
| Boilerplate (CRUD, scaffolding) | ×3–×5 | 90–100% | Максимальний leverage; найменший ризик |
| Unit-тести за шаблоном | ×5–×10 | 80–95% | 10 хвилин замість години; покриття треба перевіряти вручну |
| Бізнес-логіка / API endpoints | ×2–×3 | 70–90% | Ядро daily-роботи; тут і дається основна економія |
| Документація / spec / README | ×10 | 90–100% | Топ виграшу за часом; review обовʼязкове на фактаж |
| Переклади, міграції за патерном | ×3–×10 | 95–100% | Subagents / паралельні сесії працюють добре |
| Greenfield-проєкт зі специфікацією | ×5–×10 | 80–95% | Немає legacy-constraints; context engineering окупається з першого дня |
| Незнайомий стек (знаєш концепти) | ×10–×100 | 80–90% | Найвищий індивідуальний leverage; потрібно посилене review |
| Refactor в брaunfield-проєкті | ×2–×4 | 50–80% | Сильно залежить від якості документації і тестів |
| Bug fix з чіткими repro-steps | ×1.5–×3 | 50–70% | AI добре локалізує, але не завжди коректно фіксить — review рядок-за-рядком |
| UI-верстка без Figma MCP | ×1–×1.2 | 20–40% | Практично нульовий виграш; часто швидше руками |
| Дрібні правки (1 рядок, CSS-твік) | ×0.5–×1 | 0–30% | Часто повільніше, ніж руками; не витрачай токени |
| Accessibility / screen-reader | ×0.8–×1.2 | 10–30% | Вимагає ручної перевірки в браузері; AI систематично помиляється |
| Legacy-рефакторинг без документації | ×1–×2 | 20–50% | AI губиться; спочатку згенеруй AGENTS.md / інвентар, потім рефактор |

> 💡 **Hint:** Перед стартом задачі глянь у цю таблицю і визнач реалістичну цільку. Якщо задача з "нижньої" категорії (UI без MCP, accessibility, дрібна правка) — не витрачай 20 хвилин на prompt-craft; швидше зробити руками. AI — це важіль, а не універсальна заміна.

## D.5. Частка AI-generated коду

Самооцінка інженерів: який відсоток коду, що заходить у merged PR, написав AI.

| Діапазон | Частка групи | Типовий профіль проєкту |
|---|---|---|
| 90–100% | ≈36% | Mature Go/Node.js сервіси з розгорнутим context-ом; greenfield з хорошою spec |
| 80–89% | ≈14% | Змішаний brownfield + greenfield; активне використання skills |
| 50–70% | ≈29% | Enterprise brownfield; Plan → Apply → Review без важкого context engineering |
| 30% або менше | ≈7% | Свідоме обмеження заради контролю якості / legacy з високим ризиком регресій |
| Не фіксували | ≈14% | — |

**Медіана групи: ~80–90%.**

**Як користуватися цим числом.**

- Низька частка (<50%) **не означає** поганий інженер. Це може бути свідомий вибір на проєкті, де ризик регресії високий.
- Висока частка (>90%) **не означає** хороший інженер. AI-generated ≠ якісний; це значить тільки, що review-шар працює.
- Важливо не саме число, а **стабільність**: якщо в тебе частка гуляє 30% → 90% → 40% залежно від настрою — це сигнал, що workflow нестабільний (див. розділ 5).

> 💡 **Hint:** Не ганятися за "100% AI-generated" як за самоціллю. У групі є інженери зі свідомо обмеженою часткою 30% — вони не програють, вони оптимізують під інший ризик. Рішення "де AI, де руками" — частина Level 1 зрілості (розділ 1).

## D.6. Витрати на інструменти

Орієнтири бюджету "на одного інженера на місяць" з урахуванням primary + допоміжних інструментів.

| Профіль | $/міс | Що входить | Для кого |
|---|---|---|---|
| Basic | $20–40 | Claude Pro або ChatGPT Plus або Copilot Pro | Junior / mid у фазі навчання; легкі проєкти |
| Standard | $70–120 | Claude Max / Pro + 1–2 додаткових (ChatGPT, Gemini, Codex) | Стандартний профіль senior |
| Heavy | $150–300 | Max-tier плюс API-виклики (Codex automation, Figma Pro, MCP-сервіси) | Senior з активним automation і cross-project context |
| Experimental | $500+ | Multi-agent orchestration (BMad / AgentOS / Ralph-style loops) | Експериментальний режим; Level 3 зрілості |

**Сигнали про перевитрати.**

- Витрати зростають нелінійно місяць до місяця без зростання продуктивності — ймовірно запущено subagent-orchestration без depth-limit або циклічні agent-to-agent комунікації (див. антипаттерни у розділі 7).
- Вартість токенів > вартість зекономленого часу — tool-set підібрано не під той тип задач (напр. Opus на CRUD замість Sonnet / Composer).
- Heavy-profile на проєкті, де типові задачі — bug-fix і UI-твіки. Даунгрейд до Standard не просадить продуктивність.

> 💡 **Hint:** Витрати $500+/міс не є доказом майстерності. У групі був кейс: $500–600/міс на multi-agent setup з одночасним зростанням кількості багів і втратою контролю. Зворотний перехід на Standard ($100/міс) дав **вищу** чисту продуктивність. Орієнтуйся на чистий вихід (PR merged / баги на production), не на витрати.

## D.7. Попереджувальні сигнали (warning signs)

Метрики мають сенс тільки якщо читаються разом. Нижче — комбінації, що сигналізують про проблему.

| Сигнал | Ймовірна причина | Куди звертатися |
|---|---|---|
| Частка AI-коду росте, кількість багів на прод теж росте | Review-шар не встигає; trust-but-verify зламаний | Розділ 1 (Принцип 3), розділ 5 (Review) |
| Прискорення < ×1.5 через 2 тижні практики | Слабкий context engineering або невідповідний тип задач | Розділ 4, розділ 1 (Де AI працює добре) |
| Однакові помилки AI повторюються з сесії в сесію | Відсутній rule / skill для цього паттерна | Розділ 4 (Rules vs Skills) |
| Витрати токенів зростають нелінійно | Subagent-orchestration без depth-limit; цикл agent↔agent | Розділ 7 (антипаттерни Workflow) |
| Черга PR на ревʼю в команді зростає | Команда генерує швидше, ніж читає — командний bottleneck | Розділ 1 (Вимірювання ефекту), Level 2 рекомендується |
| "Код працює, але я не розумію, як" | Втрата контролю; AI вийшов за рамки Level 1 | Розділ 1 (Принцип 1), розділ 7 (Auto-accept) |
| Кількість ітерацій з AI до готового > 5 на середню задачу | Поганий план або відсутній CLAUDE.md | Розділ 5 (Planning), розділ 4 |
| Прискорення падає через місяць стабільної роботи | Контекст роздувся / skills застаріли / проєкт змінився | Ревізія CLAUDE.md і skills, розділ 4 |

> 💡 **Hint:** Найдорожчий warning sign — **ріст багів на прод після внедрення AI**. Якщо ти бачиш цю комбінацію у себе — зупинися і не нарощуй AI-використання далі. Спочатку стабілізуй review + тестування (розділ 5), потім повертайся до росту швидкості. Ріст багів = втрата клієнтської довіри, що коштує дорожче, ніж будь-яка економія часу.

## D.8. Що міряти особисто (перший місяць)

Мінімальний self-baseline. Пропозиція: 1 місяць, 5 хвилин на тиждень, олівцем або в одному markdown-файлі. Без дашбордів і telemetry.

**Обовʼязкові 5 метрик:**

1. **Час на задачу (до/після).** Порівняння "цю ж задачу руками" зі "цю задачу з AI". Достатньо 3–5 спостережень за тиждень; не треба міряти секундоміром — достатньо round-to-30min.
2. **Частка AI-generated у merged PR.** Приблизно, не точно. Орієнтуйся на "половина / більшість / майже все".
3. **Кількість ітерацій з AI** до готового коду. Промпт → генерація → правка промпту → нова генерація. Індикатор якості контексту.
4. **Кількість багів на production** за тиждень до і після внедрення AI. Прямий індикатор, що trust-but-verify працює.
5. **Витрати $/міс на AI-tooling.** Сума підписок + API-виклики.

**Опціональні метрики (додаткові сигнали):**

- Час на планування vs час на генерацію. Очікуваний ratio — 3:1 на користь планування (див. розділ 1, Принцип 2).
- Кількість створених / оновлених skills за місяць. Нульовий приріст — сигнал, що context engineering не розвивається.
- Частка PR, прийнятих з першої ітерації review vs потребували second-pass.

> 💡 **Hint:** Не автоматизуй збір baseline в перший місяць. Ручний облік у markdown-файлі дає більше insight-ів, ніж будь-який дашборд: ти фізично помічаєш, де витрачений час, і що спрацювало. Автоматизація — на другому місяці, коли вже знаєш, що саме автоматизовувати.

## D.9. Шаблон особистого baseline-звіту

Заповнюється раз на тиждень, займає 5 хвилин. Всі значення — approximations; точність не потрібна.

```markdown
# AI Baseline — Week N (YYYY-MM-DD)

## Context
- Проєкт: <назва / стек / стадія: greenfield|brownfield|legacy>
- Primary tool: <Claude Code | Cursor | Copilot | ...>
- Model(s): <Opus для plan / Sonnet для code / ...>

## Метрики за тиждень

| Метрика | Значення | Delta до попереднього тижня |
|---|---|---|
| Кількість завершених задач | N | ±M |
| Середній час на задачу (год) | X | ±Y |
| Оцінена частка AI-generated коду | % | ±% |
| Середня кількість ітерацій з AI до готового | N | ±M |
| Баги на production (за тиждень) | N | ±M |
| Витрати на AI-інструменти ($) | $X | ±$Y |

## Оцінка прискорення проти "руками"
- Тип задачі: <CRUD | business logic | refactor | UI | docs | ...>
- Оцінка: ×N (<1 якщо повільніше руками)

## Скіли / правила, оновлені за тиждень
- <+ new skill: назва — що покриває>
- <~ updated rule: назва — що змінилося>

## Warning signs (якщо є)
- <ex: однакова помилка з API-клієнтом повторилася тричі — треба rule>

## Висновки тижня
1. <що спрацювало>
2. <що не спрацювало>
3. <action на наступний тиждень>
```

**Як користуватися.** Через 4 тижні перечитай всі 4 звіти підряд. Тренди, що важливі:

- **Час на задачу** має падати до стабілізації, потім плато — це норма.
- **Частка AI-generated** має рости до 70%+ на 3–4 тиждень. Якщо стагнує на 30–40% — повернись до розділу 4.
- **Кількість ітерацій** має падати від 5–7 до 2–3. Якщо росте — погіршується контекст, ревізуй CLAUDE.md.
- **Баги на прод** НЕ повинні рости. Якщо ростуть — зупиняй нарощування швидкості, посилюй review.

> 💡 **Hint:** Baseline-звіт — не для менеджера. Це твій особистий інструмент. Не ділися ним у команді, поки не заповниш 4 тижні підряд — самооцінка в перший тиждень нестабільна, тренд видно тільки на горизонті місяця.

## D.10. Межі застосування цих даних

Дані в розділі D.3–D.6 мають обмеження, які треба памʼятати при інтерпретації.

**Що ці дані є.**

- Baseline для **senior**-інженерів з 5+ роками досвіду, що свідомо інвестували час у опанування AI-інструментів.
- Snapshot станом на Q2 2026 — моделі і tooling еволюціонують швидко; перевіряй актуальність кожні 3–6 місяців.
- Агрегація по різних стеках (Go, Node.js, .NET, PHP, Java, Flutter, React, Angular, Python/DevOps).

**Чим ці дані НЕ є.**

- Не KPI для performance review. Використання метрик для ранжування інженерів зламає процес збору даних на перший же місяць.
- Не універсальна "правда про AI". На junior / mid-level профілях цифри відрізняються (у деяких випадках сильніше — плюс на boilerplate, мінус на review-навичках).
- Не бенчмарк для тендерів / клієнтських пропозицій. Self-reported дані не конвертуються в гарантії — не цитуй як "Компанія дає x3 швидкості".
- Не екстраполюються на enterprise / regulated домени без поправки. Fintech, healthcare, defense можуть давати діапазон 30–50% проти типових 50–70%.

**Selection bias.**

- Дані зібрано з інженерів, що **самі визвалися** ділитися практиками. Це зміщує вибірку в бік "AI-enthusiasts". Реальна медіана по всій інженерній організації — нижча.
- Проєкти з жорсткими compliance-constraints (NDA, on-prem only, no external AI) у вибірку не увійшли. Для таких проєктів baseline потрібен окремий.

> 💡 **Hint:** Якщо тобі як tech lead потрібен baseline для **конкретного клієнтського проєкту** — не бери цифри з цього appendix буквально. Роби mini-baseline на 2–3 інженерах з **цього** проєкту протягом 2 тижнів за шаблоном §D.9. Це дасть реалістичну цільку, яку можна захистити перед клієнтом.

## D.11. Чек-лист готовності до baseline-трекінгу

Перед тим як починати вимірювання, інженер повинен могти відповісти "так" на всі пункти:

- [ ] Я розумію, що self-baseline — це особистий інструмент, не KPI для менеджера.
- [ ] Я маю стабільний workflow Plan → Apply → Review (розділ 5) — без цього дані будуть шумом.
- [ ] Я налаштував хоча б мінімальний CLAUDE.md / AGENTS.md (розділ 4).
- [ ] Я обрав 5 метрик з §D.8 і розумію, як їх фіксувати за 5 хвилин на тиждень.
- [ ] Я знаю, які warning signs з §D.7 стосуються мого проєкту і куди бігти, якщо вони зʼявляться.
- [ ] Я готовий вести облік мінімум 4 тижні перед тим, як робити висновки.

Якщо хоча б на один пункт відповідь "ні" — стабілізуй відповідну основу перед тим, як вмикати baseline-трекінг. Без фундаменту цифри дають false signal, на якому легко зробити неправильні висновки про AI або про себе.
