# 2. Вибір інструментів

**Статус:** Draft
**Дата:** 21 квітня 2026

Цей розділ визначає, які AI-інструменти використовують інженери і як обрати правильний набір під конкретний проєкт, стек і обмеження. Це не market overview і не ranking "найкращих" AI-продуктів. Це decision framework, який дозволяє інженеру свідомо сформувати власний toolset і адаптуватися до toolset проєкту без productivity gap.

Ключова теза розділу: **principles above tools**. Інженер, що опанував принципи з розділу 1 (plan-first, human-in-the-loop, context over prompt), ефективно працює з будь-яким AI-інструментом. Інструменти змінюються за місяці; дисципліна — константа.

## Що читач має винести з цього розділу

Після прочитання інженер повинен:

- знати, який набір primary tools підтримано і за якими критеріями вони відрізняються;
- уміти обрати primary tool під конкретний проєкт, стек, IDE-preference і security constraints;
- знати, коли використовувати Opus, Sonnet, GPT, Gemini чи локальну модель — і чому;
- розуміти cost-capability trade-off і не переплачувати за toki на рутинних задачах;
- знати, які допоміжні інструменти (ChatGPT, Gemini, Ollama, MCP) доповнюють primary tool і в яких ситуаціях;
- розуміти політику "freedom of choice" і межі, що її обмежують (client approved list, NDA, compliance).

## Інструменти / IDE

### Критерії вибору

Вибір AI-інструменту — інженерне рішення, а не питання смаку. Усі primary tools, описані нижче, реалізують однакові базові capabilities (code generation, chat, context management, agentic execution). Різниця — у деталях реалізації та в тому, наскільки інструмент lines up з існуючим workflow інженера.

Критерії, за якими оцінюється tool:

1. **Workflow fit.** IDE-centric (Cursor, Copilot в JetBrains) vs terminal-centric (Claude Code CLI). Інженер, що живе в JetBrains/Vim, — це інший вибір, ніж інженер на VS Code.
2. **Context engineering capabilities.** Чи є rules/skills/agents/commands; наскільки гнучко tool читає project-level config (AGENTS.md, CLAUDE.md, .cursor/rules).
3. **Model flexibility.** Чи можна обирати модель per task (Opus для плану, Sonnet для коду) чи інструмент прив'язаний до одного провайдера.
4. **Integration surface.** MCP-сервери, Git, CI/CD, Jira, Figma, client-specific frameworks (Blazor, Angular, Flutter SDK).
5. **Project constraints.** Approved tool list клієнта, data residency, NDA. Ці пункти закривають дискусію — див. підрозділ Policy нижче.
6. **Cost efficiency.** Чи вкладається tier у бюджет проєкту / інженера; чи є request-based обмеження, що стримують ритм роботи.

> 💡 **Hint:** Не вибирай tool за маркетингом. Дай йому 1–2 тижні на реальних задачах з проєкту, потім рахуй: час на задачу, кількість ітерацій, кількість багів. Якщо метрики не покращилися — tool не твій, незалежно від того, що пишуть у Twitter.

### Primary tools

Виділяється чотири primary-tool класи, що покривають домінуючі workflow-архетипи в компанії. За даними опитування інженерів, всі чотири зустрічаються на практиці, часто в комбінації.

**Розподіл primary tool (з 14 опитаних інженерів):**


| Primary tool              | Скільки використовують | Типовий workflow                                                     |
| ------------------------- | ---------------------- | -------------------------------------------------------------------- |
| Claude Code (CLI/Desktop) | 10 з 14                | Terminal-native; IDE-agnostic; autonomous agent для multi-file задач |
| JetBrains AI Assistant    | 4 з 14                 | Нативний AI в IntelliJ/WebStorm; часто поряд з Claude Code           |
| Cursor                    | 3 з 14                 | AI-native IDE на базі VS Code; найглибша інтеграція AI з редактором  |

| Codex (OpenAI)            | 3 з 14                 | Desktop App + CLI; multi-agent worktrees; cross-check поверх Claude  |

| ------------------- | ----------------------------------------------------------------------------------------------------------------------- |

**Кому підходить.** Інженерам, що вже на VS Code; проєктам із зрілим context engineering (AGENTS.md + skills); командам, що хочуть multi-model routing без зовнішніх інструментів.

**Обмеження.** 
 * Request-based pricing на Pro — стримуючий на інтенсивних днях

#### Claude Code

Terminal-native AI agent від Anthropic. IDE-agnostic — працює поруч із будь-яким редактором.


| Аспект              | Деталі                                                                                |
| ------------------- | ------------------------------------------------------------------------------------- |
| Середовище          | Terminal/CLI + Desktop; не прив'язано до IDE                                          |
| Context engineering | `CLAUDE.md` (project-level), skills, slash commands, sub-agents                       |
| Models              | Claude Opus, Sonnet                                                                   |
| Integrations        | GitHub CLI, filesystem, MCP; IDE-integration через filesystem watcher                 |
| Billing             | Pro $20/міс; Max 5× $100/міс; Max 20× $200/міс; Team Premium $100/seat; API per-token |


**Кому підходить.** Senior-інженерам, що живуть у JetBrains/Vim і не хочуть мігрувати IDE; задачам, де потрібне сильне multi-file reasoning і autonomous execution; командам, що експериментують із Level 2/3 (spec-driven, sub-agents).

**Обмеження.** Потрібен комфорт із CLI. Anthropic-only моделі — немає нативного GPT/Gemini. UI-зміни потребують перемикання між terminal і IDE/браузером для візуальної верифікації.

#### GitHub Copilot

AI plugin від Microsoft/OpenAI, що працює в більшості популярних IDE.


| Аспект              | Деталі                                                                                                                        |
| ------------------- |-------------------------------------------------------------------------------------------------------------------------------|
| Середовище          | Plugin — VS Code, JetBrains IDEs, Android Studio, Xcode                                                                       |
| Context engineering | `.github/copilot-instructions.md` — єдиний project-level файл                                                                 |
| Models              | Multi-model: GPT (Codex), Claude, Gemini                                                                                      |
| Integrations        | Native GitHub (PR review, code search), Agent mode                                                                            |
| Billing             | Free $0; Pro $10/міс; Pro+ $39/міс (всі моделі, включно з Claude Opus tier, 5× лімітів); Business $19/міс; Enterprise $39/міс |


**Кому підходить.** JetBrains-користувачам, що не хочуть змінювати IDE; проєктам, де клієнт дозволяє лише Copilot; задачам із великою кількістю boilerplate, де inline autocomplete — найсильніша фіча категорії. Самая низкая стоимость.

**Обмеження.** 
 * Context engineering поступається Cursor/Claude Code
 * Agent mode менш розвинений
 * Залежність від GitHub ecosystem.
 * менш вигідно з точки зору ціна/кількість отримуваних токенів, ніж тули від ЛЛМ провайдерів (Claude Code, Codex)

**Кому підходить.** Тим же, кому Claude Code; як незалежний reviewer поверх Claude-генерації (cross-check workflow); автоматизовані PR-review та bug-hunt; команди в OpenAI-екосистемі, що хочуть multi-agent паралелізм із worktrees та Automations.

**Обмеження.** Ecosystem lock-in на OpenAI-моделі. CLI молодший за Claude Code — менша зрілість community та tooling. Automations доступні лише через Desktop App.

**Обмеження.** Context engineering на рівні Copilot, а не Cursor/Claude Code. Autonomous agentic execution слабший.

### Decision tree: як обрати primary tool

Алгоритм ухвалення рішення "з чого почати на новому проєкті".

**Крок 1. Project constraints (жорсткий filter).**


| Constraint                                        | Рішення                                                  |
| ------------------------------------------------- | -------------------------------------------------------- |
| Клієнт має approved tool list                     | Використовувати лише approved tools. Крапка.             |
| Код не може залишати машину (NDA, data residency) | Local models (Ollama/LM Studio) + IDE-AI без cloud sync  |
| Робота у client VDI                               | Те, що доступно у VDI; інші tools — для offline research |
| Жодних обмежень                                   | Переходь до кроку 2                                      |


**Крок 2. IDE preference.**


| Якщо інженер живе в…                           | Default primary tool                   |
|------------------------------------------------|----------------------------------------|
| VS Code                                        | Cursor (або VS Code + Claude Code CLI) |
| JetBrains (IntelliJ/WebStorm/PyCharm)          | JetBrains AI + Claude Code CLI         |
| Vim/Neovim/Emacs                               | Claude Code CLI                        |
| Xcode / Android Studio / Visual Studio         | GitHub Copilot                         |
| **Немає чіткої преференції (починаєш з нуля)** | **Claude Code CLI**                    |

Якщо ти тільки переходиш на AI-assisted розробку і ще не маєш звички до конкретного IDE — починай з **Claude Code CLI + той редактор, що вже використовуєш**.

Логіка: Claude Code IDE-agnostic, встановлюється поруч із будь-яким редактором без міграції, дає повноцінне context engineering і agentic execution. Після 2–4 тижнів реальних задач стає зрозуміло, чи потрібен Cursor або JetBrains AI поверх.

> 💡 **Hint:** Не змінюй IDE заради AI-фіч. Зміна редактора коштує 2–4 тижні на адаптацію — це перекриє будь-який AI-виграш на старті. Спочатку освій workflow на знайомому інструменті, потім оціни IDE-switch.


**Крок 3. Характер задач на проєкті.**


| Домінуючий тип роботи                                      | Додатковий tool                              |
| ---------------------------------------------------------- | -------------------------------------------- |
| Autonomous multi-file refactoring, spec-driven, sub-agents | Claude Code (навіть поверх іншого primary)   |
| Великий обсяг boilerplate, CRUD, scaffolding               | Copilot + inline autocomplete                |
| Важка UI-верстка за Figma                                  | Cursor або Claude Code + Figma MCP           |
| Глибокий аналіз монорепо (>500k LOC)                       | Gemini Pro (1M context) як допоміжний reader |


**Крок 4. Cost tier.**


| Бюджет/міс | Рекомендована конфігурація                                                               |
| ---------- | ---------------------------------------------------------------------------------------- |
| ≤ $40      | Один primary tool на entry tier (Cursor Pro, Claude Pro, Copilot Individual)             |
| $70–120    | Primary (Claude Max або Cursor Pro+) + Secondary (e.g., Codex) для cross-check                           |
| $120+      | Primary + independent verification model (Codex/Gemini) + local model for sensitive code |


Типові витрати на інженера — **$70–120/міс**; outlier — $500+/міс на multi-agent workflow (не стандарт, експериментальний режим Level 3).

> 💡 **Hint:** Перша конфігурація — не фінальна. Ambassador-практика: перші 2 тижні інженер тестує 2 tools паралельно на однакових задачах, потім закріплює один primary + один допоміжний. Зафіксуй вибір у CLAUDE.md/AGENTS.md проєкту, щоб колеги знали, на чому ти працюєш.

## Моделі

### Стратегія model routing

Жодна модель не оптимальна для всіх задач. Свідомий вибір моделі per task — частина engineering discipline.

Базовий принцип: **smart models для планування, balanced models для виконання, fast models для automation.**


| Клас                | Моделі                              | Характеристика                                                             |
| ------------------- | ----------------------------------- | -------------------------------------------------------------------------- |
| Reasoning ("smart") | Claude Opus                      | Глибокий reasoning, multi-step, архітектурні рішення. Повільна, дорога.    |
| Balanced            | Claude Sonnet, GPT-Codex | Оптимальний баланс якості та швидкості для 90% повсякденного коду          |
| Execution ("fast")  | GPT Codex, Gemini Flash             | Швидка генерація, boilerplate, automation, великі обсяги рутинних операцій |
| Large context       | Будь-яка 1М модель                        | Context window до 1M tokens — аналіз цілих модулів, review великих діф-ів  |
| Local / private     | Gemma, Qwen Coder, DeepSeek V4             | Нульова передача даних назовні. Нижча якість, повний контроль              |


### Коли яку модель використовувати


| Задача                                            | Рекомендована модель         | Чому                                                                                    |
| ------------------------------------------------- | ---------------------------- | --------------------------------------------------------------------------------------- |
| Architecture design, technical spec               | Claude Opus                  | Найсильніший reasoning для multi-component рішень                                       |
| Multi-file refactoring                            | Claude Opus                  | Утримує контекст між файлами, розуміє architectural intent                              |
| Complex debugging (runtime race, multi-layer)     | Claude Opus                  | Будує довгі ланцюги причинно-наслідкових звʼязків                                       |
| Feature implementation (CRUD, API, бізнес-логіка) | Claude Sonnet                | Оптимальне співвідношення якість/вартість                                               |
| Unit/integration tests за патерном                | Claude Sonnet або GPT        | Достатня якість при низькій вартості; amb-практика: 70–90% тестів генерується за 10 хв  |
| Документація, ADR, README, API spec               | Claude Sonnet                | Writing quality на рівні Opus при значно нижчій вартості; 10× швидше за ручне написання |
| Boilerplate, configs, scaffolding                 | GPT Codex / Gemini Flash     | Швидкість важливіша за reasoning; patterns відомі                                       |
| Cross-verification плану чи diff-а                | GPT Codex або Gemini         | Незалежна перспектива — знімає blind spots первинної моделі                             |
| Аналіз великого codebase (> 100k токенів)         | Gemini Pro                   | Context window до 1M — дозволяє "прочитати" цілий модуль                                |
| Sensitive код (credentials, client data, NDA)     | Local (Qwen Coder, DeepSeek) | Дані не залишають машину                                                                |


### Cost-capability trade-off

Вартість моделей розходиться на порядок. Використовувати Opus для генерації boilerplate — марнотратство. Використовувати Sonnet для архітектурного рішення на critical path — економія, що конвертується в rework.


| Модель                | Відносна вартість         | Reasoning        | Швидкість            | Рекомендований % часу інженера                 |
| --------------------- | ------------------------- | ---------------- | -------------------- | ---------------------------------------------- |
| Claude Opus       | $$$$                      | Найвищий         | Низька               | 10–20% (plan, architecture, complex debug)     |
| Claude Sonnet     | $$                        | Високий          | Середня              | 50–60% (реалізація, тести, docs)               |
| GPT Codex / GPT-5.x   | $$                        | Середній-Високий | Висока               | 15–25% (verification, automation, boilerplate) |
| Gemini Flash          | $                         | Середній         | Висока               | 5–10% (large context, quick reads)             |
| Local (Gemma/Qwen/DeepSeek) | 0 токенів (hardware cost) | Низький-Середній | Залежить від machine | За потребою — sensitive data only              |


**Практичне правило:**

- Default — Sonnet.
- Opus — лише коли задача явно перевищує Sonnet: архітектура, multi-file refactor із tight coupling, баг, що не локалізується з першого разу.
- Codex/GPT — коли потрібна швидкість або незалежний reviewer.
- Local — коли NDA/security вимагає.

> 💡 **Hint:** Ambassador-червоний прапорець: якщо витрати токенів ростуть нелінійно (×3 за тиждень без ×3 задач), ймовірно, запущено subagent-орchestration без depth limit або Opus використовується там, де достатньо Sonnet. Щомісяця переглядай, на яких задачах ти реально тримав Opus, і скоротиш до 10–20%.

### Multi-model verification

Для critical decisions — архітектурних рішень, security-sensitive коду, складних алгоритмів — використовуй cross-model verification: генеруй рішення однією моделлю, перевіряй іншою.

Чому це працює: різні моделі навчені на різних корпусах і мають різні blind spots. Збіг відповідей — підвищена впевненість; розбіжність — явний сигнал для human review.


| Сценарій                           | Primary          | Verifier                           |
| ---------------------------------- | ---------------- | ---------------------------------- |
| Architecture decision              | Claude Opus      | GPT Codex або Gemini Pro           |
| Security-sensitive код             | Claude Opus      | Gemini + manual review             |
| Complex algorithm                  | Claude Sonnet    | Claude Opus або GPT                |
| Data migration / production script | Claude Sonnet    | Manual review + dry-run на staging |
| Large-diff PR review               | AI-review Sonnet | Codex bug-hunt поверх              |


3 з 14 опитаних інженерів формалізували dual-model verification як частину workflow (один для плану, інший для bug-hunt на diff-і). Це окупається на задачах із високою ціною помилки; на рутині — overhead.

> 💡 **Hint:** Dual-model verification варто використовувати не на кожній задачі, а на тих, де ціна помилки висока (production-міграція, billing-логіка, authentication). На CRUD з тестами — достатньо однієї моделі + ручного review.

## Політика

### Freedom of choice

Компанія **не нав'язує конкретний toolset**. Інженер вільний обирати будь-які інструменти, які працюють для нього, за умови дотримання principles з розділу 1 та project-specific constraints.

Підстави для цієї політики:

1. **Портативність навичок.** Інженер, що опанував plan-first, context-over-prompt, disciplined review, швидко адаптується до нового tool. Принципи переносяться — UI ні.
2. **Швидкість еволюції ринку.** AI tools оновлюються за місяці; жорсткий mandate застаріє швидше, ніж відбудеться rollout.
3. **Контекстна відповідність.** Різні проєкти, стеки, клієнти потребують різних tools. Універсальне рішення — subоптимальне.
4. **Portfolio readiness.** Інженер, що не залежить від одного tool, staffable на будь-який проєкт без productivity gap.

Freedom of choice **не означає** відсутність стандартів. Незалежно від обраного tool, інженер зобов'язаний:

- дотримуватися Human-in-the-Loop principle (ревʼю кожного diff);
- забезпечити належний context engineering (AGENTS.md/CLAUDE.md або аналог);
- задокументувати обраний toolset у проєктній документації;
- виконувати security та compliance вимоги клієнта.

### Пріоритет project constraints

Project-specific constraints **завжди мають пріоритет** над особистими вподобаннями.


| Constraint                           | Приклад                                  | Дія                                                                    |
| ------------------------------------ | ---------------------------------------- | ---------------------------------------------------------------------- |
| Client approved tool list            | Клієнт дозволяє лише GitHub Copilot      | Використовувати лише approved; інші — поза робочим часом для research  |
| Data residency / NDA                 | Код не можна передавати third-party APIs | Local models (Ollama/LM Studio), air-gapped environment                |
| Compliance (HIPAA, SOC 2, ISO 27001) | Потрібен audit trail AI-використання     | Документувати data flows; використовувати tools із no-train settings   |
| Client VDI / restricted workspace    | Робота лише в client-IDE або VDI         | Адаптувати workflow; інструменти поза VDI — лише для плану та research |


Constraints документуються на рівні проєкту (AGENTS.md, README, onboarding doc) і є частиною onboarding нового інженера.

> 💡 **Hint:** Перед тим, як запустити AI на клієнтському коді, перевір у контракті / NDA, чи не порушує це умови. Якщо документ не дає прямої відповіді — запитай PM або Security officer. "Я не знав" — не аргумент; AI-usage на коді третьої сторони — це ризик для компанії.

### Security guardrails

AI tools мають доступ до коду, terminal, файлової системи. Це зона підвищеної відповідальності.

Обов'язкові practices:

1. **"No train" / "no data storage" settings.** Для client projects — увімкнути в усіх AI tools, що мають таку опцію. Це вимога, не опція.
2. **Credentials isolation.** AI agent не має доступу до production credentials, API keys, secrets. Використовувати `.env` exclusion, `.gitignore`, secret manager. `.env`* файли в ignore-листі AI-tool'а.
3. **Package verification.** AI може рекомендувати неіснуючий або вразливий package (slopsquatting, typosquatting). Кожна AI-recommended dependency перевіряється перед додаванням: реальна сторінка npm/PyPI, зірки/downloads, дата останнього релізу, CVE-перевірка.
4. **Local models для sensitive zones.** Код із sensitive business logic або під жорстким NDA — через Ollama/LM Studio, не через cloud AI.
5. **Audit-trail для critical projects.** На compliance-проєктах — зберігати історію AI-сесій (логи, transcripts) для post-review у разі incident.

### Cost management

AI tools мають різні billing models. Свідоме управління витратами — частина engineering discipline.


| Стратегія        | Опис                                                                                                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Model routing    | Дорогі моделі (Opus) — лише на задачі, що цього вимагають. Рутину — на Sonnet/Codex/Flash.                                                                 |
| Context hygiene  | Чистий context = менше токенів = нижча вартість. Не тримай 3 skills, що не потрібні задачі; чисти context після 70% заповнення.                            |
| Tier awareness   | Розуміти обмеження свого pricing tier (Cursor Pro — request-limit; Claude Max — token budget). На intensive-днях перемикайся на tier, де не паузиш задачі. |
| Shared learnings | Rules/skills, що відпрацьовані на одному проєкті — шерити з командою. Витрати на context engineering амортизуються на N інженерів.                         |
| Monthly review   | Раз на місяць — переглядати витрати в розрізі tool/model. Якщо Opus > 25% часу — щось не так із routing'ом.                                                |


Типові витрати — **$70–120/міс на інженера**. Нижче — часто недостатньо для intensive workflow. Суттєво вище — зазвичай сигнал про неоптимальне model routing або experimentальний multi-agent setup.

### Документування toolset на проєкті

Кожен проєкт фіксує AI-setup у проєктних docs:

- **AGENTS.md / CLAUDE.md** — primary tool, models, skills, rules, обмеження клієнта.
- **Approved tools section** — explicit список дозволених tools (з посиланням на contract/NDA clause, якщо є).
- **Sensitive data zones** — директорії, де AI заборонено або дозволено лише local models.
- **Onboarding note** — як новий інженер на проєкті швидко підняти AI-workflow.

> 💡 **Hint:** Якщо на проєкті немає AGENTS.md/CLAUDE.md з описом AI-setup — почни з нього. Це годинна інвестиція, що окупається на кожному новому інженері та кожній новій задачі.

## Чек-лист готовності до розділу 3 (Tool Setup)

Перед переходом до setup інженер має могти відповісти "так" на всі пункти:

- Знаю, який primary tool (Cursor / Claude Code / Copilot / JetBrains AI / Codex) я обираю для поточного проєкту і чому.
- Знаю, які допоміжні інструменти (ChatGPT / Gemini / Ollama / MCP) мені потрібні і для яких задач.
- Розумію model routing: дефолт — Sonnet, Opus — на складне, Codex/GPT — на verification / speed, local — на sensitive.
- Знаю orієнтовний місячний бюджет ($70–120 baseline) і tier, який йому відповідає.
- Перевірив project constraints (approved list, NDA, compliance); знаю, які tools дозволені на цьому клієнті.
- Готовий задокументувати обраний toolset у AGENTS.md/CLAUDE.md проєкту.

Якщо хоча б на один пункт відповідь "ні" — повернися до відповідного підрозділу перед рухом далі.
